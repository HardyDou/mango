# 可执行质量契约规范

## 1. 定位

- 本文件是变更风险、测试类型、有效测试、证明路径、测试替身、质量基线和例外机制的长期规范源。
- 质量结论以 Git diff、质量契约、构建结果、运行轨迹和正式基线为证据；Agent、Skill、开发者或评审者的文字声明不能替代证据。
- 自动门禁必须 fail-closed：未知 role、phase、风险、测试类型、规则版本、缺失契约字段或过期例外均按失败处理。

## 2. 正式测试类型

正式测试只有以下三类：

| 类型 | 定义 | 最低真实性要求 |
|---|---|---|
| `UNIT` | 在进程内验证一个关键业务或关键技术决策单元 | 被测决策真实执行；允许替换证明路径之外的外部协作者 |
| `API` | 从 HTTP、事件、Consumer、Job 或 CLI 真实入口进入 | 真实经过入口、鉴权/租户、应用服务、Mapper 和隔离数据库中本次声明覆盖的部分 |
| `UI` | 从真实浏览器操作开始验证用户可见业务结果 | 真实经过前端、Mango 自有 API、后端和数据库；`E2E` 与 `UI` 同义 |

- 静态 Review、编译检查、架构检查、Mutation、截图和人工走查是验证手段或证据属性，不是新的测试类型。
- 组件或集成执行方式必须按其证明入口归入 `UNIT`、`API` 或 `UI`，不得用层级名称逃避真实性要求。

## 3. 风险与最低义务

| 风险 | 识别特征 | 最低义务 |
|---|---|---|
| `R0` | 常量、无分支访问器、声明式映射、生成代码、机械装配 | 静态 Review；不要求 `UNIT` |
| `R1` | 分支、算法、转换、边界值、错误处理或关键技术决策 | 静态 Review + `UNIT` |
| `R2` | 状态迁移、事务、持久化、权限、租户、事件或多个关键节点 | 关键节点 `UNIT` + 真实入口 `API` |
| `R3` | 用户可见页面或跨前后端完整业务结果 | `R2` 全部义务 + `UI` |

- 风险和义务由工具根据真实 diff 累加计算，只允许人工上调，不允许手工降级。
- 质量契约使用 `mango-pmo/schemas/quality-contract.schema.json`，必须绑定 base/head 提交、变更文件摘要、能力、验收结果、风险原因、测试义务和受保护证明路径。
- 每条验收结果必须具有“真实入口 → 关键决策 → 状态写入或用户可见结果”的证明路径；路径内生产实现不得被测试替身替换。

## 4. 有效测试

- `UNIT` 只覆盖简单推理无法可靠确认的关键决策、规则、边界、状态机、算法、异常和历史缺陷。
- 常量等于字面值、getter/setter、枚举声明、无分支透传、简单构造器、框架默认行为和机械装配由静态 Review 覆盖，不得作为必需测试证据。
- 只有 `not null`、`doesNotThrow`、接口 `200`、页面可打开、截图存在或 Mock 调用次数的测试，不能单独作为业务正确证据。
- 期望值与生产结果来自同一常量或同一实现函数的同源断言不能作为有效证据。
- 关键测试必须通过定向 Mutation 或故障注入证明断言能发现错误；冻结红线场景要求规定 Mutation 杀死率 `100%`。

## 5. Mock 与替身边界

- 允许替换第三方支付、短信、邮件、企业微信、不可控远程系统、时钟、随机源以及质量契约明确批准的证明路径外部边界。
- 禁止 Mock/Spy/Patch 被测类、被测方法、质量契约受保护节点或本次变更要证明的关键协作者。
- `API` 不得直接调用 Service 冒充入口，不得替换其声明覆盖的鉴权、租户、事务、Mapper 或数据库链路。
- `UI` 不得 route/intercept/fulfill Mango 自有 API；第三方边界替身必须在契约中登记精确目标和理由。
- 替身可以用于稳定注入外部失败，但测试结论不得超过真实执行范围。
- Mock 检查必须识别真实目标和运行路径，不能只依赖变量名、测试类名或单一正则文本。

## 6. Java 门禁

- Java 模块依赖使用 Maven effective model/reactor 图检查；`api` 不得依赖 `core/starter/starter-remote`，`core` 不得依赖 `starter/starter-remote`，`starter-remote` 不得承载领域实现。
- Controller 不得直接访问 Mapper；写入口必须执行参数校验，并保持统一响应、权限和租户边界。
- Service 写链路必须具有明确事务和幂等边界；Mapper/SQL 必须阻断无条件更新删除、危险全表操作、分页或租户条件遗漏。
- 结构检查、测试有效性和证明路径检查必须绑定标准 `mvn verify` 或统一质量门禁，未知规则不得只告警后继续。
- 新增或修改代码硬阻断；存量问题可以使用只读债务基线，但基线只能减少，触碰违规结构后必须重新验收。

## 7. Web 门禁

- 路由、菜单、权限 key、页面注册和真实页面必须形成可执行闭环。
- 页面和表单必须通过语义 DOM 证明标准布局/表单组件真实承担职责；隐藏节点、空壳包装和不可见字段不能冒充合规。
- 页面契约覆盖标题、主操作、加载、空、错、无权、字段、校验和提交状态；行为测试覆盖用户可见业务结果。
- UI/E2E `specs` 禁止直接使用 Mango 自有 API Mock、Element Plus 内部 class、固定等待、`force: true` 和依赖顺序的定位器作为长期方案。
- 关键页面在固定数据、视口和主题下保留最新截图基线；截图必须与业务断言绑定。

## 8. 报告与基线

- 正式基线保存在 `mango-docs/evidence/test-baseline/<capability-id>/{unit,api,ui}/latest`。
- 每个 `latest` 只保留当前脚本入口、机器报告、摘要、提交/环境/命令/数据集信息；`UI` 同时保留关键截图及视口、主题和差异阈值。
- 运行过程数据只写 `.runtime/pmo/<run-id>`，不得作为正式提交物。
- 普通测试和 `baseline check` 只能读取比较；只有独立 `baseline promote` 可以原子替换 `latest`。
- promote 必须在业务断言通过、差异已解释、责任人和批准人明确时执行；不得用更新基线消除失败。

## 9. 例外与 Flaky

- 例外必须登记规则编号、精确对象、原因、替代证据、责任人、批准人和到期时间；到期或字段缺失自动失败。
- 例外不能批准 Mock 受保护证明路径、写共享业务库、跳过关键红线或普通测试自动提升基线。
- Flaky 用例必须记录首次发生时间、责任人、证据和恢复期限；重试通过不能视为稳定通过。

## 10. 验收

- 每项门禁同时具有违规样例必须失败、合法样例必须通过的自动化测试。
- 确定性门禁评估使用独立临时目录、空 `HOME`、空 `CODEX_HOME`、相同输入和重复运行；它只证明门禁对冻结样本的判定能力，不得写成 AI 编码正确率。
- AI/Agent 空白上下文评估必须另行使用全新临时 checkout、临时 `CODEX_HOME`（只注入认证，不加载配置）、ephemeral 会话和相同模型/预算；Agent 看不到评分器与期望答案，生成者自述不参与评分。
- 两层评估分别报告，不得用确定性门禁结果替代 AI/Agent 生成实验。冻结关键红线检出率必须为 `100%`，合法边界正例关键误报率必须为 `0%`，总体正确率不得低于 `95%`。
- 任一关键红线漏检、受保护路径未真实执行或正式基线可被普通测试改写，整体验收失败。
