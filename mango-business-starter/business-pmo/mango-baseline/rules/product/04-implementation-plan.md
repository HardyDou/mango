# 实施计划规范

本文件是实施计划的唯一文档规范源。可执行投影位于 `mango-pmo/contracts/implementation-plan.json`，其中只能引用本文件的 `ruleId`。正式文档使用 `mango-pmo/templates/implementation-plan.md`。

实施计划承接已批准 TDD，只回答由谁、按什么顺序、修改哪些交付物、怎样验证和形成什么证据。它不能新增业务需求或替代技术设计。

## PLAN-SEC-001 文档控制与上游基线

- **目的**：固定计划身份、风险等级、TDD 摘要、计划责任和审批状态。
- **正向要求**：填写唯一 `documentId`、固定 `documentType: implementation-plan`、PMO/结构版本、与 TDD 一致的 `riskLevel` 和 `riskAssessmentEvidence`、状态动作、责任人与审批证据；上游必须是已批准 TDD 的 ID 和 SHA-256。
- **禁止项**：禁止没有设计基线就拆任务；禁止自行降低风险等级；禁止上游变化后继续使用旧计划；禁止占位符进入正式计划。
- **正例**：`PLAN-ANN-001` 引用 `TDD-ANN-001` 的完整摘要，风险等级保持 `L2`。
- **反例**：按当前需求直接开发，设计边做边补。错误原因：计划没有经过批准的技术输入。
- **机器判定**：`PLAN-META-001` 检查元数据、风险、上游 ID/摘要、状态动作和占位符；生命周期检查器验证摘要、风险一致和阶段顺序。

## PLAN-SEC-010 实施目标、范围与交付物

- **目的**：从 TDD 提取本次实施目标、范围、不处理范围和可交付物，防止计划压缩或扩张设计。
- **正向要求**：交付物使用 `DEL-xxx`；引用 TDD 设计项，写交付物、路径/模块、完成状态定义、验收来源和不处理边界；完整覆盖设计范围。
- **禁止项**：禁止把已批准范围改成 MVP、第一阶段或主链路；禁止新增无 TDD 来源交付物；禁止用“功能完成”代替具体产物；禁止把技术决策放在本章。
- **正例**：`DEL-001` 交付 API 契约、实现、测试和 README 更新，引用 `API-001/MOD-001/IMP-001`。
- **反例**：先做后端主流程，页面以后再说。错误原因：擅自缩减批准范围。
- **机器判定**：`PLAN-STRUCT-010` 检查交付物表、`DEL-xxx` 唯一、TDD 来源和完成定义；生命周期检查上游 ID 存在与覆盖。

## PLAN-SEC-020 工作分解

- **目的**：把设计拆成可独立执行、验证和提交的原子任务。
- **正向要求**：任务使用 `TASK-xxx`；写设计来源、交付物、责任角色、路径/模块、前置任务、具体动作、完成标准、验证 ID、预计批次和状态；一个任务只承担一个清晰目标。
- **禁止项**：禁止“实现功能”“处理前后端”等大而空任务；禁止任务没有设计来源或验证；禁止多个无关目标合并；禁止把未决定方案交给开发者临场选择。
- **正例**：`TASK-001` 根据 `API-001` 完成公开契约与参数校验，产出指定文件并由 `VAL-001` 验证。
- **反例**：`TASK-001` 完成公告所有功能。错误原因：范围不可控、不可并行、不可独立验收。
- **机器判定**：`PLAN-STRUCT-020` 检查任务表字段、`TASK-xxx` 唯一、来源、完成标准和验证引用；前置任务必须存在且依赖图无环。

## PLAN-SEC-030 顺序、依赖与里程碑

- **目的**：明确任务执行顺序、并行条件、关键依赖、里程碑和阻塞处理。
- **正向要求**：里程碑使用 `MS-xxx`；写包含任务、进入条件、完成条件、依赖、可并行任务、阻塞升级和责任人；依赖顺序与设计模块和发布依赖一致。
- **禁止项**：禁止仅按日期排列而不写依赖；禁止在契约未稳定前并行依赖其结果的任务；禁止发现阻塞后静默绕过；禁止循环依赖。
- **正例**：`MS-001 契约稳定`完成 API/错误码契约和契约测试后，前后端实现可并行。
- **反例**：前后端同时开始，后续再对接口。错误原因：没有稳定依赖和完成条件。
- **机器判定**：`PLAN-STRUCT-030` 检查里程碑表、`MS-xxx` 唯一、任务引用；`PLAN-DEP-030` 检查任务依赖无环且里程碑任务存在。

## PLAN-SEC-040 验证计划

- **目的**：把 TDD 测试设计和每个任务的完成标准转为可执行验证、环境、数据和证据要求。
- **正向要求**：验证使用 `VAL-xxx`；引用 `TC/SAC/TASK`，写验证层级、命令或步骤、环境、测试数据、权限/租户边界、预期结果、证据路径、责任人和失败处理；不复制测试规则正文。
- **禁止项**：禁止只写“运行测试”；禁止接口 200 或页面打开代替业务断言；禁止没有数据隔离和证据；禁止未执行时标记通过。
- **正例**：`VAL-001` 执行指定 API 用例，使用独立租户数据，断言状态冲突和错误语义并保存报告路径。
- **反例**：启动成功即验证通过。错误原因：没有覆盖设计与验收结果。
- **机器判定**：`PLAN-STRUCT-040` 检查验证表、`VAL-xxx` 唯一、测试/任务引用和必填证据字段；实际结果在验证阶段另行记录。

## PLAN-SEC-050 数据、升级、发布与回滚步骤

- **目的**：安排 migration、初始化、兼容升级、发布顺序、回查和回滚/补偿动作。
- **正向要求**：步骤使用 `REL-xxx`；引用 `DB/IMP/DEC`，写环境、前置检查、动作、顺序、数据备份/回填、兼容窗口、验证、失败停止条件、回滚/补偿和责任人；不适用需有 TDD 依据。
- **禁止项**：禁止只有发布命令没有回查；禁止不可逆数据变化没有备份/补偿；禁止改变 TDD 已定发布策略；禁止未发布却标记完成。
- **正例**：`REL-001` 先执行可回滚 schema 变更，再发布兼容代码，验证后清理旧入口；失败时停止后续批次并执行补偿。
- **反例**：上线后有问题再回滚。错误原因：没有停止条件、数据策略和可执行步骤。
- **机器判定**：`PLAN-STRUCT-050` 检查发布步骤表、`REL-xxx` 唯一、来源、验证与回滚字段；命令安全和真实发布由发布门禁验证。

## PLAN-SEC-060 文档与能力同步计划

- **目的**：安排规则索引、README、能力地图、业务指南、测试资产和变更记录的同步责任。
- **正向要求**：文档项使用 `DOC-xxx`；引用 `IMP/DEL/TASK`，写目标文档、变化、责任人、完成条件、检查命令和不适用依据；长期规则只能链接 PMO 规范源。
- **禁止项**：禁止公开能力变化但遗漏说明；禁止 README/设计文档复制长期规则；禁止默认“文档不受影响”；禁止无责任人。
- **正例**：`DOC-001` 更新模块 README 的接入方式和验收入口，并运行能力文档检查。
- **反例**：代码清楚，无需文档。错误原因：没有评估业务消费者影响。
- **机器判定**：`PLAN-STRUCT-060` 检查文档表、`DOC-xxx` 唯一、来源和检查入口；能力文档专项 checker 在交付前执行。

## PLAN-SEC-070 风险、阻塞与例外

- **目的**：安排实施风险、依赖阻塞和经批准例外的处理、升级、到期与回收。
- **正向要求**：条目使用 `RISK-xxx`；写风险等级、触发、影响、预防、应对、责任人、截止时间和状态；例外必须写适用 ruleId、范围、批准人、证据、到期版本/日期和跟踪 Issue。
- **禁止项**：禁止无期限例外；禁止用例外绕过安全、租户或真实交付红线；禁止把当前范围内未完成项写成“后续优化”；禁止阻断项未关闭仍 `NEXT`。
- **正例**：`RISK-001` 外部沙箱不稳定，定义替代验证、升级责任和截止时间；不改变真实发布验收要求。
- **反例**：测试环境不稳定，本次不测。错误原因：没有证据、替代方案和批准边界。
- **机器判定**：`PLAN-STRUCT-070` 检查风险表、`RISK-xxx` 唯一、枚举和必填值；存在 OPEN/BLOCKED 条目时禁止 `NEXT`；例外字段完整性由门禁检查。

## PLAN-SEC-080 实施追踪矩阵

- **目的**：证明每个 TDD 设计项均有任务、验证和交付物，每个计划项均来自批准设计。
- **正向要求**：逐项登记上游设计 ID、交付物 ID、任务 ID、验证 ID、发布/文档项和覆盖说明；覆盖所有 TDD 本地设计/测试/影响项和所有本地计划 ID。
- **禁止项**：禁止孤儿任务或验证；禁止遗漏设计项；禁止用一个任务覆盖多个独立交付物却无拆分说明；禁止引用不存在 ID。
- **正例**：`API-001 -> DEL-001 -> TASK-001 -> VAL-001`，并关联 `DOC-001`。
- **反例**：所有设计均包含在开发任务中。错误原因：无法证明覆盖和责任。
- **机器判定**：`PLAN-TRACE-080` 检查本地 ID 全覆盖、引用存在和无孤儿；生命周期检查器读取 TDD 合同检查所有上游 ID 全覆盖。

## PLAN-SEC-090 阶段判定与审批

- **目的**：确认计划可执行、无未关闭阻断、覆盖完整并获得实施责任人批准，决定是否允许开发。
- **正向要求**：登记计划 checker、handoff、依赖图、阻断/例外、风险等级和审批证据；L2/L3 必须存在完整 BRD/SRS/TDD/Plan 链；全部门禁通过才允许 `NEXT`。
- **禁止项**：禁止 AI 自报 PASS；禁止仅凭任务清单进入开发；禁止复杂任务跳阶段；禁止审批后上游变化仍继续。
- **正例**：所有设计项有 TASK/VAL，依赖无环、阻断为 0，实施负责人批准后编排器更新 `APPROVED/NEXT`。
- **反例**：计划已足够详细，可以先开发再补审批。错误原因：门禁可被绕过。
- **机器判定**：`PLAN-GATE-090` 检查门禁表、风险和元数据一致；生命周期 checker 验证完整链路、摘要、审批和覆盖。

## PLAN-BOUNDARY-001 阶段边界

- **目的**：阻止实施计划重新定义需求或设计，并阻止把计划冒充完成事实。
- **正向要求**：所有交付物、任务和验证均引用 TDD；新发现需求/设计缺口必须 `STOP/ASK` 并回到上游修订；计划只描述将执行动作。
- **禁止项**：禁止新增业务目标、功能、页面、API、表或技术方案；禁止改变模块/API/数据/安全决策；禁止声称代码、测试、发布已完成；禁止把验证计划当验证结果。
- **正例**：任务按 `API-001` 实现既定契约；若契约缺字段则停止并修订 TDD。
- **反例**：开发时新增一个批量接口更方便。错误原因：计划越权改变技术设计和范围。
- **机器判定**：合同检查每个计划项的 TDD 来源、禁止完成态措辞和上游覆盖；是否存在隐性新设计由 Tech Lead 与实施负责人评审。
