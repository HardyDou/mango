# 测试用例与自动化工程化流程

## 1. 定位

- 本文件约束测试用例从需求验收项登记、设计映射、自动化实现、执行分层到结果基线沉淀的全流程。
- 本文件规定各交付模式下 M09-M16 如何实施。模式决定流程成本，验证能力仍按真实入口和可观察结果启用，不得为了承载测试反向补文档。
- FULL 的 BRD/SRS/TDD/Plan 分别承载业务验收、系统验收、测试技术映射和执行命令；STANDARD 在一个文件承载这些映射；SIMPLE 直接追踪任务成功条件。
- 后端测试细节遵循 `rules/backend/08-test.md`；前端测试细节遵循 `rules/frontend/04-test.md`；测试资产目录遵循 `rules/04-test-assets.md`。

## 2. 生命周期门禁

1. FULL 在适用 BRD/SRS 建立验收项，STANDARD 在单文件建立验收项，SIMPLE 以任务成功条件作为验证来源。
2. FULL 技术设计或 STANDARD 单文件可把适用 M09-M16 映射为测试用例候选项；SIMPLE 不得为测试映射反向生成文档。
3. M09-M13 存在真实观察目标时才实现对应稳定测试契约和必要锚点。
4. 按模式和事实范围执行 M09-M16，把真实结果写入约定证据载体；例外记录依据和剩余风险。
5. 用户授权 PR 时，只说明已确认措施对应的新增、修改、废弃用例和证据；发布阶段使用独立发布流程，不在此处增加措施。
6. 只有当前目标需要把测试资产交给后续消费者时，才输出相应测试交接信息，不创建无消费者的固定交接包。

### 2.1 任务风险等级

任务风险使用 `L0` 至 `L3`；测试用例执行优先级使用 `P0` 至 `P3`。两者用途不同，禁止混用。风险必须分别评估需求影响和解决方案风险，最终等级取二者较高值：

`finalRiskLevel = max(requirementImpactLevel, solutionRiskLevel)`

| 等级 | 需求影响判定 | 解决方案风险判定 |
|---|---|---|
| `L0` | 不改变业务结果、系统行为或公共契约；仅说明、拼写、格式或局部视觉位置发生变化 | 改动隔离、无逻辑/数据/安全影响，可通过单点回退立即恢复 |
| `L1` | 只改变单一页面、单一内部能力或单一角色的局部行为，不影响公共契约、持久化、安全和主干流程 | 使用成熟模式在单模块内实现，依赖少、影响可定位、回退简单且不需要数据修复 |
| `L2` | 影响重要业务结果、公共契约、持久化、权限、租户、状态或异常边界，但影响面可限定 | 进入共享组件、多层链路、事务、数据迁移或授权边界；失败后需要受控恢复或存在明显回归面 |
| `L3` | 影响核心用户主流程、跨域/跨服务结果、重大安全或数据一致性、平台发布或 PMO 核心门禁 | 方案跨服务/跨模块、涉及并发或不可逆数据、平台架构/发布链路，或不确定性与失败后果高 |

风险判定必须回答五类事实：影响哪些用户和入口、影响哪些契约/数据/安全边界、波及范围、失败后果、回退与恢复难度。代码行数、文件数量、Issue 标签和“缺陷”“重构”等关键词都不能单独决定等级。

| 阶段 | `riskLevel` 含义 | 要求 |
|---|---|---|
| BRD | 需求影响预评 | 只基于业务目标、对象、流程和业务后果，不假定技术方案 |
| SRS | 系统影响预评 | 在 BRD 基础上补充用户入口、系统行为、数据和非功能影响，不得降级 |
| TDD | 最终风险 | FULL TDD 显式评估解决方案风险并计算 `max`；STANDARD 在单文件记录同一事实 |
| Plan | 最终风险 | 与已批准 TDD 完全一致，不得重新定级 |

- **正向要求**：先写需求影响事实，再写解决方案事实；同一需求采用不同方案时允许得到不同最终等级；新事实只能升级或维持等级。最终等级映射到 SIMPLE、STANDARD 或 FULL；验证能力按目标观察面选择。
- **禁止项**：禁止按改动行数、文件数或关键词单独定级；禁止只评需求不评方案；禁止把“实现很简单”作为权限、租户、事务或跨服务变更的降级依据；禁止按 L0-L3 机械增加无真实入口的测试。
- **正例**：只移动现有按钮且不改变可见条件、动作和接口，需求影响与 CSS 方案均为 L0；同一局部需求若选择改共享布局引擎，需求影响仍为 L0/L1，但方案风险可升至 L2；跨租户授权缺陷即使只改一行，失败后果仍至少为 L2/L3。
- **反例**：按钮右移 8px 也要求 BRD、SRS、TDD、Plan 和全流程 E2E；一个跨租户条件只改一行就判 L1；看到“API”一词便机械判 L2。错误原因：均未依据真实影响、方案和恢复事实。
- **机器判定**：PR 必须填写 `Requirement impact`、`Solution risk`、`Final risk`、`Delivery mode` 和 `Workspace decision`；检查器验证最终值等于二者最大值、模式映射正确，并检查对应文档承载方式。

### 2.2 测试层级术语

- 单元测试验证单个规则、算法、状态机或转换。
- 组件测试验证前端组件或模块内协作。
- API 测试验证 HTTP 契约、输入输出、权限、状态和错误行为。
- 集成测试验证 Spring 装配、Mapper、数据库、事务、消息及模块协作。
- 入口级流程测试验证 app/API/安全过滤器/跨模块主流程，但不称为 E2E。
- `UI/E2E` 是同一概念，只指从浏览器用户入口执行的端到端测试；没有浏览器用户入口的后端测试不得命名为 E2E。

## 3. 用例登记字段

测试用例候选项至少登记：

| 字段 | 要求 |
|---|---|
| 用例 ID | 使用 `TC-xxx`，长期自动化用例必须稳定 |
| 来源 | 引用 `AC-xxx`，必要时同时引用 `BO/BF/BR/PG` |
| 场景 | 一个用户目标或一个业务规则结果 |
| 优先级 | `P0`、`P1`、`P2` 或 `P3` |
| 测试层级 | 单元、API、集成、入口流程、组件、UI/E2E、截图、手工 |
| 自动化判断 | `AUTO`、`MANUAL` 或 `EXCEPTION` |
| 测试数据 | 数据来源、唯一标识、清理策略 |
| 稳定契约 | 语义锚点、API fixture、测试账号或环境要求 |
| 执行入口 | 测试文件、标签、命令或手工步骤 |
| 证据 | 报告、截图、trace、日志或人工记录路径 |
| 状态 | `CANDIDATE`、`AUTOMATED`、`MANUAL`、`FLAKY`、`DEPRECATED` |

## 4. 业务开发交接输出

业务开发者消费 Mango 能力或业务 starter 时，交付材料必须能直接判断：

- 哪些验收项已经沉淀为测试用例。
- 哪些用例可以由业务项目复用、复制或按模块标签执行。
- 执行入口是什么，包括测试文件、标签、命令和必要环境变量。
- 测试数据、测试账号、租户、权限和清理边界是什么。
- 失败、阻塞、例外、flaky 时应该查看什么证据、如何重跑、何时升级 Mango Issue。

业务开发交接输出落到交付契约或验收证据，不新增第二套规范源。

## 5. 用例颗粒度

- 一个长期 UI/E2E 用例只能覆盖一个用户目标和一个可验证业务结果。
- 一个用例可以包含必要的前置、操作和清理步骤，但不得把多个独立能力合并成“主流程通过”。
- 表单校验、局部组件状态、接口参数校验和纯业务规则优先放到组件、API 或单元测试；不得为了覆盖率堆 UI/E2E。
- 只有排序、排名、分页位置、拖拽顺序本身是业务目标时，才允许按第几个断言。

优先级定义：

| 优先级 | 定义 | 执行要求 |
|---|---|---|
| `P0` | 登录、权限、租户、核心入口和核心业务可用性 | 每次 PR 或 AI 交付优先执行 |
| `P1` | 关键业务闭环和高风险回归 | PR 按影响范围执行，主干定时全量执行 |
| `P2` | 边界、历史缺陷、复杂组合和低频流程 | 夜间或发布前执行 |
| `P3` | 探索、临时诊断或一次性验证 | 不作为长期资产，任务结束后删除或升级 |

## 6. 固定验证、复核与验收措施

PR 和交付使用固定目录中的 M09-M16，不再把集成测试并入 API，也不再要求每个任务从四类套餐中至少选择一项：

| 措施 | 证明对象 | 典型实现 |
|---|---|---|
| `M09 静态验证` | 结构、格式、配置、代码规则、类型或编译事实 | checker、lint、typecheck、compile、diff review |
| `M10 单元测试` | 独立规则、算法、状态转换或函数行为 | 单元测试、组件局部测试、无外部边界模块测试 |
| `M11 集成测试` | 模块、数据库、框架装配或组件协作 | 集成测试、真实持久化测试、应用装配测试 |
| `M12 API 验证` | API 或服务入口契约、权限、数据和失败行为 | API 测试、服务入口流程测试 |
| `M13 UI 验证` | 用户可见布局、交互、路由和浏览器结果 | 定向截图、视觉检查、UI/E2E |
| `M14 专家复核` | 专业不确定性、高影响决定或治理自修改 | 相关专家独立复核 |
| `M15 外部状态回读` | GitHub/Gitea 等外部平台真实配置和运行状态 | 平台 API/CLI 回读与期望值比对 |
| `M16 人工验收` | 自动化无法充分证明的业务、视觉、责任或现场结果 | 责任人按步骤确认并记录证据 |

AI 只对命中固定触发事实的措施提出建议，并逐项等待用户确认。不同措施可以组合，但不能因成本顺序、风险等级或 PR 类型自动累加；M11 和 M12 只有在“真实协作”和“服务入口”两个事实都存在时才同时推荐。

- **正向要求**：纯规则建议 M10；数据库或框架真实协作建议 M11；服务入口变化建议 M12；浏览器用户结果变化建议 M13；自动化不足时才建议 M16。
- **禁止项**：禁止用 M09 证明运行时行为；禁止 mock 数据库后声称 M11 通过；禁止用 M12 冒充 M11；禁止后端任务仅因 L3 强制 M13；禁止 UI 变化自动追加 M16。
- **正例**：按钮位置调整建议 M09 和 M13；租户查询修复按真实事实建议 M10、M11、M12，只有专业不确定性或高影响决定明确存在时再建议 M14。
- **反例**：修改按钮间距后自动执行全仓单测、全部 API 和完整 E2E；事务修复只跑格式检查；API 用例连接真实数据库便把 M11 与 M12 合并为一项。错误原因：措施触发事实和证明对象被混淆。
- **机器判定**：PR 校验用户确认的措施 ID、精确值、人工确认证据和已启用措施证据；机器不判断未列出的措施是否应该启用，也不要求为未触发措施写跳过理由。

## 7. 前端自动化稳定契约

前端 UI/E2E 必须优先使用业务语义锚点：

| 属性 | 用途 | 示例 |
|---|---|---|
| `data-page` | 页面能力 | `menu.management` |
| `data-surface` | 业务区域、表单、弹窗或抽屉 | `menu.form` |
| `data-action` | 业务动作 | `menu.create` |
| `data-field` | 业务字段 | `menu.name` |
| `data-record-key` | 业务记录、行、卡片或树节点 | `menu:e2e-menu-001` |
| `data-state` | 业务状态 | `ready`、`empty`、`error` |

规则：

- 锚点按业务语义命名，禁止按布局、顺序、组件结构或样式命名。
- 页面布局变化、按钮位置变化、弹窗改抽屉、表格改卡片时，业务语义锚点不应改名。
- 删除或改名长期锚点视为测试契约变化，必须同步测试用例、脚本和结果基线。
- E2E `specs` 中禁止直接依赖 `.el-*`、布局 class、深层 DOM、`nth()`、`first()`、`last()`、`waitForTimeout()` 和 `force: true`。
- 无法避免的 DOM 细节只能封装在 `support`、`fixtures`、`tasks` 或 `components` 中，并写明原因。

## 8. 复用结构

长期自动化测试按以下层次复用：

| 层次 | 责任 |
|---|---|
| `fixtures` | 登录态、租户、测试账号、测试数据、浏览器上下文和清理 |
| `tasks` | 业务动作，例如创建菜单、发布流程、发起审批 |
| `selectors` | 语义定位器和少量兼容封装 |
| `assertions` | 业务结果、页面状态和错误检查 |
| `specs` | 只表达用例目标、步骤和断言，不写复杂 DOM 查找 |

禁止把临时 workaround、具体测试断言或一次性数据构造过度抽成公共复用能力。

## 9. 测试数据和隔离

- 自动化用例必须创建或声明自己的测试数据，不依赖人工预置数据、其它用例残留状态或执行顺序。
- 写入数据必须使用可识别唯一前缀，例如 `E2E_`、`IT_`、`TC_<用例ID>_`。
- 用例必须提供前置清理或后置清理；清理只能处理本用例创建的数据。
- 涉及真实后端、租户、权限、支付、工作流、文件或消息时，必须登记账号/租户标识、数据集和环境边界。

## 10. 执行策略

| 场景 | 最低执行要求 |
|---|---|
| 本地开发 | 执行模式和事实启用的 M09-M16，并限制到受影响模块和入口 |
| AI 交付 | 记录需求影响、方案风险、最终等级、模式、验证与剩余风险；只执行能够证明本次结果的检查 |
| PR | 稳定 required check 始终产生结果；内部只运行公共轻量门禁和受影响模块/能力的定向套件 |
| 主干定时 | `P0` 和 `P1` 全量 |
| 夜间 | `P0`、`P1`、`P2` 全量，可包含多浏览器 |
| 发布前 | 发布影响范围内 `P0/P1` 必须通过，`P2` 按风险执行或登记例外 |

默认日常 UI/E2E 使用 Chromium；Firefox/WebKit 放到夜间、发布前或兼容性专项。CI 重试通过仍必须记录 flaky 风险，不能视为稳定资产。

### 10.1 Maven 架构门禁范围

- **正向要求**：普通后端 PR 根据 Git 变更映射最近 Maven 模块，质量门禁只扫描直接修改模块，不使用 `-am` 或 `-amd` 扩大 Reactor；依赖构建和消费者兼容性根据具体依赖事实推荐并由用户确认。架构规则仍以 `changed/no-new-violations` 阻断本次新增违规。根聚合 POM、全局 parent、架构规则/插件、债务基线或门禁 workflow 变化时升级为全 Reactor。完整历史债务盘点由 `.github/workflows/architecture-debt-inventory.yml` 定时或手工执行。
- **禁止项**：禁止每个普通 PR 无条件扫描全部 Reactor；禁止只检查改动文件而漏掉其 Maven 模块和消费者；禁止使用 partial-reactor 报告写回全局债务预算；禁止以提速为由跳过本次新增架构违规。
- **正例**：修改 `mango-system-core` 时，质量门禁只选择该模块并由架构验证模块执行规则；公共 API 变化的消费者编译作为独立验证；修改根 POM 时执行完整 Reactor；前端按钮位置变化不启动 Java。
- **反例**：每次 starter baseline 同步都编译 212 个无关 Maven 模块；普通 core 质量扫描通过 `-am` 或 `-amd` 扩大到未修改模块；只对一个 Java 文件跑文本检查而不验证所属模块；用局部报告宣称全仓债务下降。错误原因：前两者浪费资源，后两者证据范围不足。
- **机器判定**：`classify-pmo-check-scope.mjs` 输出 `backend_mode=none|partial|full` 和直接修改模块 selectors；PR workflow 的 partial 质量门禁必须使用这些 selectors 和 `requireFullReactor=false`，且禁止 `-am`、`-amd`；full 分支才运行债务预算检查；workflow 自身和全局架构治理文件变更必须 fail-closed 到 full。

## 11. 用例资产维护

- 自动化用例必须支持按单用例、标签/能力组合和全量套件执行。
- Playwright 用例标题必须带优先级和模块标签，例如 `@p0 @menu 平台管理员可维护菜单`。
- 后端入口级流程测试使用 JUnit 5 `@Tag`，至少包含 `flow` 和能力标签；存量 `e2e` 标签在文件被修改时迁移。
- `FLAKY` 用例必须登记原因、证据和修复计划；连续影响交付时必须降级、隔离或删除。
- 业务废弃时删除用例；业务路径变化时更新用例；只是布局变化时应优先维护锚点或 task 封装。
- 新增回归缺陷时，必须补充对应用例候选项，并判断自动化层级。

## 12. 禁止事项

- 禁止 BRD/SRS 没有可追踪验收项就进入 TDD。
- 禁止设计没有测试层级映射就进入开发。
- 禁止把所有验收项默认自动化成 UI/E2E。
- 禁止把只打开页面、接口 200、截图有画面或无 console error 当作完整验收。
- 禁止用不稳定脚本冒充长期测试资产。
- 禁止自动化测试向共享业务库写入不可清理脏数据。
- 禁止脱离事实机械降级流程；也禁止对权限、租户、事务或其它运行时结果只做无法观察目标的编译、启动或页面打开检查。
- 禁止机械全选 M09-M16；每项建议必须有真实触发事实，并以用户确认值为准。

## 13. 空白上下文验收

- PMO 规则、模板、Agent、Skill 或检查器变化属于 `L3/FULL` 治理任务。使用治理决策记录、实施计划、独立空白上下文 Agent 正例/反例/非触发/边界测试和专家复核，不伪造四份产品文档。
- 空白上下文用例至少记录 prompt、可用输入、期望 Skill/动作、禁止输出、实际结果和判定。
- 至少包含一个按钮位置 `L0` 用例，证明 Agent 只推荐与可观察目标相关的定向静态/视觉验证；包含一个 L3 仓库治理用例，证明 Agent 不自动生成 BRD/SRS/TDD/Plan；包含一个跨租户任务，证明 Agent 推荐业务规则、技术设计、真实入口验证等由事实触发的相关措施并等待用户确认；包含同一需求采用不同方案得到不同最终等级的用例；包含一个无 UI 的后端 `L3` 用例，证明 Agent 不伪造 UI 验证。
- 机器可判定的触发、文档结构、引用、状态和退出条件由 eval/checker 阻断；业务语义质量由独立 Agent 和阶段审批共同验收。
- 正例：空白 Agent 面对按钮位置调整选择 `L0 + STATIC/UI`；面对跨租户审批选择 `L3 + API` 真实入口验证并在无浏览器入口时明确跳过 UI。
- 反例：测试 Agent 读取了本次实现对话后复述预期结论；只测 Skill 能触发，不测不应触发、缺输入和越界请求。
