# Mango Issue 登记与处理 Runbook

## 1. 触发条件

业务开发使用 Mango 时，确认问题由 Mango 框架、starter、CLI、模板、前端包或发布物料引起，必须登记 Mango Issue。

Mango 维护任务已经位于非 `main` 工作区，且用户明确要求在当前任务解决问题时，该指令直接确认修复范围：必须在当前工作区处理，不要求先重复登记 Issue，也禁止为该问题再建 worktree。用户明确要求登记时按本文件登记；意图不清时先询问。

非缺陷类建议也必须登记 Issue，并标记为建议。

处理已有 Mango Issue 时，必须先按本文件的处理流程确认事实和现状，再决定是否进入修复、验证、关闭或补充信息。

## 2. 仓库

Mango Issue 统一提交到：

```bash
https://github.com/HardyDou/mango/issues
```

处理已有 Issue 时，以用户提供的 Issue URL 和实际托管平台为准，不因为 Mango 新 Issue 默认登记在 GitHub 就迁移或重复登记已有 Issue。

## 3. 标题

标题格式：

```text
P0|P1|P2: <影响对象> <问题摘要>
```

示例：

```text
P0: Mango Flyway migration blocks upgraded business backend startup
P1: Generated mango.dev.json does not adapt to renamed business app folders
```

## 4. 标签

- 缺陷：`bug`
- 能力优化：`enhancement`
- 文档或流程：`documentation`
- 信息不足：`question`

没有合适标签时，先用最接近标签，不得因为标签不全而不登记 Issue。

## 5. 优先级

- `P0`：阻断服务启动、构建、发布、登录、核心验收或数据安全。
- `P1`：不阻断主流程，但导致业务升级、开发、验证明显不稳定或需要人工绕行。
- `P2`：体验优化、文档补充、低风险建议。

## 6. 证据

Issue body 必须包含：

- Mango 版本：CLI、npm 包、Maven 依赖或 Git commit。
- 消费项目场景：业务项目名称、启动方式、命令。
- 复现步骤：最少可复核步骤。
- 实际结果：错误日志、截图、命令输出或失败断言。
- 期望结果：Mango 应提供的行为。
- 影响范围：阻断、绕行成本、涉及模块。
- 业务任务记录：当前业务任务中登记 Issue 地址和阻塞状态。

日志和截图放在业务任务证据目录；Issue 中只贴关键摘要和证据路径，禁止上传密码、token、密钥、客户敏感数据。

## 7. 命令

```bash
gh issue create \
  --repo HardyDou/mango \
  --title "P1: <影响对象> <问题摘要>" \
  --label bug \
  --body-file /path/to/issue-body.md
```

紧急问题可直接写 body：

```bash
gh issue create \
  --repo HardyDou/mango \
  --title "P0: <影响对象> <问题摘要>" \
  --label bug \
  --body "## 现象
...

## 影响
P0

## 证据
..."
```

## 8. 处理已有 Issue

接到“处理 Issue / 修复 Issue / 关闭 Issue / Issue #xxx”任务时，必须先加载 Issue 信息，不得在未知 Issue 内容和影响范围时直接进入开发 preflight 或修改代码。

必须执行：

1. 读取 Issue 标题、正文、标签、状态、评论、关联 PR、最新相关提交和当前分支状态。
2. 判断 Issue 类型：缺陷、能力优化、文档流程、信息不足或已完成待关闭。
3. 判断问题是否仍存在：检查 `main`、相关发布物料、关联 PR 和本地代码；不能仅凭记忆判断。
4. 判断是否可复现：能复现时记录复现命令、环境、数据、日志或截图；不能复现时记录缺失条件和需要补充的信息。
5. 判断是否已被修复：如已修复，必须给出修复来源、版本或提交依据，并执行可行的回归验证后再建议关闭。
6. 判断影响范围：明确涉及路径、模块、接口、数据库、前端页面、测试、文档或发布物料。
7. 制定处理方案：关闭、补充信息、复现验证、修复、回归、发布或转为新 Issue。
8. 只有确定需要修改受版本控制文件、形成验证结论、发布、提交或 PR 时，才按明确的 role、phase、task 和 paths 执行 PMO preflight；`References` 只在边界不明确时定向查阅。
9. preflight 按策略决定 M01：主工作区自动 `CREATE`，已有任务 worktree 自动 `REUSE`；只有用户要求 `MAIN_EXCEPTION` 时提示风险并取得确认。

禁止：

- 未读取 Issue 内容就直接按猜测修复。
- 未判断问题是否仍存在就创建分支或改代码。
- 未复现或未说明不可复现原因就声明修复完成。
- 已被修复的问题重复改代码。
- 用登记 Issue 流程替代处理已有 Issue 流程。
- 当前非 `main` 工作区已经收到解决指令后，再为同一问题创建 worktree 或只登记 Issue 不处理。

## 9. 修复完成与验收记录流程

制作证据、上传附件、发布验收评论和更新 Issue 状态是修复工作的标准收尾流程，由处理该 Issue 的 Agent 在同一任务中完成。代码或文档修复并完成回归验证后，Agent 必须继续执行本节流程，直到 Issue 状态已经更新，或出现无法自行消除的环境、权限或外部系统阻塞。

Agent 根据 Issue 涉及的软件、验收对象、运行环境和交互方式，现场决定证据组合，并选择、发现或制作合适的采集方式。取证没有固定步骤、顺序、工具或证据套餐；可以随着复现和回归结果动态调整。决策以以下结果为准：

- 相关：证据直接对应 Issue 的问题对象和修复前后差异。
- 充分：其他人能够据此复核关键验收路径和结论。
- 可访问：证据已发布到 Issue，或使用验收者稳定可访问的链接。
- 适度：只收集有证明价值的材料，不为满足形式制造无意义证据。

平台交互工具按实际 Issue 托管平台选择：

- GitHub Issue 优先使用 `gh` 读取正文、评论、关联信息和状态，并发布评论或更新状态。
- Gitea Issue 优先使用 `tea` 完成对应操作。
- CLI 是建议入口，不是固定依赖。先确认工具可用且当前身份具备目标仓库权限；当 CLI 不支持所需附件或交互时，由 Agent 根据现有授权选择平台 API、浏览器或其它可验证方式，不得把未上传的本地路径当作 Issue 证据。

Issue 涉及对应页面或页面交互时，修复前后页面截图和关键验收路径视频属于必要证据。Issue 不涉及页面时，由 Agent 选择最能直接证明结果的过程数据，页面截图和视频不强制。

取证完成后，把证据选择、不适用原因和实际证据评论到 Issue，并重新读取评论确认内容可访问。验收结论为 `PASS` 时，继续关闭 Issue 或标记为 `resolved`、`已解决` 或等价终态，再次读取 Issue 确认最终状态。

提交、PR、测试通过或本地证据目录本身都不能替代 Issue 评论。

证据评论应覆盖以下可验收信息，字段可以根据 Issue 合并、改名或调整顺序，不要求机械套用模板：

- 修复来源：修复版本、commit 和关联 PR；尚未发布时明确说明可验证的分支或制品。
- 验证环境：操作系统、浏览器或运行时、Mango 版本、关键配置与测试数据边界。
- 验收对象与证据选择：说明 Issue 是否涉及对应页面、选择了哪些证据以及为什么足以支持他人复核。
- 页面截图与视频：Issue 涉及对应页面或页面交互时，提供修复前后页面截图和关键验收路径视频并标明观察点；前置现象已由 Issue 原证据完整覆盖时可引用原评论。
- 过程数据：复现和回归命令、关键输入、日志、请求响应、断言、测试报告或性能数据，以及修复前后对比结论。
- 验收说明：最短复核步骤、实际结果、剩余限制或风险和明确结论。

选定的截图、视频和过程数据必须作为 Issue 可访问附件上传，或使用对验收者稳定可访问的 PR、制品和报告链接。只写本地绝对路径、临时路径、Agent 会话路径或未上传的证据目录不算完成。上传前必须脱敏，禁止包含密码、token、密钥、客户敏感数据或不必要的个人信息。

Issue 不涉及对应页面时，在证据评论中将页面截图和视频标记为不适用并说明原因，不要求制作无意义的页面媒体。所选过程数据仍必须覆盖修复前后对比和完整验收路径。

以下任一情况表示标准收尾流程尚未完成。Agent 必须先继续制作、补充、脱敏、重新上传或重新验证证据，不得把这些工作直接留给用户或验收者：

- 证据评论尚未发布或发布失败。
- 根据 Issue 对象决策出的必要证据缺失，或页面类 Issue 缺少修复前后截图和关键路径视频。
- 附件或链接不可访问、仍在上传、已经过期或只能由本机访问。
- 验证结果失败、结论不明确或仍存在阻断验收的问题。
- 证据包含尚未完成的脱敏风险。

继续处理后仍因环境、权限或外部系统故障而无法完成时，记录具体阻塞并返回 `STOP`，保持 Issue 打开，不添加 `resolved`、`已解决` 或等价标签/状态。不要仅因为证据尚未制作就立即停止。

可选评论结构：

```markdown
## 修复验收证据

- 修复来源：<version / commit / PR>
- 验证环境：<OS / runtime / Mango version / key config>
- 验收对象与证据选择：<target / page applicability / evidence decision>
- 修复前截图：<required for page issues; otherwise N/A with reason>
- 修复后截图：<required for page issues; otherwise N/A with reason>
- 回归视频：<required for page issues; otherwise N/A with reason>
- 过程数据：<commands / logs / assertions / report links>
- 复核步骤：<minimal reproducible verification steps>
- 实际结果：<observed result>
- 限制与风险：<none or details>
- 验收结论：PASS | FAIL | BLOCKED
```

证据评论及其附件检查通过且验收结论为 `PASS` 后，标准流程继续执行关闭或标记已解决步骤。关闭或更新状态后，再次读取 Issue 确认最终状态与目标一致。

## 10. 后续处理

- Issue 创建后，必须把 URL 写回当前业务任务记录。
- Mango 缺陷阻塞当前模块且没有同等质量替代方案时，暂停该模块开发。
- 当前任务结束时，必须提醒开发者根据 Issue 结论决定升级 Mango、更换方案或调整业务计划。
