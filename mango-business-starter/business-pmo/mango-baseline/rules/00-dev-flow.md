# Mango PMO 总流程

## 1. 定位

- `mango-pmo` 是 Mango 的唯一规范源。
- `mango-docs` 只放设计文档、Sprint 计划、交付记录。
- 规范、流程、角色、Skill 一律放 `mango-pmo`。

## 2. 目标

- AI 能基于 Mango 完成一句话需求。
- 产出可开发、可验证、可发布的结果。
- 降低歧义、返工、越权、遗漏。

## 3. 标准流程

### 3.0 业务消费 Mango 问题处理

业务开发使用 Mango 时发现疑似 Mango 框架、starter、CLI、模板、前端包或发布物料问题，必须先按 [Mango Issue 登记 Runbook](./07-mango-issue-runbook.md) 归因、登记和回写任务记录。

本节只保留流程入口；Issue 触发条件、登记字段、阻塞处理和任务结束提醒统一维护在 `rules/07-mango-issue-runbook.md`。

### 3.0.1 PMO 加载原则

- preflight 输出本次任务可能需要的 `References`、适用 `Code baselines`、工作区策略和检查命令。
- `References` 是定向查阅入口，不是开工前全文阅读清单；只有边界不明确或 checker 无法解释失败时查阅具体条目。
- 开发任务优先读取选中的代码模板、模板 manifest 和目标模块源码事实，不批量加载规则文档。
- 领域参考只在路径或任务事实命中时输出；禁止因为“前端”“后端”泛词一次性返回整套规范。
- 简单问答、只读定位、状态查看、日志查看、目录查看、worktree 列表不触发正式流程。
- 任何受版本控制文件改动都遵循默认 worktree 隔离；规范、设计文档和交付记录不再拥有直接修改 `main` 的默认例外。

PMO preflight 的首要目的不是审批命令或强制阅读，而是解析工作区策略、代码模板、参考资料和验证入口。Agent 先识别用户意图和变更风险，再决定是否进入 PMO。

Agent 在长会话和复杂任务中容易出现以下问题：

- 忘记本项目已有规范，按通用经验或旧习惯执行。
- 想不到本次任务对应的前端、后端、数据库、测试、发布、文档或工作区规则。
- 只关注眼前报错，忽略权限、租户、真实数据、验证证据和发布影响。
- 顺手扩大范围、修历史问题，或把非本次问题混入当前交付。
- 用“能编译、能启动、能打开页面”替代真实验收。

判定原则：

- 先判断用户意图：是交付变更、方案/验收、发布/提交，还是查看、同步、定位、本地运维。
- 再判断风险：是否存在规范遗漏风险，或会影响受版本控制文件、服务行为、接口/数据库/测试/构建、发布物料、长期规范或交付结论。
- 用户意图是“交付一个变更”，或风险会影响可交付结果时执行。
- 用户意图只是“查看状态、同步仓库、整理本地环境”，且风险只限本地状态时不执行。
- 如果不触发的操作过程中发现需要人工修改文件、解决冲突、修复问题或形成交付结论，先停止当前操作，再按实际任务执行 preflight。

意图与风险判定：

| 用户意图 | 风险特征 | 是否执行 |
|----------|----------|----------|
| 查看、解释、定位、列举 | 只读，不改变仓库和运行态 | 不执行 |
| 纯同步仓库 | 只执行 fast-forward/fetch，不解决冲突、不形成验证结论 | 不执行 |
| 本地运维 | 只影响本机进程、缓存、端口、未跟踪临时文件 | 不执行 |
| 编码、修复、重构、配置变更 | 需要召回开发、测试、边界、工作区规范 | 执行 |
| 设计、测试方案、验收、发布、提交、PR | 需要召回交付、证据、发布、PR 规范 | 执行 |
| 规范、流程、Agent 入口治理 | 需要召回规范唯一源和文档归档规则 | 执行 |
| 冲突处理、失败修复、回滚选择 | 需要人工判断并改变代码或历史 | 执行 |

以下情况必须执行：

- 按设计文档、plan、Sprint 计划或交付台账进行开发、验证、发布或治理。
- 人工新增或修改代码、接口、数据库、测试、前端页面、构建配置。
- 新增或修改设计文档、Sprint 计划、交付记录、规范或 Agent 入口。
- 做架构设计、技术方案、测试方案、验收、发布、提交或 PR。
- 处理 `git pull`、`rebase`、`merge` 产生的冲突，或为同步后的失败检查做修复。
- 用户明确要求“按 PMO / 按计划 / 按设计文档 / 按交付台账”推进。

以下情况不需要执行：

- 简单问答、概念解释、使用说明。
- 只读定位文件、类、接口、配置或快速查看模块现状。
- 查看 git 状态、目录结构、日志、报错片段，但不进入修复或交付。
- 执行纯仓库同步命令，例如 `git fetch`、`git pull --ff-only`、`git remote update`，且不人工编辑文件、不解决冲突、不做交付验证。
- 查看或刷新 GitHub Issue、PR、分支、tag、release 列表，但不创建、修改或发布。
- 安装依赖、清理本地缓存、停止本地进程、查看端口占用等本地运维操作，且不修改受版本控制文件。
- 用户明确要求“先快速看看 / 暂不进入 PMO 流程”。

### 3.0.2 工作区自动隔离与 main 例外

PMO preflight 输出工作区事实和 M01 策略决策。只要需要修改受版本控制文件，Agent 按 [交付模式与保障措施规范](./11-delivery-assurance.md) 自动创建或复用任务 worktree；默认决策不再逐次 Ask User。只有用户明确要求在 `main` 或主 worktree 修改时，才提示风险并取得 `MAIN_EXCEPTION` 确认。

- `reuse-current-worktree`：当前已经位于非 `main` 任务工作区，策略决策为 `M01=REUSE`。
- `worktree-required`：当前位于主工作区且任务会修改受控文件，策略决策为 `M01=CREATE`。
- `main-exception-authorized`：用户明确要求并确认主工作区例外，策略决策为 `M01=MAIN_EXCEPTION`。
- `needs-human-check`：目标或修改范围不足，先确认任务边界；它不是要求展示 M01 问卷。

工作区判定顺序：

1. 先读取当前分支和 `git worktree list --porcelain`，再判断是否需要创建工作区；只有会话和分支事实证明属于同一任务时向 preflight 传 `--reuseCurrentTask true`。
2. 当前已在非 `main` 分支或非主工作区时，用户明确要求解决的问题必须在当前工作区处理；不得再次创建 worktree，也不得改为登记 Issue 来规避处理。
3. 用户明确要求登记 Issue 时只登记；用户没有说明是当前修复还是登记，且范围确实无法判断时，必须先询问用户。
4. 当前位于主工作区、属于新的独立任务且没有可复用任务 worktree 时，preflight 直接决策 `CREATE` 并创建新 worktree。

以下事实使策略决定 `M01=CREATE`：

- 代码、接口、数据库、测试、前端页面、构建配置。
- `mango/**`、`mango-ui/**`、`mango-business-starter/**`、`scripts/**`、`.github/**`。
- `package.json`、`pnpm-lock.yaml`、`pom.xml`、migration、`src/**`。
- 发布脚本、启动脚本、CLI、starter、模板和发布物料。

规范、设计文档、交付记录和 Agent 入口只要发生受控文件修改，同样适用自动隔离。只读查看和纯同步不创建 worktree。

同一任务或同一 PR 在本地只能对应一个开发 worktree。用户在当前非 `main` 工作区继续提出并要求解决的问题，以及验收返工、Review 修改、CI 修复、PR 门禁修复和交付台账未完成项，必须复用当前或原任务 worktree 和原任务分支。

### 3.1 需求

必须完成：

1. 明确目标、范围和验收标准
2. 分别计算需求影响和方案风险，取较高值形成 `L0-L5` 最终等级
3. 按等级建立无文档、单文档或 L5 四文档资产

产出：

- 模式要求的需求资产或会话内目标基线

### 3.2 设计

必须完成：

1. 明确影响模块、接口、数据和验证范围
2. 按 `L0/L1` 无文档、`L2-L4` 单文档、`L5` 四文档形成设计计划，并映射适用 M09-M16
3. 需要结构化承载时可复用 [交付契约与设计说明规则](./01-delivery-contract.md)，不得把它变成目录外的默认措施

产出：

- 模式要求的设计或计划资产

### 3.3 开发

必须完成：

1. 确认风险、交付模式和保障基线已经解析
2. 按 M01 策略值自动创建或复用 worktree；main 例外必须有人工作证
3. 选择 preflight 返回的适用 `Code baselines`，先在隔离目录渲染并通过模板自检，再集成到任务工作区
4. 新增代码以代码 baseline 为结构和实现基准；当前项目配置、接口与领域模型提供业务输入，历史实现只提供兼容事实
5. 本次修改触及的旧文件必须清理同一符号或局部代码块内可保持行为不变且可定向验证的违规
6. 不扩大历史债务；跨公共契约、数据、安全、事务、模块边界或显著扩大验证面的旧问题登记为独立治理项

禁止：

- 绕过自动隔离策略，或在缺少明确人工确认时使用 main 例外。
- 多个任务共用同一个开发 worktree。

产出：

- 代码
- 模式和观察事实要求的测试或其它验证资产

### 3.4 验证

必须完成：

1. 运行模式和观察事实启用能力对应的检查命令
2. 验证改动范围
3. 记录未完成项和风险
4. 只执行能证明目标的 M09-M16，并逐项记录真实证据
5. 停用措施保留用户接受的剩余风险，不由风险等级重新启用

产出：

- 验证结果

### 3.4.1 任务中发现新问题

适用于 Mango 开发者、Mango 维护者和业务开发者在开发、联调、回归测试、验收或发布验证中发现的新问题。

必须先判断问题归属：

1. 如果问题由本次任务改动引入，必须纳入当前任务直接修复；新事实出现后重新推荐适用的 M09-M16，并由用户确认是否补充回归验证。
2. 如果用户在当前非 `main` 工作区明确要求解决该问题，该指令即确认问题进入当前范围，必须原地修复并重新确认适用保障措施，不得新建 worktree。
3. 如果问题不是本次任务引入、由 Agent 自行发现且用户未要求当前解决，必须登记 Issue，记录复现路径、影响范围、证据和建议优先级，然后回到当前任务主线。
4. 如果无法判断用户是要求当前解决还是只要求记录，必须先询问；禁止自行新建 worktree。
5. 如果无法判断问题来源，必须对比主分支、发布物料或任务前基线；来源不影响用户已经明确作出的“当前解决”或“登记 Issue”选择。

禁止：

- 把非本次任务引入的问题顺手扩展成当前任务范围。
- 因为发现历史问题而中断当前任务主线。
- 未登记 Issue 就把已确认的非本次问题留作口头记录。
- 用 Issue 逃避本次任务引入的缺陷修复。
- 用户已明确要求当前解决时另建 worktree、另起无关分支或只登记 Issue。

### 3.4.2 任务返工与验收缺陷修复

验收、Review、CI 或 PR 检查中发现的问题，必须先判断是否属于当前任务或当前 PR。

必须执行：

1. 如果问题由当前任务或当前 PR 引入，属于同一任务返工，必须回到原任务 worktree 和原任务分支修复。
2. 同一任务返工包括验收发现的 bug、Review 修改意见、CI 失败、PR 门禁失败和交付台账未完成项。
3. 修复前必须先执行 `git worktree list`，确认是否已有当前任务分支或 PR 分支对应的 worktree。
4. 原 worktree 不可用时，必须优先基于原任务分支重建 worktree，并在交付报告中说明原因。
5. 如果问题不是当前任务引入，必须登记 Issue 或 PR 评论，并等待用户确认是否作为新任务处理。

禁止：

- 同一任务返工时新建无关联 worktree。
- 同一任务返工时新建无关联修复分支。
- 将当前任务引入的缺陷拆成新任务来规避原任务验收。

### 3.5 提交

本节是用户明确授权提交、Push 或创建 PR 后的独立版本控制流程，不属于交付模式自动权限；不得因为模式和保障基线已解析就自动执行外部写操作。

必须完成：

1. 在用户确认的工作区内完成已启用验证
2. 使用任务分支时，提交前先将最新 `main` 合并到任务分支，并处理冲突
3. 合并 `main` 后重新执行已启用且受影响的验证
4. 提交代码
5. 用户授权 Push 时 Push 任务分支
6. 用户授权创建 PR 时使用 `gh` 创建 PR
7. 说明改动范围
8. 说明验证结果
9. 说明遗留问题
10. 用户已启用结构化交付记录时，说明总项、完成项和例外项

PR 要求：

- 禁止绕过 PR 直接把任务分支合并到 `main`。
- 用户确认 `M01=CREATE` 且 PR 已创建时，必须保留任务 worktree，直到 PR 已合并。
- 用户确认 `M01=CREATE` 且 PR 合并后，必须使用开发环境规范中的 worktree 删除脚本清理任务 worktree。

产出：

- 用户已授权并实际完成的 Commit、Push 或 PR

## 4. 文档放置规则

### 4.1 `mango-pmo`

只放：

- 规范
- 流程
- Agent 定义
- Skill 约束

### 4.2 `mango-docs`

只放：

- 架构设计
- Sprint 计划
- 交付记录
- 历史设计

禁止：

- 在 `mango-docs` 新增规范文件
- 在 `mango-docs` 维护规则入口
- 在 `mango-docs` 写“必须遵守”的长期规则

## 5. 角色分工

### 5.1 使用者定义

| 使用者 | 定义 | 主要边界 |
|--------|------|----------|
| Mango 维护者 | 维护 Mango 主仓、发布物料、PMO 规范、CLI、starter、框架能力和公共模块的人或 Agent | 可以修改 Mango 框架、模板、规范和发布流程；必须保证发布物料彼此兼容 |
| Mango 开发者 | 在 Mango 主仓内开发框架能力、平台模块、公共组件、CLI 和 starter 的人或 Agent | 面向可复用能力开发；不得把单一业务项目逻辑写入 Mango 通用模块 |
| 业务开发者 | 在企业业务项目内基于 Mango 发布物料开发业务模块的人或 Agent | 依赖 Mango CLI、starter、前后端包和业务 PMO 基线开发；不得直接修改 Mango 主仓来交付单一业务需求 |

Mango 维护者和 Mango 开发者面向框架通用性负责；业务开发者面向企业业务交付负责。

### 5.2 Agent 角色

| 角色 | 负责 |
|------|------|
| PM Agent | 需求说明、范围、验收标准 |
| Tech Lead Agent | 设计、模块边界、接口、任务拆分 |
| Dev Agent | 开发、测试、提交 |
| QA Agent | 测试范围、执行结果 |
| PMO Agent | 规范、流程、资产治理 |

## 6. 执行原则

- 规则优先于习惯
- 当前生效规则优先于历史代码、历史设计、旧提交和旧测试中的写法；发现冲突时按当前规则实施，并记录需要另行治理的存量问题
- 当前代码 baseline 是新增代码的首选结构与实现来源；历史项目代码不得覆盖 baseline 中已经明确的标准写法
- 新规则只写一次，只放 `mango-pmo`
- 新代码遵守新规则
- 老代码按模块渐进重构，但不得以“历史代码一直如此”作为新增或复制违规的依据
- 设计文档不作为规范源

## 7. 禁止事项

- 没有范围和验收标准就直接开发
- 没有交付契约和设计说明就直接开发
- 在设计文档里定义长期规则
- 同一规则在多个目录维护
- 明知已有规范仍写第二份
