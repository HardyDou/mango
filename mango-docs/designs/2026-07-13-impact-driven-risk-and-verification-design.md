# 基于影响范围的风险分级与低成本验证设计

## 1. 背景

当前 `L0-L3` 表格把缺陷、API、并发、发布等变更类型直接映射为风险等级，并把等级映射成固定测试套餐。结果是：

- 局部按钮位置或文字调整可能被放大为完整 BRD、SRS、TDD、Plan 和全套后端检查。
- 同一种需求采用不同解决方案时，无法体现模块、契约、数据和回滚范围的差异。
- 后端高风险变更可能被机械要求 UI/E2E，即使 UI 不能增加有效证明。
- `pmo-doc-check` 对所有 PR 执行完整 Java、CLI、starter 和 PMO 包检查，低风险前端或文档改动成本过高。

本次调整不改变 `L0-L3` 名称，改正等级的计算输入和验证选择方式。

## 2. 目标与边界

目标：

1. 需求影响和解决方案风险共同决定最终等级。
2. 风险等级依据实际影响、失败后果和恢复难度，不依据文件数、代码行数或变更关键词。
3. 每个验收结果选择能够充分证明效果的最低成本验证。
4. 前端局部视觉调整不进入完整产品文档链，也不触发无关 Java、CLI 或 starter 检查。
5. 结构计算、Skill 路由和 CI 范围具备正例、反例和回归测试。

本次不处理：

- 不重写 Java 架构债务检查器。
- 不把历史产品文档批量迁移到新格式。
- 不把业务优先级 `P0-P3` 与交付风险 `L0-L3` 合并。
- 不用代码覆盖率或测试数量代替验收结果证明。

本治理变更影响所有 Mango 与业务项目的 PMO 路由，需求影响为 `L3`；解决方案同时修改规则、Skill、Checker、CI 和发布投影，方案风险为 `L3`；最终等级为 `L3`。

## 3. 方案比较

### 3.1 方案 A：继续使用变更关键词直接定级

实现最少，但 API、缺陷、并发、发布会被整体升档，无法区分真实影响，继续制造无效流程。本方案不采用。

### 3.2 方案 B：需求影响定级，按等级固定执行测试套餐

比当前模型准确，但仍会出现 `L3 = 静态 + 单元 + API + UI` 的机械叠加。无 UI 的后端任务仍承担无效成本。本方案不采用。

### 3.3 方案 C：需求影响与解决方案风险取高，逐验收项选择最低成本充分验证

该方案同时解决定级准确性和执行成本问题，并允许 CI 根据实际改动路径跳过无关门禁。本次采用该方案。

## 4. 风险模型

### 4.1 两阶段输入

需求影响评估关注：

- 影响的用户、租户、业务流程和消费者范围。
- 失败后对业务、数据、安全、资金、合规和可用性的后果。
- 是否改变公开业务承诺或兼容边界。

解决方案风险评估关注：

- 涉及的模块、服务、公共契约和发布物料。
- 数据、权限、租户、事务、并发、迁移和外部依赖。
- 技术不确定性、可测试性、可观测性、灰度和回滚难度。

最终计算：

```text
finalRiskLevel = max(requirementImpactLevel, solutionRiskLevel)
```

简单实现不能降低需求失败后果形成的等级；低影响需求也不能掩盖高风险解决方案。

### 4.2 等级含义

| 等级 | 影响含义 | 典型恢复特征 |
|---|---|---|
| `L0` | 不改变业务行为、交互语义、契约或数据；包含局部文字、位置、格式和非行为样式 | 无运行态恢复或只需恢复静态文件 |
| `L1` | 单模块或私有实现的局部影响；无公共契约、持久化、安全和主流程变化 | 可直接回滚，影响对象有限 |
| `L2` | 有界业务范围、多个内部模块或有限消费者；兼容性和数据变化可控制 | 可协调回滚或修复，影响可隔离 |
| `L3` | 主流程、跨服务、平台级消费者或严重后果；包括数据损失、租户越界、安全、资金、破坏性契约和难回滚变化 | 需要多方恢复、数据补偿或不可逆 |

缺陷、API、并发、发布只是评估事实，不直接等于某个等级。

## 5. 生命周期路由

1. 任务入口先记录需求影响和已知的解决方案轮廓，形成初步等级。
2. `L0/L1` 使用轻量路径：范围、验收结果、两阶段评估和定向验证，不生成四阶段空文档。
3. `L2/L3` 使用 BRD -> SRS -> TDD -> Plan：BRD 只拥有业务影响，SRS 补充系统影响，TDD 评估解决方案并锁定最终等级，Plan 使用最终等级安排验证。
4. 解决方案使等级从 `L0/L1` 升到 `L2/L3` 时，开发前回到完整生命周期；不能继续沿用轻量路径。
5. 实际 diff 超出设计范围时重新评估，只能在新证据和重新评审后调整等级。
6. 现有文档继续使用 `riskLevel` 和 `riskAssessmentEvidence`，避免历史文档格式迁移。BRD/SRS 的 `riskLevel` 记录需求或系统影响，TDD/Plan 的 `riskLevel` 记录最终等级；生命周期 Checker 接受等级随阶段上调，拒绝无证据降级，并要求 TDD、Plan 与入口最终等级一致。
7. `riskAssessmentEvidence` 在需求阶段引用需求影响事实，在技术设计和实施计划阶段同时引用需求影响、解决方案风险及取高结果。

## 6. 验证选择

正式执行类型收敛为四类：

| 类型 | 能够证明的内容 | 成本顺序 |
|---|---|---|
| `STATIC` | 文档、结构、依赖、命名、配置、类型和生成物一致性 | 1 |
| `UNIT` | 算法、转换、状态规则、边界和异常决策 | 2 |
| `API` | 接口契约、权限、租户、事务、数据库和服务协作 | 3 |
| `UI` | 页面交互、布局和用户可见的前后端结果 | 4 |

选择逻辑：

1. 为每个验收项定义可观察结果。
2. 从低成本到高成本选择第一个能够真实执行目标链路并证明结果的类型。
3. 边界分支优先下沉到低层测试，最高层只保留无法由低层证明的关键结果。
4. 不重复在四个层级验证同一个断言。
5. 风险等级增加覆盖范围、异常场景和环境真实性，不自动增加 UI 测试。
6. Mock 不能替代本次验收需要证明的实现、权限、租户、事务或数据链路。

示例：

| 场景 | 需求影响 | 方案风险 | 最终等级 | 充分验证 |
|---|---|---|---|---|
| 同一工具栏内移动按钮位置，不改变动作和权限 | `L0` | `L0` | `L0` | 静态样式检查 + 定向 UI 截图；无 BRD/SRS/TDD/Plan、单元和 API |
| 修改纯函数中的金额舍入规则 | `L1` | `L1` | `L1` | 静态检查 + 单元边界测试 |
| 增加向后兼容的查询字段并读取数据库 | `L1` | `L2` | `L2` | API/集成测试；无页面消费时不做 UI |
| 一行租户过滤修复 | `L3` | `L1` | `L3` | 真实租户边界 API 测试；代码量不能降级 |
| 平台发布状态机改变不可变制品恢复 | `L3` | `L3` | `L3` | 静态、状态机单元和真实仓库消费验证；无 UI 时不做 UI |

## 7. 机器门禁与 Skill 调整

### 7.1 PR 风险与验证记录

PR 模板增加一个简短区段：

- `Requirement impact`：等级和事实。
- `Solution risk`：等级和事实。
- `Final risk`：两者较高值。
- `Selected verification`：`STATIC/UNIT/API/UI` 中实际选择项。
- `Why sufficient`：如何覆盖验收结果。
- `Skipped verification`：未选择类型及不适用事实。

新增 Checker 校验字段完整、等级合法、最终等级等于较高值，并拒绝空理由和模板占位。生命周期 Checker 通过 `--risk` 接收最终等级并验证阶段等级 progression。语义真实性仍由路径事实、测试证据和 PR 评审共同确认。

### 7.2 Skill 与 Agent

需求 Skill 只评估需求影响，不设计技术方案。技术设计 Skill 评估解决方案风险并确定最终等级。Plan、Engineering 和 QA Skill 使用最终等级及逐验收项验证映射，不把测试类型机械累加。

Skill Eval 至少覆盖：

- 按钮位置调整走 `L0` 轻量路径。
- 同一需求采用不同方案得到不同最终等级。
- 一行租户修复不能因实现简单降级。
- 无 UI 的 `L3` 后端任务不要求 UI。
- 低成本测试无法证明事务或租户效果时升级到 API。

### 7.3 CI 影响范围

`pmo-doc-check` 保留稳定 check-run，但在 job 内根据 Git 路径分类执行：

- 通用轻量门禁始终执行：风险记录、PR 结构、能力文档影响和治理入口检查。
- PMO 规则、合同、Skill、模板或包变化时执行 PMO 测试、Eval、包构建和投影检查。
- Java、POM、Java 架构规则或后端模板变化时执行 Java 架构和债务门禁。
- CLI、starter、PMO 投影或发布锁变化时执行 CLI/starter 消费检查。
- README、能力地图或公开源码事实变化时执行相应 README/能力文档检查。

纯前端局部布局变化不会执行 Java Reactor、Java 债务预算、CLI 和 starter 生成验证。后端 Java、POM、Java 架构规则或基线发生变化时仍执行完整架构清点；正式发布和定时治理继续执行全量兜底。

## 8. 兼容与发布

- 保留 `L0-L3`、`riskLevel` 和现有文档类型，历史文档不批量迁移。
- 新语义由 canonical rule、PR 模板、Checker、Skill 和 Eval 同步发布。
- starter baseline 和 `@mango/pmo` 包由规范源机械同步。
- 该变化影响业务项目的 PMO 工作方式，采用新的 PMO 次版本发布，并在 README、CHANGELOG 和升级说明中记录。

## 9. 验收

1. 按钮位置正例被判定为 `L0`，仅选择定向静态/UI 证明，Skill 不创建四阶段文档。
2. 需求影响与方案风险不一致时，Checker 只接受两者较高值。
3. 无 UI 的后端 `L3` 正例不选择 UI，仍能通过充分性评估。
4. 用单元测试冒充权限、租户、事务或数据库证明的反例失败。
5. 纯前端局部变更的 `pmo-doc-check` 不启动 Java、CLI 和 starter 重门禁。
6. PMO、Java 架构和发布物料变更仍命中各自完整门禁。
7. PMO 包构建、starter 投影和 Skill Eval 无漂移。

## 10. 回滚

如果影响分类漏跑必需门禁，先把对应分类恢复为全量执行，再修正分类器和反例。规则、Checker、Skill、模板和投影作为同一批次回滚，避免仅回滚其中一层形成语义漂移。
