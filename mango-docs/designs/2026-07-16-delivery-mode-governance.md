# SIMPLE、STANDARD、FULL 交付模式治理设计

## 背景

现有流程把 M01-M16 逐项确认作为任务入口，导致大量明确、低风险业务修改在开工前消耗过多交互；同时风险等级与流程强度完全分离，使业务开发者无法快速判断应直接实现、登记一个文件还是进入完整流程。

本设计来自 Codex 历史会话中反复出现的三类需求：大量局部修复和定向验证、部分跨页面或接口/数据协作任务、少量安全/租户/发布/治理重构。历史原文只用于本地归纳，仓库测试仅保存脱敏改写后的最小需求句。

## 已确认方案

- L0/L1 使用 SIMPLE：直接实施，无交付文档，执行最低成本充分验证。
- L2 使用 STANDARD：一个文件登记可观察要求、技术决定、实施清单和验收结果。
- L3 使用 FULL：执行适用的完整产品或专项治理流程。
- 修改受控文件时默认自动创建或复用非 main worktree。
- 只有用户明确要求并确认风险时允许 MAIN_EXCEPTION。
- M01-M16 保留为内部执行能力，不再作为每个任务的固定问卷。
- 风险等级决定流程强度，测试类型仍由真实入口和可观察结果决定。

长期规则只维护在 [交付模式与保障措施规范](../../mango-pmo/rules/11-delivery-assurance.md)，本文件不作为第二规范源。

## 兼容策略

- 保留 `delivery-assurance` contract ID 和 M01-M16 ID，降低现有 PR、Skill 和业务基线迁移成本。
- Contract 升级到 schema revision 2，新增工作区策略、风险到模式映射和三档模式元数据。
- M01 新增 `REUSE`、`MAIN_EXCEPTION`；旧 `DO_NOT_CREATE` 只作为历史基线兼容值。
- STANDARD 新增独立模板和结构检查器；现有四文档 checker 只服务 FULL 产品流程。
- starter 中的 PMO baseline 由同步脚本机械生成，不手工维护规则副本。

## 验证设计

- preflight 单元测试：main 自动 CREATE、任务 worktree 自动 REUSE、未知范围只问事实、治理文件不再直改 main、main 例外必须显式参数。
- 风险与 PR 合同测试：L0/L1、L2、L3 模式映射，工作区决策和例外风险。
- STANDARD 文件测试：完整模板通过，缺少可观察要求或验收映射失败。
- 历史需求测试：32 个脱敏用例，覆盖多数 SIMPLE、部分 STANDARD、少数 FULL、只读、main 例外和模式升级。
- 空白上下文 Skill 测试：简单任务直接路由、L2 单文件、L3 产品流程、L3 治理流程、无 UI 的 L3 不伪造 UI 测试。
- 投影测试：业务 starter PMO baseline 与规范源无漂移。

## 风险与控制

- 误把高影响的一行修改定为 SIMPLE：最终等级仍取需求影响和方案风险最大值，权限、租户、资金、数据破坏和安全事实不得降级。
- STANDARD 成为低质量大杂烩：模板要求 ID、要求、决定、实施和验收映射，检查器阻断缺失章节。
- FULL 机械生成无关文档：产品流程与治理、发布专项流程分开，禁止治理任务伪造 BRD/SRS/TDD。
- 自动 worktree 造成重复：发现同一任务已有非 main worktree 时必须 REUSE，禁止创建第二个。
