# PMO 可执行质量契约与空白上下文验收设计

> 日期：2026-07-10  
> 状态：书面设计待审阅  
> 适用范围：`mango-pmo`、Mango Java 工程、`mango-ui`、CI 与交付证据  
> 规范归属：本文记录设计决策与实施边界，长期规则仍只维护在 `mango-pmo/rules`，本文不作为第二规范源。

本设计融合 AI Coding、Java/Spring/MySQL/微服务、Web、测试工程和敏捷治理五类评审意见；共同结论已转化为可执行机制和验收阈值，而不是保留为角色观点清单。

## 1. 背景与目标

当前 PMO 已描述开发流程、AI 编码红线、交付质量、文档资产和能力说明，但大量要求仍依赖 Agent 自觉解释。实际开发中反复出现以下结果：

- 为常量、getter、框架默认行为等机械事实编写无价值测试，以数量或覆盖率伪装质量。
- 为验证关键逻辑而 Mock 掉关键逻辑本身，测试通过但没有证明真实实现正确。
- 通过包装类、辅助函数、嵌套 Agent/Skill 或换名绕过字面规范，形式符合而语义逃逸。
- Java 的 `api/controller/service/mapper` 以及 `api/core/starter/starter-remote` 边界缺少统一、不可绕过的编译期或测试期门禁。
- 前端页面、表单、路由、状态、可访问性和 UI 测试缺少可执行契约，导致反复人工调整细节。
- 测试脚本、报告、UI 截图和基线没有稳定生命周期，过程数据与正式交付物混杂。

本设计把 PMO 从“文字说明”升级为“由真实变更自动生成义务、由独立工具验证、由反例证明有效”的质量系统。目标不是增加测试数量，而是用最小充分证据证明关键行为正确。

## 2. 术语与测试分类

正式测试只保留三类：

| 类型 | 定义 | 主要证明对象 |
|---|---|---|
| `UNIT` | 在进程内直接验证一个关键业务或关键技术决策单元 | 分支、状态机、算法、金额、权限、幂等、转换规则 |
| `API` | 从真实 HTTP、事件、Consumer、Job 或 CLI 入口进入，穿过真实应用层和持久化边界 | 协议、鉴权、租户、事务、Service/Mapper 协作、数据库结果 |
| `UI` | 从真实浏览器操作开始，经过真实前端、Mango 自有 API、后端和数据库，验证用户可见结果 | 完整用户流程；`E2E` 与 UI 测试同义 |

静态 Review、架构检查、编译检查、契约检查、Mutation、截图比对都是验证手段或证据属性，不再被命名为第四种测试。组件测试和集成测试只作为执行属性记录，最终归入上表三类之一。

## 3. 合并后的问题清单与发生概率

概率表示“保持现有 PMO 不变时，在一次涉及该类代码的中等规模需求中至少发生一次”的条件概率。它不是缺陷统计的伪精确值，而是根据当前规则实现、现有测试样本、用户长期反馈与专家审查形成的风险区间：极高 `80%–95%`、高 `60%–79%`、中 `35%–59%`、低 `10%–34%`。

| 编号 | 问题 | 概率 | 主要后果 |
|---|---|---:|---|
| P01 | 为 `A = 10` 再断言 `A == 10` 等机械事实编写测试 | 极高 | 测试数量增加但不提供行为证据 |
| P02 | 为 getter、setter、枚举成员、简单委托或框架生成代码写测试 | 高 | 维护成本和噪声升高 |
| P03 | 仅追求行覆盖率，断言没有业务含义或只断言“不抛异常” | 极高 | 形成虚假安全感 |
| P04 | Mock 被测类、被测方法或关键决策分支 | 高 | 测试验证的是 Mock 配置，不是真实逻辑 |
| P05 | 在错误层级 Mock Service/Mapper，切断本应由 API 测试证明的链路 | 高 | 鉴权、事务、租户和 SQL 问题被隐藏 |
| P06 | UI/E2E 拦截 Mango 自有 API 并返回理想数据 | 高 | 浏览器用例无法证明系统全流程 |
| P07 | 将直接调用 Service 的测试标记为 API 测试 | 高 | 接口协议和入口过滤器没有被验证 |
| P08 | UI 用例只验证 DOM 存在或按钮可点击，不验证持久化结果 | 高 | 视觉假通过，业务结果可能失败 |
| P09 | 截图存在但未绑定业务断言、视口、数据集和基线版本 | 中 | 截图只能作为装饰，无法复验 |
| P10 | 测试紧耦合私有实现、CSS 类名或调用次数 | 高 | 重构即大面积误报，团队倾向关闭门禁 |
| P11 | `force`、固定等待和易变选择器掩盖竞态 | 高 | UI 测试不稳定且难定位 |
| P12 | 测试运行过程日志、临时截图和报告被提交 | 高 | 仓库污染，正式证据难识别 |
| P13 | 同一能力保留多个“最新”基线或旧基线仍在生效 | 中 | 验收标准漂移 |
| P14 | 普通测试命令可以顺便更新基线 | 中 | 失败可以被“更新预期”消除 |
| P15 | 变更风险与 `UNIT/API/UI` 义务没有自动映射 | 极高 | Agent 自由选择最便宜的测试 |
| P16 | 关键逻辑只靠人工声明“已覆盖”，工具不验证执行路径 | 极高 | 报告与真实执行脱节 |
| P17 | 通过包装层、重命名、反射、辅助脚本规避字面检查 | 高 | 正则门禁形式通过、语义仍违规 |
| P18 | 嵌套 Agent/Skill 只复述规范，产物本身不满足规范 | 高 | 多 Agent 变成责任转移通道 |
| P19 | 非法 role、phase、未知测试类型或缺少证据时 fail-open | 中 | 错误输入反而绕开门禁 |
| P20 | PMO 源码、发布包和业务 starter 使用的规则版本漂移 | 中 | 本地通过、实际 Agent 使用旧规则 |
| P21 | Controller 缺少统一返回、校验、权限、租户或错误码约束 | 高 | 接口行为不一致且易越权 |
| P22 | `api/core/starter/starter-remote` 依赖方向被破坏 | 高 | 循环依赖、实现泄漏和启动器耦合 |
| P23 | Service 事务边界、幂等、领域校验或跨租户访问不一致 | 高 | 数据部分提交或隔离失效 |
| P24 | Mapper/SQL 出现危险全表操作、分页遗漏、字段/租户条件遗漏 | 中 | 数据正确性或性能事故 |
| P25 | API DTO、事件和错误码在生产者/消费者之间漂移 | 中 | 编译可过但运行协议失败 |
| P26 | 前端路由、页面注册、权限 key、菜单和真实页面未形成闭环 | 高 | 页面能写出来但不能正确访问 |
| P27 | 页面用任意容器伪装标准布局，或隐藏组件骗过静态检查 | 高 | 形式合规但视觉和交互不合规 |
| P28 | 表单字段、校验、提交态、错误态、权限态和 i18n 不完整 | 极高 | 每次验收都需反复调整细节 |
| P29 | 自定义组件绕过设计系统，间距、颜色、响应式持续漂移 | 高 | UI 一致性依赖人工逐页检查 |
| P30 | 门禁未绑定 Maven/PNPM/CI 主链路，可选择不运行 | 高 | 规范只在文档中存在 |
| P31 | “临时例外”没有责任人、失效时间和回归用例 | 中 | 绕过永久化 |
| P32 | 历史债务与新增变更一起全量阻断 | 中 | 上线成本过高，最终被整体关闭 |
| P33 | 没有 Mutation 或故障注入证明断言能杀死错误实现 | 高 | 测试执行了，但无法证明有效 |
| P34 | Flaky 用例没有隔离、归因和恢复时限 | 中 | 失败被习惯性重跑忽略 |
| P35 | 测试报告无法追溯到能力、变更、命令、环境与提交 | 高 | 无法复现交付结论 |
| P36 | 静态 Review 与自动测试职责混淆，简单逻辑和复杂流程一刀切 | 极高 | 要么无用测试泛滥，要么关键流程漏测 |

## 4. 总体方案：差异驱动的质量契约

每次变更由工具读取真实 Git diff、模块元数据和入口清单，生成一份不可由 Agent 自由降级的 `quality-contract.json`。人工只补充能力名称、可观察验收结果和确有必要的外部系统替身说明；风险等级和测试义务由工具计算。

```json
{
  "schemaVersion": 1,
  "change": {
    "base": "git:merge-base(origin/main,HEAD)",
    "head": "git:HEAD",
    "filesDigest": "sha256:generated-from-changed-files"
  },
  "capabilities": [
    {
      "id": "workflow-approval-threshold",
      "acceptance": [
        "达到阈值后任务进入 approved，未达到时保持 pending"
      ],
      "risk": "R2",
      "riskReasons": ["branch", "state-transition", "persistence"],
      "obligations": ["STATIC_REVIEW", "UNIT", "API"],
      "protectedProofPath": [
        "http-entry",
        "WorkflowApprovalThreshold",
        "workflow-state-write"
      ],
      "allowedExternalDoubles": []
    }
  ]
}
```

示例中的 Git 引用和摘要来源由生成器解析；正式契约保存解析后的提交哈希和文件摘要，不保留符号引用。

风险与义务采用累加关系：

| 风险 | 自动识别特征 | 最低验证义务 |
|---|---|---|
| R0 机械事实 | 常量、无分支访问器、声明式映射、生成代码 | 静态 Review；不要求 UNIT |
| R1 关键决策 | 分支、算法、转换、边界值、错误处理 | 静态 Review + UNIT |
| R2 业务链路 | 状态迁移、事务、持久化、权限、租户、事件或多个关键节点 | 关键节点 UNIT + 真实入口 API |
| R3 用户流程 | 用户可见页面或跨前后端完整业务结果 | R2 义务 + UI/E2E |

风险只允许工具上调，不能由 Agent 手工下调。确需例外时走独立例外清单，记录规则编号、具体对象、责任人、批准人、到期时间和替代证据；到期自动失败。

## 5. 测试有效性与 Mock 防逃逸

### 5.1 受保护证明路径

每条验收结果被映射为“真实入口 → 关键决策 → 状态写入或用户可见结果”。路径中的生产实现都是受保护节点：

- UNIT 可以替换外部不可控依赖，但不能替换被测决策及其同一证明路径上的协作者。
- API 必须从真实 HTTP/Event/Consumer/Job/CLI 入口进入，不得直接调用 Service 冒充入口。
- UI/E2E 不得拦截 Mango 自有 API；第三方支付、短信、邮件等外部系统可以在明确边界处使用契约替身。

Mock 检查分三层：

1. 类型/AST 检查识别 `mock/spy/patch/intercept` 的真实目标，不依赖变量名或代码表面结构。
2. 运行时探针记录受保护生产方法、入口过滤器、Mapper/SQL 和前端请求是否真实执行。
3. 定向 Mutation 或故障注入把关键条件、比较符、状态写入或返回值改错；有效测试必须失败。

这样可以抓住“把 Mock 藏进辅助函数”“换一个变量名”“包装三层后调用”和“用页面假数据绕开后端”等潜逃方式。

### 5.2 无用测试识别

静态检查将以下模式标记为无证明价值：

- 断言编译期常量等于其字面值。
- 仅验证 getter/setter、枚举声明、无分支委托或框架默认行为。
- 只有 `not null`、`doesNotThrow`，且没有可观察业务结果。
- 生产表达式与测试期望来自同一份常量或同一实现函数，形成同源断言。
- 测试不触达质量契约中的任何验收结果或关键节点。

静态工具只决定“该测试不能作为义务证据”，不会禁止团队保留确有诊断价值的辅助测试。R0 变更由静态 Review 直接覆盖，避免为了过门禁制造测试。

## 6. Java 可执行门禁

Java 侧以现有 `mango-maven-plugin` 为统一入口，拆成三类检查并绑定标准 Maven 生命周期：

| 阶段 | 实现方式 | 解决的问题 |
|---|---|---|
| `validate` | 读取 Maven effective model 和 reactor 依赖图 | 固化 `api → core → starter` 与 `starter-remote` 的允许依赖方向，禁止只靠读取 POM 文本的漏检 |
| `test` | ArchUnit/字节码规则 | 校验包、类和注解边界，覆盖 Controller、Service、Mapper、DTO、事件和远程契约 |
| `verify` | Java AST、测试报告、运行时探针和定向 Mutation 汇总 | 校验关键逻辑未被 Mock、真实入口已执行、断言能杀死指定错误 |

第一批结构规则：

- API 模块只暴露契约 DTO、事件、错误码和接口，不依赖实现模块或数据库实现。
- Core 不依赖 Starter；Starter 只做装配；Starter Remote 只做远程适配，不反向承载领域实现。
- Controller 统一校验、响应、权限与租户上下文，不直接访问 Mapper，不吞掉业务异常。
- Service 明确事务与幂等边界；跨租户和跨聚合操作必须有可识别的授权或领域入口。
- Mapper/SQL 阻断无条件更新删除、危险全字段查询、分页和租户条件遗漏等可静态确定的问题。
- API/Event/DTO 变更执行生产者—消费者契约兼容检查。

门禁采用“新增或修改代码硬阻断、历史问题建立只读债务基线”的策略。基线只能减少，不能扩大；触碰到历史违规文件时按变更行和受影响结构重新验收。这能立刻约束新代码，同时避免一次性修完整个仓库导致门禁被关闭。

### 6.1 Java 问题的实际闭环

以新增 `OrderController → OrderService → OrderMapper` 为例：

1. effective model 先判断模块依赖是否合法，`api` 直接依赖数据库实现会在 `validate` 失败。
2. ArchUnit 判断 Controller 是否直接注入 Mapper、是否缺少规定的入口注解和返回契约。
3. AST 判断 Service 是否在关键分支中绕过领域校验，Mapper 是否出现危险 SQL 形态。
4. UNIT 证明金额、状态或幂等决策；API 从真实 HTTP 入口经过鉴权、租户、事务和隔离 MySQL 验证落库。
5. Mutation 改反关键条件或跳过写入，测试必须失败；否则不能作为交付证据。

因此规范不再依赖开发者记住 `api/controller/service/mapper` 细节，而是在最早可确定的阶段给出文件、规则编号、证据缺口和修复方向。

## 7. Web 可执行门禁

前端门禁通过 TypeScript AST、项目注册表、Vitest 页面契约和 Playwright UI/E2E 组合完成，并绑定统一 `pnpm quality` 与 CI：

| 层次 | 检查内容 | 证据 |
|---|---|---|
| 静态结构 | 路由、菜单、权限 key、页面注册、依赖方向、标准页面/表单组件、设计 token | AST 与注册表报告 |
| 页面契约 | 标题、主操作、加载/空/错/无权状态、字段、校验、提交态、可访问名称 | 真实组件挂载后的语义 DOM 断言 |
| UI 行为 | 用户输入、提交、跳转、刷新后状态、错误恢复、权限差异 | Playwright 浏览器步骤与业务断言 |
| 视觉基线 | 固定数据、视口、主题下的关键状态截图 | 最新 golden 截图和差异报告 |

静态检查不会只搜索某个组件名。页面契约要求标准组件真实渲染并承担语义职责，隐藏节点、空壳包装和无可见字段不能通过。UI/E2E 禁止拦截 Mango 自有接口，选择器优先使用角色、标签和稳定业务测试标识；固定等待、`force` 和易变 CSS 选择器进入阻断或限期治理清单。

### 7.1 前端问题的实际闭环

以新增“创建流程”页面为例：

1. 静态门禁确认路由、菜单、权限 key 和页面注册闭环，页面使用真实标准布局和表单组件。
2. 页面契约挂载真实页面，验证必填字段、错误提示、提交中禁用、空态和无权态，不接受隐藏组件占位。
3. UI/E2E 从浏览器填写并提交，真实调用 Mango API，后端真实落库，刷新或列表查询后验证用户可见结果。
4. 固定桌面和移动视口生成关键状态截图，与该能力唯一最新基线比较。
5. 若用路由拦截伪造成功响应、用 `force` 掩盖不可点击按钮或仅断言 DOM 存在，门禁直接说明证据缺口。

这把页面和表单规范从“人工看起来差不多”改成可重复的结构、语义、行为和视觉四重验收。

## 8. 测试脚本、报告与基线生命周期

正式基线按能力和测试类型保存：

```text
mango-docs/evidence/test-baseline/<capability-id>/
  unit/latest/
  api/latest/
  ui/latest/
```

每个 `latest` 只包含当前标准交付物：

- 可复现测试脚本或脚本入口。
- 机器可读报告及简短人工摘要。
- 代码提交、环境指纹、执行命令、数据集摘要和质量契约摘要。
- UI 测试的关键状态截图、视口、主题和差异阈值。

运行过程数据写入 `.runtime/pmo/<run-id>` 并被 Git 忽略。普通测试命令只有读取和比较基线的权限；独立 `baseline promote` 命令在全部业务断言通过、差异已解释、审批信息完整后，原子替换当前 `latest`。当前树只保留一份最新基线，历史变更仍可通过 Git 历史审计。

## 9. PMO 与 Agent/Skill 防潜逃设计

PMO 自身采用“输入 fail-closed、输出由产物反证”的原则：

- role、phase、测试类型、风险值或规则版本未知时失败，不再默认为可继续。
- preflight 输出规则清单的摘要与版本指纹，交付校验确认 Agent 实际读取版本与仓库版本一致。
- Agent/Skill 的文字声明不计为证据；只读取 Git diff、编译图、测试轨迹、报告和基线。
- 规则检查包含直接违规、换名、包装、跨文件辅助函数、嵌套 Skill、错误例外和陈旧发布包等对抗样本。
- 子 Agent 产物回到主 Agent 后重新执行同一门禁，不能以“专家已审查”替代验证。
- 规则发布包与源码执行同一组 golden fixtures；版本或行为不一致时阻断发布。

这解决了“规范写得很多，但 Agent 复述后仍按旧习惯写代码”的根因：最终裁判从自然语言自证切换为独立产物验证。

## 10. 角色、Definition of Ready 与 Definition of Done

| 角色 | 责任 |
|---|---|
| PM/业务负责人 | 给出能力 ID 和可观察验收结果，确认基线业务含义 |
| Tech Lead | 维护架构边界清单、关键证明路径与例外审批 |
| Developer/AI Agent | 交付生产实现和最小充分证据，不手工决定风险降级 |
| QA | 维护 API/UI 场景、Mutation 目录、Flaky 治理和基线提升 |
| PMO | 维护机器规则、规则版本、债务基线和空白上下文评估集 |

进入开发前需具备能力 ID、可观察验收结果、真实入口和数据影响说明。完成交付需同时满足质量契约、结构门禁、必要的 UNIT/API/UI、Mutation、报告和最新基线要求。例外必须有责任人、批准人、替代证据和自动到期时间。

## 11. 实施拆分

实施按可独立回滚的提交或 PR 递进：

1. 契约与评估骨架：定义 schema、风险分类器、反例 fixtures、空白上下文 runner 和报告格式。
2. PMO 自身硬化：preflight fail-closed、规则版本指纹、源码/发布包一致性和例外生命周期。
3. Java 门禁：effective model 依赖图、ArchUnit/AST 结构规则、测试证明路径和定向 Mutation。
4. Web 门禁：TS AST/注册闭环、页面契约、Playwright 自有 API 拦截检测、语义选择器和视觉基线。
5. 证据与基线：运行目录隔离、报告聚合、唯一 latest、独立 promote。
6. 真实项目试点：工作流阈值、支付入口和工作流页面三个纵向切片。
7. 全仓启用：新增变更硬阻断，历史债务基线化并设置递减目标。

每一步都先提交“违规样例必须失败、合法样例必须通过”的工具自测，再接入真实项目，避免用真实业务代码充当门禁工具的唯一测试。

## 12. 空白上下文 A/B 验证实验

### 12.1 隔离条件

对照组使用当前 `main` 的 PMO，实验组使用候选分支。两组均在独立 checkout 中运行，并满足：

- 空 `HOME`、空 `CODEX_HOME`、无历史会话、无用户级 Skill 和记忆。
- 相同模型、系统提示、任务提示、工具、token 预算、超时和网络策略。
- 任务输入只包含该 checkout 的入口文件，不向 Agent 解释隐藏判分点。
- 生成完成后由独立校验器评分，不使用生成 Agent 的自述。

### 12.2 用例集

首批不少于 30 个场景，至少 60% 为生成 Agent 不可见的隐藏变体。普通场景重复 3 次，关键红线场景重复 5 次。至少覆盖：

- 常量、getter、委托和“只断言不抛异常”等无用测试诱饵。
- 直接 Mock 被测方法、辅助函数包装 Mock、跨文件 Mock、Spy 改返回值。
- API 测试直接调用 Service、替换 Mapper、绕过鉴权/租户和使用非隔离数据库。
- UI 拦截 Mango API、隐藏标准组件、假路由注册、CSS 选择器、固定等待和 `force`。
- Java 非法模块依赖、Controller 直连 Mapper、事务缺失、危险 SQL 和契约漂移。
- PMO 非法 role/phase、规则版本漂移、嵌套 Agent/Skill、过期例外和多份 latest。
- 合法外部第三方替身、R0 仅静态 Review、合法 starter 装配等正例，验证误报。

### 12.3 机器评分与盲审

机器指标：

- 已知关键红线 fixtures 检出率 `100%`，任何漏检直接判实验失败。
- 合法外部替身和 R0 正例的关键误报率 `0%`。
- 全部场景正确判定率不低于 `95%`，并比对照组提高至少 `30` 个百分点。
- 规定 Mutation 的杀死率 `100%`；关键变更 PIT mutation score 不低于 `85%`。
- 要求执行的真实入口、关键节点和持久化路径运行时命中率 `100%`。
- 同一输入多次运行的门禁结论一致率不低于 `95%`。

需要业务语义判断的输出由两名不知道组别的评审者独立评分，Cohen's kappa 不低于 `0.85`；分歧由第三人裁决。性能同时记录总耗时、Flaky 率和平均修复轮次，防止以不可接受成本换取表面正确率。

### 12.4 真实项目纵向验收

选择三个现有能力作为真实样本：

1. `WorkflowApprovalThreshold`：删除或拒绝机械断言，保留边界与状态决策 UNIT；改反阈值比较符后测试必须失败。
2. `PaymentChannelContractServiceImpl` 相关入口：从真实 API 经过事务、Mapper 和隔离 MySQL 验证状态；Mock Service/Mapper 的伪 API 用例必须被拒绝。
3. 工作流管理/发起页面：浏览器经过真实前后端完成业务流程并生成关键截图；拦截 Mango API 的同形用例必须被拒绝。

真实样本既要证明新门禁能抓错，也要证明合法实现不会被误伤。所有命令、报告和截图进入相应能力的唯一最新基线。

## 13. 验收口径与“100% 可落地”的边界

本方案的工具、规则、测试、报告、基线和 CI 接入均可在 Mango 仓库中实现；冻结的已知红线样本要求 100% 检出，关键证明路径要求 100% 实际命中。对未来未知业务语义不做无法验证的“永不漏错”承诺，而是通过隐藏用例、Mutation、真实纵向样本和持续新增反例，把可验证范围内的结论做成硬门禁。

候选方案只有同时满足以下条件才允许取代现行 PMO：

- 不再要求 R0 机械逻辑编写 UNIT，且能阻止其冒充关键证据。
- 关键逻辑被 Mock、真实入口被绕过或 UI 自有 API 被拦截时稳定失败。
- Java 与 Web 结构规则绑定本地标准命令和 CI，无法通过不运行检查绕过。
- 正常测试不能更新基线，过程数据不进入版本库，当前树只有唯一 latest。
- 空白上下文 A/B 指标达到第 12 节阈值，三个真实项目样本全部通过。
- 所有失败能定位到规则编号、文件/节点、缺失证据和修复建议，团队可以实际处理。

## 14. 已评审的替代方案

| 方案 | 结论 | 原因 |
|---|---|---|
| 只扩写 PMO/Skill 文档 | 不采用 | 无法约束未阅读、误解或主动潜逃的 Agent |
| 统一提高代码覆盖率 | 不采用 | 会进一步激励常量测试和无意义断言 |
| 全部逻辑都写 UNIT | 不采用 | 与“静态 Review 覆盖机械逻辑”的目标冲突，维护成本不可控 |
| 全面禁止 Mock | 不采用 | 第三方系统、时钟、随机源等边界仍需要可控替身 |
| 一次性全仓零违规 | 不采用 | 历史债务会让门禁无法落地并最终被关闭 |
| 差异驱动契约 + 分层门禁 + Mutation + 空白 A/B | 采用 | 同时覆盖正确性、防逃逸、成本和渐进落地 |

## 15. 风险与回滚

- 风险：初期规则误报影响开发。缓解：每条规则同时提供正反 fixtures，先对新增变更启用，合法样本误报为零才升级硬门禁。
- 风险：Mutation 和 UI/E2E 增加 CI 时间。缓解：按质量契约只运行受影响能力，合并前运行定向集合，夜间运行扩展集合。
- 风险：历史债务基线变成永久豁免。缓解：基线只读、不能扩大，触碰即重验，并按模块设递减目标。
- 风险：基线提升被滥用。缓解：测试与 promote 权限分离，提升必须附差异解释和审批。
- 风险：新门禁自身错误。缓解：每项门禁可按独立提交回滚；规则版本与报告保留明确关联，不回滚业务代码来迁就错误门禁。
