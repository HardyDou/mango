# 交付保障措施与人工确认设计

## 1. 背景

当前 PMO 将最终风险等级直接映射为文档数量：L2/L3 一律要求 BRD、SRS、TDD 和实施计划。该映射没有判断文档是否对当前目标提供保障，导致仓库治理等任务生成无关产品文档。

## 2. 目标

- 由 AI 基于实际任务提出保障措施建议，不再套固定任务套餐。
- 措施名称、解释、用途和触发事实使用稳定目录，任务内不得临时发明或改名。
- 使用 Agent 原生 Ask User 让用户逐项决定；用户确认结果优先于 AI 建议。
- 风险等级继续描述影响，但不再决定文档数量。
- CI 只验证用户启用的措施，不替用户增加流程。
- 发布继续由独立发布流程处理，不进入本机制。

## 3. 决策

新增 `mango-design-delivery-assurance` Skill 和 `delivery-assurance` v1 合同。合同固定 16 项措施，覆盖工作区、数据库重建、四类产品文档、治理/能力说明、验证、专家复核、外部状态回读和人工验收。

当某项措施的触发事实出现时，AI 必须说明推荐、价值、成本和跳过影响，并调用原生 Ask User。用户可启用或停用；数据库只允许“重建/不重建”，worktree 只允许“新建/不新建”。未触发的措施不进入问卷。

Ask User 每批最多三项。用户确认后形成任务执行基线；只有目标、范围或措施组合发生实质变化时，才重新询问受影响项。

## 4. 生命周期调整

- 删除 `requiredStagesByRisk`，风险等级不再选择文档。
- 生命周期检查器改为接收用户确认的 `--required-stages`；只要求所选阶段。
- 已选择的相邻文档继续校验摘要、追踪、风险单调和审批证据。
- 未被选择的文档不因 L2/L3 自动失败。
- SRS、TDD 和实施计划允许独立启用；没有前置文档时显式引用人工确认的保障基线，不反向补齐文档链。
- 历史四阶段文档和现有单文档 checker 继续可用。

## 5. CI 与投影

- PR 合同先校验人工确认基线、合法措施值、已启用措施证据和已停用措施剩余风险。
- PMO CI 从确认基线读取 M08-M16；文件路径只裁剪受影响范围，不再决定启用哪些文档或测试。
- PR body 修改会重新触发 PMO CI，确保人工调整措施后执行集同步变化。
- `mango-business-starter` 基线和 `@mango/pmo` 可分发包由规范源机械同步；同步不等于发布。

## 6. 边界

- 本机制不包含发布、版本、制品、发布仓库回查和发布恢复。
- 数据库策略只有重建与不重建，不引入第三种选择。
- 新增措施必须通过独立 PMO 治理变更升级目录版本；Agent 不得在任务中增加 `M17`。
- 系统、平台和工具不可绕过的安全限制不由用户选择覆盖。

## 7. 验证

- 合同测试固定 16 项 ID、名称、选择值和发布边界。
- Skill eval 覆盖 single-owner、业务规则、API、UI、数据库和发布非触发场景。
- 生命周期测试证明 L3 可只选择治理措施而不生成四文档，同时证明用户选择文档后仍执行对应 checker。
- 100 条推荐用例覆盖 single、组合、边界、非触发和发布排除；测试输入不携带期望答案，分片交给空白上下文 Agent 独立判断。
- 最终盲测 100/100 精确匹配，且包含 17 个不触发、10 个发布排除和 34 个触发但不需要 worktree 的反固定套餐用例。
