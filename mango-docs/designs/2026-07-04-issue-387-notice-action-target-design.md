# Issue 387 通知动作目标设计

## 背景

系统消息原先只能承载标题、正文、业务类型和业务编号。业务模块如果希望用户从消息进入处理页面，容易把前端页面地址写进消息内容或业务事件，导致前后端强耦合、权限绕过风险、重构成本高，也无法表达“先提交事件、再进入业务处理”的交互。

## 目标

- 系统消息只传业务语义，不传具体页面地址。
- 消息支持结构化目标、主题、场景、扩展数据和动作列表。
- 支持普通跳转、业务流程入口、事件提交三类行业常见交互。
- 前端按已注册目标 key 打开页面或业务流程，业务模块可以注册自定义交互入口。
- 动作提交具备幂等请求、状态回写和实时刷新能力。

## 协议模型

### 场景

`messageScene` 表示消息产生场景，例如：

- `workflow.task.assigned`
- `job.instance.failed`
- `payment.order.failed`
- `identity.user.created`
- `auth.login.locked`

### 主题

`messageSubject` 表示消息关联的业务对象：

- `subjectType`
- `subjectId`
- `subjectName`

### 目标

`messageTarget` 表示消息默认入口：

- `targetType`: `ROUTE`、`FLOW`、`EXTERNAL`
- `targetKey`: 已注册目标 key，例如 `workflow:task:detail`
- `params`: 业务参数，只保存对象 id、状态、来源等语义字段

目标 key 由前端或业务模块注册。通知中心只负责保存和分发，不理解具体页面实现。

### 动作

`messageActions` 表示消息可执行动作：

- `interactionType=ROUTE`: 打开命名目标。
- `interactionType=FLOW`: 进入自定义业务交互流程。
- `interactionType=EVENT`: 向后端提交动作事件，由后端发布领域事件并返回动作请求状态。

动作状态包含 `AVAILABLE`、`PROCESSING`、`COMPLETED`、`FAILED`、`EXPIRED`。事件动作按消息、动作、用户维度幂等，避免重复提交。

## 自定义交互流程

涉及业务自定义表单、审批处理、异常处理等场景时，不把具体页面地址写入消息。业务模块提供稳定 target key：

- 工作流审批详情：`workflow:task:detail`
- 支付异常处理：`payment.exception.resolve`
- 退款异常处理：`payment.refund-exception.resolve`

通知前端只把 target key 和 params 交给路由/流程注册表。目标不存在或无权限时，前端提示“目标未注册或当前无权访问”。

## 模块案例

| 模块 | 场景 | 目标/动作 |
| --- | --- | --- |
| 通知 | 系统消息列表、消息中心、实时消息 | 展示动作按钮，事件动作提交后变更状态，命名目标跳转 |
| 任务 | 任务执行失败告警 | 打开任务实例，携带任务实例和任务定义语义参数 |
| 工作流 | 待办、驳回、结束、完成 | 打开待办详情、已办、我发起等工作流目标 |
| 支付 | 支付失败、退款失败 | 打开订单或异常处理流程 |
| 身份 | 用户创建、密码重置、外部账号绑定变化 | 打开个人资料或密码设置目标 |
| 认证 | 登录成功、登录锁定 | 打开个人资料或用户安全处理目标 |

## 兼容性

- 旧消息没有结构化目标和动作时，仍按普通消息展示。
- 发送接口新增字段均为可选字段。
- 数据库新增字段和动作表不改变原消息主键、已读、删除、分页逻辑。
- 前端保留公告、接收设置等现有入口，但改为命名目标打开。

## 验证

- 通知后端集成测试覆盖消息发送、动作持久化、动作提交、动作完成、失效动作拦截。
- 任务、工作流、支付、身份、认证模块测试覆盖结构化消息事件。
- 管理端 E2E 覆盖消息中心动作按钮、事件提交、动作禁用、命名目标跳转、详情、已读、删除。
