# Mango 文本资产全量重写计划

## 结论

本任务不是继续给少数 README 增加摘要，而是先升级文档规范和模板，再按统一职责重写当前文本资产。历史交付记录和验收证据保留原文，只补索引或迁移说明，不改写历史事实。

当前仓库统计：

- Markdown：约 2,216 个；
- Markdown、MDX、文本配置和结构化文本：约 4,548 个；
- GitHub Pages 白名单文档：165 个。

因此采用同一任务下的分批重写，不用机器批量替换正文，不把静态结构通过当作内容质量通过。

## 章节职责

| 章节 | 文档职责 | 主要读者 | 禁止承载 |
|---|---|---|---|
| 开始 | Mango 定位、阅读路线、版本和入口选择 | 所有人 | API 细节、历史日志 |
| 示例场景 | 按真实任务提供前置条件、步骤、结果和失败处理 | 业务开发者 | 长期规范正文 |
| 产品文档输出 | BRD/SRS/TDD/Plan 的选择和阶段关系 | PM、Tech Lead、Dev | 平台能力说明 |
| 基础能力 | 基础设施和公共装配的能力边界与接入入口 | 开发者 | 业务模块交付历史 |
| 平台能力 | 后端模块、前端包、责任边界和最小接入路径 | 业务开发者 | Issue/Release 时间线 |
| 架构设计 | 稳定分层、依赖边界、关键决策和迁移约束 | 架构师、Tech Lead | 操作步骤和 API 参考 |
| PMO 规范与模板 | 研发流程、角色、模板、门禁和工具入口 | Agent、PM、Dev、QA | 业务能力事实 |

## 文档类型职责

| 文档类型 | 先回答的问题 | 内容边界 |
|---|---|---|
| 模块 README | 这个能力是什么，怎么接入，失败看哪里 | 当前源码、配置、API、权限、租户和验证入口 |
| 场景指南 | 我要完成这个任务时按什么顺序操作 | 可执行步骤、前置条件、正常流和失败流 |
| 能力地图 | 我应该选择哪个能力和模块 | 索引、场景映射、责任模块和链接 |
| 规则 | 长期必须遵守什么 | 唯一规范、触发条件、禁止项和机器检查 |
| 模板 | 这个阶段要填写什么 | 阶段输入、最小字段、交付物、追踪和审批 |
| 设计文档 | 为什么这样设计 | 事实、方案、取舍、风险和决策证据 |
| 计划文档 | 谁按什么顺序交付并验证 | 任务、依赖、命令、证据和失败处理 |
| 交付/验收记录 | 本次交付实际发生了什么 | 不可变事实、命令输出、证据和剩余风险 |

## 模板升级顺序

```text
模板选择页 -> BRD -> SRS -> TDD -> Implementation Plan -> 验收/交付记录
```

- 旧 PRD 只保留迁移入口，默认导航不再提供旧模板。
- 每个模板先给适用场景、不适用场景、上游输入、输出和最小填写示例。
- 大型追踪矩阵、审批字段和机器门禁放在模板后半段，不阻断第一次阅读。
- SIMPLE、STANDARD、FULL 继续保留，不为低风险任务生成不适用的产品文档。

## 模板实用性合同

每个字段和章节都要有明确用途：

| 检查问题 | 通过条件 |
|---|---|
| 这个字段回答什么问题？ | 能用一句具体话说明，不接受“补充信息”这类空定义。 |
| 谁填写、依据什么填写？ | 有责任角色和事实来源；不能要求作者猜测。 |
| 填完后谁会使用？ | 能被下一阶段、实现、测试、验收或审批直接消费。 |
| 不适用时怎么办？ | 删除、标记 `NONE` 并说明原因，不能留下空占位表。 |
| 如何判断填写正确？ | 有示例、checker、追踪关系或可执行验证。 |

模板不再追求字段数量。无下游用途的字段删除；重复表达同一事实的章节合并；机器合同保留，但放在文档元数据和阶段判定区，不占用首次阅读入口。

四类核心模板的实用章节：

- **BRD**：问题、目标、范围、参与者、业务对象/状态、场景、规则、业务验收和待确认项。
- **SRS**：系统边界、参与者、功能、页面/动作、数据、外部交互、非功能、失败反馈和系统验收。
- **TDD**：设计输入与决定、模块边界、流程与一致性、API、数据、安全、错误与观测、前端映射、测试和回退。
- **Plan**：交付物、任务、依赖、里程碑、验证命令、数据步骤、风险、交付台账和移交。

任何章节如果不能改变下一步行动、验证结果或责任判断，就不进入正式模板。

## 重写顺序

1. **规范与模板**：先固定章节职责、文档类型合同和模板选择入口。
2. **公开入口**：重写站点首页、`mango-docs/README.md`、能力地图和场景目录。
3. **场景指南**：每个场景按“问题、前置、最小路径、成功、失败、源码入口”重写。
4. **模块 README**：按能力事实重写后端、前端和组件 README；不改源码语义。
5. **架构与 PMO**：重写当前设计说明、规则说明和工具入口；历史决策保持可追溯。
6. **全量验证**：链接、章节职责、源码事实、模板合同、文档构建和人工理解评测。

## 保留边界

- 历史 Issue、发布说明、交付台账和验收证据是审计事实，不直接润色改写。
- 需要面向当前读者的内容，从历史记录抽取当前结论，写入能力地图或场景指南，并保留历史链接。
- 生成的 HTML、VitePress dist、package 产物和机器快照不作为人工重写目标。
- 规则正文只维护在 `mango-pmo/rules/**`，其它文档只链接，不复制长期规则。

## 验收标准

- 每个公开章节有唯一职责说明和明确首读入口；
- 新需求入口不再出现可误用的 PRD 模板；
- 能力地图不包含 Issue/Release 时间线正文；
- 每个当前 README 能回答场景、责任、最小路径、边界、源码入口和失败入口；
- 每类模板能说明适用阶段、上游输入、输出、最小填写方式和下一步；
- 历史证据的原始内容、路径和摘要保持可追溯；
- 真实读者评测达到 `5/6`，首次源码入口命中率达到 `80%`，未解释术语不超过 3 个；
- 静态检查通过不替代真实读者评测和人工同行评审。

## 三轮独立评审

| 轮次 | 视角 | 关注点 | 结论 |
|---|---|---|---|
| 1 | 业务开发 | 能否从任务找到正确能力、模板和源码入口 | 章节按任务和能力组织，避免仓库目录式导航 |
| 2 | 文档治理 | 是否重复规则、混淆当前事实和历史事实 | 规则集中，历史记录保留，当前入口单独重写 |
| 3 | QA/交付 | 是否能验证内容理解和链接事实 | 增加逐章检查、源码引用检查和真实读者门禁 |

**同行评审状态：** 当前为 Agent 内部方案整理，尚未完成真实人工同行评审；在同行评审和人工理解评测完成前，不标记正式投产批准。
