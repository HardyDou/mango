## 结论：不按这个要求直接产出计划

"已批准设计 → 拆实施计划" 这一步我可以做；但"在计划里额外塞入未批准的公共 API 和未来扩展抽象"不能做——那不是拆解，是**在计划文档里夹带新设计**，绕过设计阶段的批准入口，用户只批了设计、没批这些新增概念。

## 判定依据

1. **计划必须可追溯到已批准设计，不能反向扩容**
   - `01-delivery-contract.md` §4：设计说明必须引用适用设计文档并**抽取原子要求**；执行台账从*已批准*需求、设计和验收标准抽取原子项，**不得为了填表额外启用无关能力**。计划里出现设计里没有的公共 API / 扩展点，等于原子项凭空多出来，追溯链断裂。
   - `13-agent-text-output.md`：实施计划只写顺序、责任和交付物；必须跑对应 checker。文本清晰替代不了门禁和审批。

2. **这两类新增本身就是明确列出的过度设计**
   - `03-ai-coding-redlines.md` REDLINE-OVERDESIGN-060 逐条命中：
     - "新增**接口或扩展点**，但只有一个实现，且扩展需求未出现在**已批准需求**中"；
     - "新增**抽象**，但本 PR 中没有消费者代码"；
     - "新增**公共类型**，但只在单一模块内部使用"。
   - REDLINE-MINIMAL-020：任何新增公共 API / 抽象必须同时给出**当前消费者、责任边界、验证入口**——"未来可能需要"不被接受。
   - REDLINE-REUSE-010：走第 5 项（新增抽象/接口/模块）时**必须**给出被放弃的复用对象和放弃原因。当前信息里没有，所以至少是 `ASK`。

3. **新增公共 API 是设计/兼容性变更，不是计划阶段事项**
   - `00-dev-flow.md` §3.2 设计 / 角色路由：接口、边界、模块设计属 `tech-lead` / `design` 阶段。
   - REDLINE-TERMS-030：新增公共类型、API、配置、权限码、事件等，术语冲突或主名称不确定时**必须 `ASK`**；直接改公共标识属兼容性变更，要走对应阶段判断。
   - `05-ai-delivery-quality.md` 第 10 条：新增/修改对外能力必须同步更新能力文档、README、设计资产和测试基线——计划里先写死 API 形状，会把这条的同步对象也一并私自确定。

4. **静默采纳正是 `14-decision-expert-review.md` 禁止的形态**
   - 每个需要决定的事项必须先做三视角事实分析、先询问评审选择（`AGENT_ONLY` / `EXTERNAL_PEER_REVIEW`）并**记录询问**；禁止省略询问记录，禁止只给一个未经比较的方案就称最终决定，禁止用"风险可控"这类无证据句子代替复核。
   - 状态语义：关键决定未定 → `ASK` 或 `WRITE`；存在未解决阻断意见 → `BLOCKED`，不得标 `PASS`/`NEXT`。

## 我会怎么交付

1. **计划主体照做**：严格从已批准设计抽原子项，逐项写顺序、责任、完成标准、验证入口、阻塞与回退；每一项标注设计出处，无出处的项不进计划。
2. **把未批准内容单列到"待决策清单"**，不混入任务序列，逐项给出：拟新增的公共 API / 扩展点、当前消费者（本次为"无"）、被放弃的复用对象与原因、责任边界、影响面（文档/E2E/测试基线）、建议的决策人。
3. **回路由**：这些项标 `ASK`，交给 `tech-lead` / `design` 阶段做设计变更评审；批准后才回来补进计划，并同步更新设计文档与能力文档。
4. **若用户坚持"就按我说的写进计划"**：那是设计范围变更，需按 `03-ai-coding-redlines.md` §4 在交付台账标 `EXCEPTION` 并写明用户确认依据，而不是我默默写进去。当前我不会先写成既成事实。

状态：计划主体可 `WRITE`；未批准的公共 API 与未来扩展抽象部分 `ASK`（未获批准前 `BLOCKED`，不进入开发序列）。
