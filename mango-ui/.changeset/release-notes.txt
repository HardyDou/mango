## Pull Requests

- Added: [PR #1244](https://github.com/HardyDou/mango/pull/1244) Added a reuse scope to node-affinity auto assignment: `nodeAffinityScope` selects `PROCESS_INSTANCE` (default, 1.7.0 behavior), `BUSINESS_KEY` or `AFFINITY_KEY`, and the runtime resolves handlers from the nearest scope outwards while requiring the handler to remain in the current candidate set. Packages: the complete Maven/docs `1.8.0` tuple including `io.mango.platform.workflow:mango-workflow-{api,core,starter,starter-remote}:1.8.0`, `io.mango:mango-docs-bundle:1.8.0`, and `@mango/workflow@1.2.0`. Business Adaptation: apply migration `V4`, upgrade the tuple and regenerate the designer; only nodes that opt into `BUSINESS_KEY` or `AFFINITY_KEY` change behavior.

## Added

- `WorkflowNodeAffinityScope` with `PROCESS_INSTANCE`, `BUSINESS_KEY` and `AFFINITY_KEY`, plus `WorkflowApprovalNodeConfig.nodeAffinityScope` and the matching designer control shown only for `AUTO + NODE_AFFINITY`.
- Optional `affinityKey` on `CreateWorkflowBusinessApplyCommand` and `StartBusinessWorkflowCommand`, returned on `WorkflowBusinessApplyVO`, trimmed on create and not updatable afterwards.
- `AUTO_ASSIGN` audit fields `nodeAffinityScope` and `nodeAffinityHit` so the resolved layer (`PROCESS_INSTANCE`, `BUSINESS_KEY`, `AFFINITY_KEY` or `FALLBACK`) is traceable.
- Flyway `V4` adds `workflow_business_apply.affinity_key` and the `(tenant_id, business_type, affinity_key, process_instance_id)` index conditionally, so databases that already patched the column stay upgradable.

## Fixed

- Re-submitting a changed project no longer loses the previous handler: the new process instance can reuse a handler recorded under the same business key or affinity key instead of returning the task to the claim pool.
- Cross-instance reuse never assigns an ineligible user: a historical handler that is no longer in the current candidate set is skipped and lookup continues to the next layer.
- Each lookup layer is bounded to the 200 most recent records and falls back according to `nodeAffinityFallback` when nothing matches.

## Business Impact

- Businesses that re-submit the same project or contract can keep the previous approver for a node instead of forcing the applicant or an administrator to reassign manually.
- The reuse boundary is explicit per node: instance-only remains the default, business-key reuse follows the same business order number, and affinity-key reuse follows the stable aggregation key the business passes at application creation.
- Cross-tenant leakage is not possible: every lookup and join is filtered by the current tenant, and the new index keeps the lookup off a full table scan.
- Approval trails gain `nodeAffinityScope` and `nodeAffinityHit`, so an auto-assigned handler can be explained during review.
- A migration is introduced: `workflow_business_apply` gains `affinity_key` and one index; historical rows are not backfilled, so pre-existing applications keep no affinity key.

## Upgrade Estimate

- Audience: Mango backend consumers using workflow auto assignment, and frontend consumers of the workflow and admin npm closure.
- Engineering Effort: 1-2 engineer-days per consumer to upgrade the tuple, apply `V4`, decide which nodes need business-key or affinity-key reuse and pass `affinityKey` where required; 0.5 engineer-day for the npm closure upgrade and designer regeneration.
- Execution Window: 2-4 hours per consumer including database backup, migration, restart, permission verification and a re-submission regression.
- Service Downtime: one controlled backend restart window; the migration adds a nullable column and an index, so no table rewrite of business data is required.
- Rollback Effort: 1 engineer-day per consumer to restore the complete Maven `1.7.0` tuple and the previously verified npm closure, including removing the added column and index if the schema must return to `V3`.
- Assumptions: consumers have a recoverable database backup, at least one business flow with re-submission, at least two candidate handlers, and permission to change process definitions.

## Upgrade Notes

1. Upgrade the complete Mango Maven/docs tuple from `1.7.0` to `1.8.0`; do not update only one starter or module.
2. Apply Flyway `V4` (`affinity_key` column and index). It is conditional and idempotent, and does not backfill historical applications.
3. Set `nodeAffinityScope` only on nodes that should reuse handlers across submissions; leave it unset to keep the instance-only behavior.
4. Pass a stable `affinityKey` at application creation when `AFFINITY_KEY` reuse is required; the value must survive re-submission, and it cannot be changed afterwards.
5. Use `BUSINESS_KEY` reuse when the business order number itself identifies the aggregate and no extra key is available.
6. Check the `AUTO_ASSIGN` audit for `nodeAffinityHit` when a handler looks unexpected; `FALLBACK` means no eligible history was found.
7. Regenerate the designer with `@mango/cli@1.4.7` so the reuse-scope control and defaults are available.
8. Upgrade the npm closure to `@mango/workflow@1.2.0`, `@mango/admin-shell@1.1.7`, `@mango/workflow-business-example@1.0.69` and `@mango/admin@2.0.9`, then rebuild the admin bundle.

## Rollback

- Restore consumers to the complete Maven/docs `1.7.0` tuple and the previously verified npm closure; immutable coordinates are never overwritten.
- Rolling back the configuration restores instance-only affinity without touching data; nodes already assigned keep their handler.
- Rolling back the schema requires removing the index and `affinity_key` column only after confirming no consumer reads them; historical rows were never backfilled, so no data repair is involved.
- Tasks already assigned through cross-instance reuse stay assigned; reassign them with the standard transfer operation instead of editing workflow tables.
- If registry visibility is ambiguous, stop and resume read-only status/repair using the same prepared candidate; never create a second candidate for the same coordinates.
