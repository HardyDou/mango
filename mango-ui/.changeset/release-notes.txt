Business Adaptation: business repositories upgrade PMO through CLI, remove the PMO-managed project copy of `mango-release`, and use `mango-submit-pr` for PR submission; business PR and application release processes do not use the Mango component release flow.

## Fixed

- Remove the `@mango/admin-pages -> @mango/system -> @mango/file -> @mango/admin-pages` cycle by moving the neutral page, feature and Notice provider contracts into FE1 `@mango/admin-extension` while preserving same-instance compatibility re-exports from Admin Pages.
- Keep `@mango/cms/admin-pages` external in the Admin aggregate so CMS registrars and Admin Shell resolve the same page registry; all nine CMS management routes can be registered in a clean full consumer.
- Enable the domain-event Outbox in newly generated full projects so the default system-event menu and `/api/system/events` controller configuration agree.
- Register `/notice/setting` as a hidden Notice route, include a real favicon in the full template, normalize backend numeric strings before passing them to Element Plus, and migrate affected radio/pagination/tag props away from deprecated or invalid values.
- Narrow `notice.message.received` to identifiers and status. Message bodies remain in Notice storage, attachments remain in File storage, and broadcast payloads no longer carry body, address or attachment identifier lists.
- Preserve Maven `sourceVersion=1.0.36` when the in-progress mixed plan is recalculated, and probe `io.mango:mango-bom:1.0.36` through both Maven registry roles so a non-browsable hosted root cannot cause a false preflight failure.
- Bind the release plan to the exact committed source snapshot and reject source, tree or file-set drift after planning while accepting the machine-generated dependency-closure version projection in the final Release-only commit.
- Project the CLI README current version, exact query and installation examples from the machine plan, then reject every other README change against the source snapshot.
- Project the unresolved full frontend template's exact CLI development dependency from the machine plan without parsing its placeholders, then reject every other template change against the source snapshot.
- Use the Runner's trusted Release-only classifier in `release:local-check`, selecting `release:pr-check` for machine projections and retaining ordinary Changeset/plan checks for mixed source changes.
- Retain high-volume Maven and npm output from `mango release prepare` with an explicit 64 MiB child-process buffer, preventing Node's default output limit from terminating a healthy candidate build before its manifest is written.
- Validate mixed Release Changeset intent only through the plan's committed source snapshot, while the separate plan check continues to verify every final machine-generated package/version projection.

## Added

- Add Changesets plus Git-impact reconciliation, runtime dependency closure and the CLI version matrix as the machine-owned Mango component release scope.
- Add SHA-256 sealed npm and Maven candidates, mixed candidate consumption, pure consume-registry verification and resumable publish/repair without rebuilding immutable coordinates.
- Add `mango-submit-pr` and require a final-head local equivalent for every applicable required Runner check before Push.

## Changed

- Keep the repository-only `mango-release` Skill exclusively in the Mango source repository; it is not projected into `@mango/pmo`, Business Starter or a business repository.
- Preserve a local-only superseded candidate as audit evidence when the Release PR HEAD/tree changes, then rebuild the canonical candidate from the new exact source.

## Business Impact

- Aggregated Admin consumers upgrade only `@mango/admin` to `1.0.66` and refresh the lockfile; direct or modular consumers align the exact `release-versions.json` matrix, especially Job `1.0.27`, Admin Shell `1.0.60` and Admin `1.0.66`.
- Job users regain correct totals, page number, page size and page navigation on four management lists. No Job API URL, permission, tenant, menu, database schema or runtime configuration changes.
- Business repositories receive `mango-submit-pr` through PMO upgrade and lose any PMO-managed project-level `mango-release` copy. Their existing business PR, build, deployment and application-release processes remain separate.
- There is no backend Maven, database, API, menu, permission, tenant, service configuration or data migration in this batch.

## Upgrade Estimate

- Audience: owners of business repositories consuming Job, Admin/Admin Shell, or the PMO/CLI toolchain; repositories consuming none of these coordinates require no change.
- Engineering Effort: approximately 0.5 person-day for an aggregated Admin consumer, 0.5 to 1 person-day for a direct or modular consumer, and 0.25 to 0.5 person-day for a PMO-only repository.
- Execution Window: approximately 30 to 90 minutes for dependency and PMO changes plus 30 to 60 minutes for repository-specific typecheck, production build and focused acceptance; normal deployment-pipeline time is additional.
- Service Downtime: no Mango-mandated downtime or database maintenance window; only the business system's normal frontend or service redeployment window applies.
- Rollback Effort: approximately 15 to 30 minutes to revert the business upgrade commit and lockfile, plus the repository's normal build and deployment-pipeline time.
- Assumptions: the business repository has a clean dependency lock, no private patch against these Mango packages, access to the company npm group registry, and an existing repeatable build/deployment pipeline; custom forks or unrelated dependency conflicts require a separate estimate.

## Verification

- Run a frozen dependency install, frontend typecheck and production build in every upgraded business repository.
- In a Job consumer, verify the definition, instance, Worker and alarm-rule lists show backend totals, preserve page size, request the selected page and move between pages correctly.
- In an Admin consumer, verify a clean production build and parent-menu highlighting, including sibling-prefix rejection.
- Verify `mango pmo check --project-dir . --locked` succeeds, the managed project copy of `mango-release` is absent, and `mango-submit-pr` is installed.
- Release preparation must pass Changeset/Git impact, machine plan, package exports, Admin style gates, PMO projection, sealed mixed-candidate consumption and the final pure consume-registry install/typecheck/production build.

## Rollback

1. Revert the business repository's dependency/PMO upgrade PR or commit and restore its previous lockfile; rebuild and redeploy through that repository's normal pipeline.
2. For a PMO transaction, run `mango pmo rollback --project-dir . --dry-run`, review the exact managed files, then run the same rollback without `--dry-run` and finish with the locked PMO check.
3. Keep database and Maven state unchanged; this batch has no database or Maven migration to reverse.
4. Never delete, overwrite or republish the immutable npm coordinates from this batch. A Mango artifact defect requires a new patch version and a new release batch.
