## Added
- File record editing: `FileApi.updateRecord` sends `UpdateFileRecordCommand` to `PUT /file/files`, and only the supplied metadata fields change while an empty string clears a nullable field.
- File content replacement: `FileApi.replaceContent` keeps the file id, defaults to the original file name, and automatically chooses the one-shot `POST /file/files/replace` path or a chunked upload session created with `replaceFileId`.
- File management edit dialog in `@mango/file` that edits name, purpose, access level, business type, business id, directory and business metadata for one file id.
- Business apply attributes: `workflow_business_apply_attribute` stores one row per value, multi-value attributes are supported, and Flyway `V5` creates the table and its indexes.
- `WorkflowBusinessApplyApi.updateFilterAttributes` replaces the registered attributes of one apply, which covers values that only become known after submission, such as a document version status.
- Task paging accepts `applyAttributeFilters` with an AND between conditions and an OR inside one condition, plus `applyTimeBegin`, `applyTimeEnd` and `sortBy=applyTime`.
- Workflow events carry `applyAttributes`, and default notifications expand a template variable per filterable attribute.
- Candidate-group nodes expand role, position and organization members at runtime, then create one task per member for countersign, or-sign and sequential approval modes; an empty member set returns the `EMPTY_ASSIGNEE` sentinel instead of a shared claim task.
- `WorkflowCandidateGroupProvider.memberUserIds` is the single implementation that maps a candidate group to members, and auto assignment reuses it.

## Fixed

- A file can be replaced without losing its id, so permissions, business bindings and audit history stay attached to the same record instead of a newly created duplicate.
- A replaced file keeps the original name when the caller does not supply a new one, so business views that render by name do not show an empty title.
- `@mango/cms` row saving no longer depends on an editor config that may omit `create` or `update`; the missing branch returns early instead of calling an undefined callback.
- `@mango/rbac` no longer sends an invalid runtime code when a runtime strategy row has no module code.
- Task paging by apply attributes no longer requires joining business tables per query, which removes the previous key-list workaround and its page-size limit.
- Countersign, or-sign and sequential approvals now take effect for role, position and organization approvers: each resolved member gets a task, and a task that already has an assignee is no longer re-filled with the candidate group.

## Business Impact

- Uploaded documents can be corrected in place: a business user edits the byte content of an existing file record instead of deleting and re-uploading, so permissions, references and history stay on the same file id.
- File metadata such as business type, business id and directory can be corrected after upload, which removes the previous workaround of re-registering the record.
- Task lists can filter by business attributes that the business module declares, which replaces the business-side key-list query and makes large task lists pageable again.
- Attribute values that change after submission, such as a document version status, can be refreshed through one idempotent update call, so task filters do not serve stale values.
- Default notifications can show filterable attributes and use the business view target for pending-approval messages, so a recipient opens the business page instead of a generic workflow page.
- Role, position and organization approvers are expanded into individual tasks, so a countersign node waits for every member and an or-sign node completes with the first member instead of one member claiming a shared task.
- Two additive migrations run on upgrade: Flyway `V5` creates `workflow_business_apply_attribute` with its indexes, and Flyway `V7` adds the replace target column to `file_upload_session`.

## Upgrade Estimate

- Audience: Mango backend consumers that use `mango-file`, `mango-workflow` or the default notification templates, and consumers of the eighteen npm packages in the sealed closure.
- Engineering Effort: 0.5 engineer-day per consumer to upgrade the tuple, apply the two migrations and pass `filterAttributes` plus `applyAttributeFilters` from business pages that need task filtering.
- Execution Window: 2 hours per consumer including backend restart, two file replacements and one filtered task page check.
- Service Downtime: one controlled backend restart window; both migrations are additive and run before the new build serves traffic.
- Rollback Effort: 0.5 engineer-day per consumer to restore the complete Maven `1.8.1` tuple and the previously verified npm and CLI versions; the two migrations can stay in place because they add a table and a nullable column.
- Assumptions: consumers run MySQL 8 or a compatible engine, use the Mango Flyway history, and have a business page that can trigger a task list query with at least one filterable attribute.

## Upgrade Notes

1. Upgrade the complete Mango Maven/docs tuple from `1.8.1` to `1.9.0`; do not update only one starter or module.
2. Let Flyway `V5` and `V7` run during startup; do not create `workflow_business_apply_attribute` or the `file_upload_session` replace column by hand.
3. Upgrade the eighteen npm packages as one closure with `@mango/cli@1.4.9`; mixing `@mango/file@1.3.0` with an older `@mango/admin-shell` is not supported.
4. Register filterable attributes with `filterAttributes` on apply creation and refresh changing values through `PUT /workflow/business-applies/filter-attributes` before the business page depends on them.
5. Pass `applyAttributeFilters`, `applyTimeBegin`, `applyTimeEnd` and `sortBy=applyTime` from the business task page instead of joining business tables to build a key list.
6. Verify one small-file replacement, one chunked replacement above the single-request limit, one metadata-only edit and one filtered task page in a test environment before production rollout.

## Rollback

- Restore the complete Maven `1.8.1` tuple and the previous npm versions recorded in `mango-ui/.changeset/release-baseline.json`; do not patch a single module.
- Keep the two applied migrations: `V5` adds a table and `V7` adds a nullable column, so `1.8.1` code runs unchanged against the upgraded schema.
- Stop using `filterAttributes`, `applyAttributeFilters` and the file replace endpoints in business pages before rolling the backend back, otherwise those requests return an unknown-endpoint error.
- Roll back the workflow modules to `1.8.1` and re-save the process definitions through the designer to drop the multi-instance collection expression, otherwise candidate-group nodes keep the `1.9.0` BPMN and fail on the old runtime.
- If a replaced file must be recovered, restore the previous object from the storage backup of that file id; the database row keeps the same id, so restoring the object restores the previous content.
