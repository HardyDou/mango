# 交付模式与保障措施规范

## 1. 定位

- 本文件是 `SIMPLE / STANDARD / FULL` 交付模式、工作区隔离和 `M01-M16` 执行能力的唯一规范源。
- 交付模式负责控制流程和文档成本；保障措施负责证明具体目标，二者不得互相冒充。
- 风险等级采用 `max(需求影响, 方案风险)`，并决定默认交付模式；验证类型仍按真实入口和可观察结果选择。
- 发布、版本、制品、tag、Release 和发布恢复继续使用独立发布流程。

## 2. 工作区默认策略

1. 只读问答、状态查看、日志查看和纯 fast-forward 同步不创建 worktree。
2. 需要修改受版本控制文件时，默认禁止在 `main` 分支或主 worktree 开发。
3. 当前已在同一任务的非 `main` worktree 时传入 `--reuseCurrentTask true` 并直接复用；非 main 不能自动证明属于同一任务，缺少该事实时按新任务隔离。
4. 当前位于 `main` 或主 worktree 且没有可复用任务 worktree 时，Agent 自动创建任务分支和仓库外同级 worktree，不再逐次询问 M01。
5. 只有用户明确要求在 `main` 或主 worktree 修改，并在 Agent 提示污染、并行冲突和误提交风险后再次确认，才允许 `MAIN_EXCEPTION`。
6. M01 是仓库策略决策，不是普通任务问卷。机器记录 `CREATE`、`REUSE` 或 `MAIN_EXCEPTION` 及证据；历史 `DO_NOT_CREATE` 只用于兼容旧基线。

## 3. 三档交付模式

| 模式 | 默认等级 | 适用事实 | 文档与执行方式 |
|---|---|---|---|
| `SIMPLE` | `L0-L1` | 文档、注释、局部可逆实现、明确小缺陷，且不改变公共契约、数据/安全边界或跨模块协作 | 直接实现；不创建 BRD、SRS、TDD、Plan 或标准交付记录；执行能够证明目标的最低成本定向验证。 |
| `STANDARD` | `L2` | 可观察行为、公共能力、接口/数据协作或多步骤实现发生中等影响，但边界和恢复方式明确 | 使用一个标准交付记录文件，集中登记精简 SRS、技术决定、实施清单、验收映射和结果；不拆成四份阶段文档。 |
| `FULL` | `L3` | 主干业务、跨服务/跨模块、高影响数据、安全、权限、租户、资金、发布或治理系统修改自身 | 执行完整的需求、设计、计划、实现、验证和验收流程；产品变更使用适用的 BRD/SRS/TDD/Plan 链，治理或发布任务使用其专用完整记录，不伪造无关产品文档。 |

默认映射固定为：`L0/L1 -> SIMPLE`、`L2 -> STANDARD`、`L3 -> FULL`。

- 用户可以明确选择更高模式。
- 降低模式必须说明成本收益和剩余风险，并由用户明确确认；PR 使用 `MODE_DOWNGRADE_CONFIRMED` 保存人工证据。权限、租户、资金、数据破坏、安全和不可逆发布必须登记到 `Non-downgradable facts`，checker 从风险事实交叉识别，命中后不得降级。
- 实际范围、方案或失败后果扩大时立即升级模式，只补新增要求，不重做已经有效的证据。
- 行数少、文件少或实现简单不能降低已经成立的需求影响。

## 4. STANDARD 单文件

标准交付记录固定使用 `templates/standard-delivery-record.md`，业务项目建议放到 `business-docs/delivery/<task>.md`。文件至少包含：

1. 目标、范围和不处理范围；
2. 用户或外部系统可观察要求和失败语义；
3. 接口、数据、权限、兼容性和关键技术决定；
4. 有序实施清单、受影响路径和回滚方式；
5. 验收项到验证方式、结果和证据的映射。

同一事实只登记一次。STANDARD 文件不是第二套长期规范，也不得复制 PMO 规则正文。

## 5. M01-M16 执行能力

| ID | 能力 | 启用来源 |
|---|---|---|
| M01 | Worktree 隔离 | 工作区策略自动决定；只有 `MAIN_EXCEPTION` 需要人工确认。 |
| M02 | 数据库重建 | 涉及空库形成、初始化或数据库验收时提出；破坏性执行必须人工确认。 |
| M03-M06 | BRD、SRS、TDD、实施计划 | `FULL` 的适用产品文档链自动展开；`STANDARD` 合并投影到一个标准交付记录；`SIMPLE` 不创建。 |
| M07 | 治理决策记录 | 长期 PR、CI、权限、审批责任或仓库治理语义变化时启用。 |
| M08 | 能力说明 | 公开能力、配置、接入、使用或验收方式变化时启用。 |
| M09 | 静态验证 | 结构、格式、配置、代码规则或编译可以观察目标时启用。 |
| M10 | 单元测试 | 独立规则、算法、状态转换或函数行为变化时启用。 |
| M11 | 集成测试 | 结果依赖模块、数据库、框架装配或组件协作时启用。 |
| M12 | API 验证 | API 或服务入口行为变化时启用。 |
| M13 | UI 验证 | 用户界面或浏览器交互变化时启用；无 UI 的 L3 不启用。 |
| M14 | 专家复核 | 专业不确定性、高影响决定或治理系统修改自身时启用。 |
| M15 | 外部状态回读 | 当前目标需要 GitHub、Gitea 等外部状态证明时启用。 |
| M16 | 人工验收 | 自动化不足以证明业务、视觉、责任或现场结果时启用。 |

风险等级选择流程强度，不机械选择测试类型。每项验证必须能观察其声称证明的结果；最低成本服从充分证明。

## 6. 决策与询问边界

Agent 必须先确认目标、成功条件、范围、受影响对象和可核验事实，再计算风险和模式。下列情况才询问用户：

- 目标、范围或关键业务决定无法从事实确定；
- 请求 `MAIN_EXCEPTION`；
- 请求低于默认风险等级对应的模式；
- M02 将清空或重建非一次性数据库；
- 外部写操作、发布或其它需要独立授权的动作；
- 成本、权限、环境影响或剩余风险发生实质变化。

禁止把 M01-M16 做成每个任务都要回答的固定问卷。模式和措施已能由规则与事实确定时直接执行。

受信任 base checker 尚未升级的合同切换 PR，可以使用带明确人工责任人的历史 `CONFIRMED` 基线；新合同合并后统一使用 `RESOLVED`，不得把兼容入口恢复为逐项人工问卷。

## 7. 决策基线与重新评估

基线至少记录：目标、范围、需求影响、方案风险、最终等级、交付模式、工作区决策、事实证据、启用能力、验证证据、例外和剩余风险。基线可以保存在会话、PR、标准交付记录、完整流程文档或忽略的运行时状态。

以下事实变化时重新计算，只升级或调整受影响部分：

- 目标、成功条件、范围或受影响系统变化；
- 实际 diff 超出确认边界；
- 方案改变耦合、恢复成本或失败后果；
- 数据库、外部状态、验证、复核或人工验收事实新增或消失；
- 已选验证无法证明目标。

命令参数修正、等价实现细节、只读诊断和同一验证重试不要求重新确认。

## 8. 机器检查边界

- 机器可以校验风险与模式映射、工作区决策、标准交付记录结构、能力 ID、证据和范围一致性。
- CI 按交付模式检查文档承载方式，并只运行能证明当前目标的适用验证；不得给无 UI 任务补 UI 测试。
- 机器不得把行数、文件数或关键词作为唯一风险判断，也不得替用户批准 main 例外、破坏性数据库操作或发布。

## 9. 禁止事项

- 禁止在 `main` 或主 worktree 默认开发。
- 禁止 SIMPLE 任务机械生成文档或长问卷。
- 禁止 STANDARD 拆出重复的 BRD、SRS、TDD、Plan。
- 禁止 FULL 伪造与任务无关的产品文档或测试入口。
- 禁止用低风险或低成本验证绕过权限、租户、事务、资金、数据和真实入口证明。
- 禁止把发布授权混入交付模式决策。
