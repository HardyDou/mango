# 交付保障方案与人工确认规范

## 1. 定位

- 本文件是交付保障措施目录、建议场景和人工确认方式的唯一规范源。
- AI 根据实际目标和事实提出建议；用户决定采用、停用或在目录内替换措施，并接受停用后的剩余风险。
- 风险等级只描述影响和复核强度，不选择固定文档或测试套餐。
- 本机制不包含发布、版本、制品、仓库发布回查、tag、Release 和发布恢复；发布继续使用独立发布流程。

## 2. 选择原则

1. AI 必须先确认目标、成功条件、范围、受影响对象和可核验事实，再检查固定目录 `M01` 至 `M16`。
2. 只以当前任务要改变、决定或证明的事实触发措施。只验证已经部署或已经变更的对象时，不倒推补开历史 BRD/SRS/TDD；纯查看列表、状态或日志且不形成配置/交付结论时，不触发本机制。M15 只在外部状态回读承担当前配置或目标的证明责任时触发。
3. 出现某项建议场景时，AI 必须说明该措施的价值、成本和停用影响，并通过 Agent 原生 Ask User 询问；出现触发事实不等于自动启用。
4. 未出现触发事实的措施不得进入问卷。禁止把十六项做成每个任务都要回答的固定清单。
5. 用户确认值优先于 AI 建议。AI 必须记录停用后的剩余风险，不得自行恢复被用户停用的措施。
6. 每项采用的措施必须保障当前目标、失败模式、证明责任或恢复需要；与任务无关且不承担保障作用的措施不采用。
7. 现有有效材料已经提供同等保障时优先复用；启用文档措施不等于必须重复创建文件。
8. 系统、平台和工具不可由用户绕过的安全限制不属于本目录的可选项。

## 3. 固定 v1 措施目录

| ID | 措施 | 允许值 | 建议场景与询问触发事实 | 保障价值 |
|---|---|---|---|---|
| M01 | Worktree 隔离 | `CREATE` / `DO_NOT_CREATE` | 需要修改受版本控制文件 | 隔离任务改动，避免污染错误分支或其它并行工作；不新建时必须明确当前工作区承载该任务的影响。 |
| M02 | 数据库重建 | `REBUILD` / `DO_NOT_REBUILD` | 涉及数据库结构、初始化数据、空库启动或数据库验收 | 证明目标数据库可从受管输入形成预期状态；不重建时保留既有数据或迁移状态未被空库验证的风险。 |
| M03 | BRD | `ENABLE` / `DISABLE` | 业务目标/范围/参与者责任/业务规则/业务验收变化 | 固化业务承诺和验收边界，防止技术实现代替业务决定。 |
| M04 | SRS | `ENABLE` / `DISABLE` | 用户或外部系统可观察行为/状态/输入输出/失败语义变化 | 固化可观察系统行为，避免实现、测试和业务预期分叉。 |
| M05 | TDD | `ENABLE` / `DISABLE` | 接口/数据/安全/架构/兼容性/关键技术取舍 | 保存关键技术决定、边界和恢复依据，避免实现者自行补设计。 |
| M06 | 实施计划 | `ENABLE` / `DISABLE` | 实施顺序/多人协作/跨模块依赖/复杂步骤 | 协调任务依赖、责任和完成顺序，降低漏项与返工风险。 |
| M07 | 治理决策记录 | `ENABLE` / `DISABLE` | 长期PR/CI/权限/审批责任/仓库治理语义变化 | 保存治理意图、适用条件和责任边界，防止未来配置与规则漂移。 |
| M08 | 能力说明 | `ENABLE` / `DISABLE` | 公开能力/配置/接入/使用方式变化 | 让能力消费者获得与实现一致的使用、配置和接入事实。 |
| M09 | 静态验证 | `ENABLE` / `DISABLE` | 目标可由结构/格式/配置/代码规则/编译证明 | 以最低成本证明可静态观察的约束，但不能替代其观察不到的运行行为。 |
| M10 | 单元测试 | `ENABLE` / `DISABLE` | 独立规则/算法/状态转换/函数行为变化 | 隔离验证局部决策和边界分支，快速定位逻辑回归。 |
| M11 | 集成测试 | `ENABLE` / `DISABLE` | 结果依赖模块/数据库/框架装配/组件协作 | 证明真实协作、装配和持久化边界，不以孤立替身冒充集成结果。 |
| M12 | API 验证 | `ENABLE` / `DISABLE` | API或服务入口行为变化 | 从服务入口证明契约、权限、数据和失败行为。 |
| M13 | UI 验证 | `ENABLE` / `DISABLE` | 用户界面/交互变化 | 从用户入口证明可见结果、交互和浏览器运行态。 |
| M14 | 专家复核 | `ENABLE` / `DISABLE` | 专业不确定性/高影响决定/治理系统修改自身 | 使用独立相关视角发现知识盲区和自证偏差。 |
| M15 | 外部状态回读 | `ENABLE` / `DISABLE` | 目标涉及GitHub/Gitea等外部平台配置或运行状态 | 证明真实外部状态已生效并发现配置漂移，包括声明、请求和远端结果之间的偏差。 |
| M16 | 人工验收 | `ENABLE` / `DISABLE` | 自动化不足以证明实际目标 | 由责任人确认自动化无法覆盖的实际结果，包括业务、视觉、责任或现场判断。 |

目录名称、ID、允许值和语义固定为 v1。新增、改名、合并或拆分措施必须作为独立 PMO 治理变更升级目录版本；任务内禁止临时创建 `M17`。

值建议边界：

- M01：已确认要修改受版本控制文件，且当前位于主工作区、没有可复用任务 worktree 时建议 `CREATE`；已经位于同一任务的隔离 worktree 时建议 `DO_NOT_CREATE`。若工作区事实未知，先补充事实，不得猜值。“实现、修改、修复、重构、更新仓库内容”等交付动词可作为会修改受控文件的事实，明确只读或不写文件时除外。
- M02：目标明确要求空库形成、空库启动或可丢弃测试库重建证明时建议 `REBUILD`；生产历史数据、迁移后兼容性或明确不可清空的验收建议 `DO_NOT_REBUILD`。数据库验证层级另按 M11 的独立触发事实判断。
- M03-M16：出现本表触发事实时通常建议 `ENABLE`；用户已明确停用、目标只要求设计组合而非执行，或已有等价保障时可建议 `DISABLE`，但必须说明剩余风险或复用证据。

## 4. 原生人工确认

- 原生 Ask User 或 `request_user_input` 可用时必须使用，不得只在正文中写“请确认”。
- 每个问题只确认一项措施；每批最多三项，只询问已触发措施。
- 推荐值放在第一项，问题必须说明价值和另一个值留下的剩余风险。
- 不设置自动确认或超时默认值。
- 先询问 M01、M02；根据回答重新识别事实后，再分批询问 M03 至 M08、M09 至 M16 中仍然触发的措施。
- M01 只允许 `CREATE`、`DO_NOT_CREATE`；M02 只允许 `REBUILD`、`DO_NOT_REBUILD`；M03 至 M16 只允许 `ENABLE`、`DISABLE`。
- 用户提出替代方案时，必须落到现有措施的执行变体或“停用原措施、启用另一现有措施”；不得在任务内发明新措施。

## 5. 确认基线与重新确认

确认基线至少记录：目标、范围、事实证据、触发措施、AI 建议、用户选择、选择依据、接受的剩余风险和基线摘要。基线可以保存在会话、PR body、任务记录或被忽略的运行时状态；禁止仅为保存选择而强制新增版本控制文档。

以下事实发生实质变化时，只重新询问受影响措施，并保留其它选择：

- 目标、成功条件、范围或受影响系统变化；
- 实际 diff 超出确认边界；
- 已选措施无法执行或需要不同保障能力的替代；
- 数据库、文档、验证、复核、外部状态或人工验收触发事实新增或消失；
- 成本、权限、环境影响或剩余风险显著变化。

命令参数修正、等价实现细节、只读诊断和原措施重试不要求重新确认。

## 6. 机器检查边界

- 机器可以校验措施 ID、允许值、原生确认记录、基线摘要、所选措施的执行证据和当前范围是否一致。
- CI 只验证用户确认启用且适用于 CI 的措施，不得按风险等级补加文档或测试套餐。
- 机器不得替用户选择措施，不得把 AI 建议写成已确认值，不得因未触发措施缺少选择而失败。

## 7. 禁止事项

- 禁止把风险等级直接映射为 BRD、SRS、TDD、Plan 或固定测试组合。
- 禁止向每个任务展示十六项长问卷。
- 禁止把发布混入交付保障确认。
- 禁止 AI、CI 或默认超时替代用户确认。
- 禁止用户停用措施后仍暗中执行或声称该措施已提供保障。
