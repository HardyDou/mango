# 系统需求规格说明书规范

本文件是系统需求规格说明书（SRS）的唯一规范源。可执行投影位于 `mango-pmo/contracts/system-requirements.json`，其中只能引用本文件的 `ruleId`。正式文档使用 `mango-pmo/templates/system-requirements.md`。

系统需求规格说明书只在用户确认 `M04 SRS=ENABLE` 时建立，只回答系统必须向用户和外部参与系统提供什么可观察行为。用户同时启用 M03 时承接已批准 BRD；未启用 M03 时，以交付保障确认基线中的目标、范围、参与者和验收事实作为直接来源，并把上游文档元数据显式写为 `NONE`。页面、字段和交互属于本阶段；URL、HTTP、DTO、数据库、模块、类和实现方案属于技术设计。

## SRS-SEC-001 文档控制与上游基线

- **目的**：固定 SRS 身份、规则版本和适用来源基线，防止基于过期或臆造需求继续设计。
- **正向要求**：填写唯一 `documentId`、固定 `documentType: system-requirements`、版本、风险和证据、状态动作、责任人与审批证据；FULL 产品流程存在 BRD 时，SRS 风险不得低于 BRD并引用其 ID/hash；BRD 不适用时使用 `NONE` 并引用模式基线。
- **禁止项**：禁止把未启用 BRD 伪造成前置文档；启用 BRD 时禁止没有上游摘要、引用 DRAFT/BLOCKED BRD 或在上游变化后保留 `APPROVED/NEXT`；禁止 SRS 未审批即作为已批准输入使用。
- **正例**：`SRS-ANN-001` 引用 `BRD-ANN-001` 的完整 SHA-256，状态由门禁在评审后更新。
- **反例**：上游写“最新版 PRD”。错误原因：来源不唯一、不可验证且沿用已废弃混合 PRD 概念。
- **机器判定**：`SRS-META-001` 检查元数据、上游 ID/摘要格式、状态动作和占位符；生命周期检查器校验摘要和阶段顺序。

## SRS-SEC-010 系统范围与上下文

- **目的**：把 BRD 业务范围转成系统责任边界，区分本系统、用户、外部参与系统和人工环节。
- **正向要求**：系统范围项使用 `SC-xxx`；启用 BRD 时引用 `BS/BG/BF`，未启用时上游 ID 写 `NONE` 并按保障基线写系统责任、边界外责任、参与方和可观察输出；上下文关系使用业务能力名称。
- **禁止项**：禁止写模块包名、部署拓扑、类、数据库或技术协议；禁止扩大 BRD 范围；禁止把人工业务责任默认为系统自动化。
- **正例**：系统负责记录公告提交和审核决定并向相关参与者展示当前结果；法务线下定稿不在系统责任内。
- **反例**：由 `mango-notice-core` 和 Redis 实现审核。错误原因：属于技术架构。
- **机器判定**：`SRS-STRUCT-010` 检查上下文表结构、至少一行和来源引用格式；`SRS-ID-010` 检查 `SC-xxx` 唯一；上游来源由生命周期检查器验证。

## SRS-SEC-020 系统参与者与访问行为

- **目的**：把业务参与者映射为系统使用者，定义可见内容、可执行操作、不可执行操作和系统反馈。
- **正向要求**：参与者使用 `SA-xxx`；启用 BRD 时引用 `BA-xxx`，未启用时上游参与者 ID 写 `NONE` 并使用保障基线中的人工确认角色事实；写使用入口类别、可见范围、可执行动作、禁止动作及用户可见原因，只描述行为边界。
- **禁止项**：禁止权限码、角色编码、注解、token、数据权限 SQL 或默认授权实现；禁止只写“有权限/无权限”；禁止改变 BRD 职责分离规则。
- **正例**：审核员可查看待其处理的公告并作出决定，不能编辑公告正文；系统明确显示“审核角色不能修改提交内容”。
- **反例**：拥有 `notice:audit` 的用户可调用接口。错误原因：权限资源和调用方式属于技术设计。
- **机器判定**：`SRS-STRUCT-020` 检查参与者表和必填值；`SRS-ID-020` 检查 `SA-xxx` 唯一；BRD 参与者引用格式由本地检查、存在性由生命周期检查。

## SRS-SEC-030 功能需求

- **目的**：以“系统应”形式定义可观察功能行为、触发条件、输入语义、处理结果和失败结果。
- **正向要求**：功能需求使用 `FR-xxx`；启用 BRD 时每项引用至少一个 `BG/BF/BR/BAC`，未启用时上游 ID 写 `NONE` 并以保障基线为来源；写触发者、前置条件、输入信息语义、系统行为、成功反馈、失败/禁止反馈和状态影响；一个独立能力一项。
- **禁止项**：禁止 URL、HTTP 方法、DTO、类或算法；禁止只写“支持新增/修改/删除”；禁止把多个独立能力合并为“管理功能”；禁止引入无上游来源的新业务规则。
- **正例**：`FR-001`：运营人员提交完整公告时，系统登记提交结果并显示“待审核”；缺少必需业务信息时保持可编辑并指出缺项。
- **反例**：`POST /api/notices` 接收 `CreateNoticeCommand`。错误原因：描述了技术接口而非系统行为。
- **机器判定**：`SRS-STRUCT-030` 检查功能表字段和至少一行；`SRS-ID-030` 检查 `FR-xxx` 唯一；来源引用必填；`SRS-BOUNDARY-001` 检查技术内容。

## SRS-SEC-040 用户场景与交互流程

- **目的**：把 BRD 业务流程展开为用户与系统之间的可观察交互，包括主路径、替代路径和失败路径。
- **正向要求**：交互场景使用 `UC-xxx`；启用 BRD 时引用 `BF`，未启用时上游流程 ID 写 `NONE`；始终引用本地 `FR`，写参与者、入口、前置状态、用户动作、系统反馈、替代/异常路径和完成状态；用户动作和系统反馈分列。
- **禁止项**：禁止写 Controller-Service 调用链、事务、消息队列或数据库处理；禁止只有点击步骤没有系统反馈；禁止以页面跳转代替业务结果。
- **正例**：用户选择提交后，系统先指出缺失信息；信息完整时显示提交成功和新的业务状态。
- **反例**：前端请求后端，Service 保存数据库。错误原因：是内部处理，不是交互需求。
- **机器判定**：`SRS-STRUCT-040` 检查场景表、必填值和 `UC-xxx` 唯一；`BF/FR` 引用格式、已定义本地 FR 和上游 BF 覆盖由检查器验证。

## SRS-SEC-050 页面、信息与动作需求

- **目的**：明确用户需要的页面、信息组织、字段业务语义和按钮行为，为技术设计提供无歧义的系统呈现要求。
- **正向要求**：页面使用 `PG-xxx`，动作使用 `BT-xxx`；页面表写用途、参与者、信息区域、状态和关联 FR；动作表写所在页面、显示/可用条件、用户交互、成功/失败反馈；字段表写业务名称、语义、来源类别、必填条件、输入限制、空值含义和展示要求。
- **禁止项**：禁止路由、component key、组件库、CSS、接口字段名或数据库列；禁止只写“标准列表页/标准表单”；禁止没有空、加载、失败和不可操作状态。
- **正例**：`PG-001 公告工作区`按业务状态分组展示；`BT-001 提交审核`仅在必需信息完整且公告可编辑时可用。
- **反例**：路由 `/notice/list` 使用 `ElTable`，按钮调用 `approveApi`。错误原因：属于前端和接口实现。
- **机器判定**：`SRS-STRUCT-050` 检查页面、动作、字段和页面状态四张表及表头；`SRS-ID-050` 检查 `PG/BT` 唯一；动作页面与 FR 引用必须存在；边界由 `SRS-BOUNDARY-001` 检查。

## SRS-SEC-060 逻辑数据需求

- **目的**：定义系统需要接收、保存、展示和交换的信息语义、质量、保留与可见范围，不决定物理数据模型。
- **正向要求**：逻辑数据使用 `DR-xxx`；引用 `BO/BR/FR`，写业务信息、来源、使用场景、完整性/唯一性口径、保留要求、敏感级别和用户可见空值语义。
- **禁止项**：禁止表名、列名、数据类型、主外键、索引、ORM Entity 或 migration；禁止把页面字段直接等同为数据库字段；禁止自行增加 BRD 未确认的数据口径。
- **正例**：审核决定必须关联作出决定的业务参与者、决定时间和原因，拒绝时原因必填并对提交人可见。
- **反例**：`notice_audit.reason VARCHAR(500) NOT NULL`。错误原因：是物理数据设计。
- **机器判定**：`SRS-STRUCT-060` 检查数据需求表和必填值；`SRS-ID-060` 检查 `DR-xxx` 唯一；来源引用格式和本地 FR 存在；SQL/数据类型由边界检查。

## SRS-SEC-070 外部交互需求

- **目的**：描述本系统与外部参与系统之间要交换的业务能力、信息语义、时效、失败可见结果和责任边界。
- **正向要求**：外部交互使用 `IR-xxx`；写外部参与方、业务目的、触发、输入/输出业务信息、时效、重复/失败业务处理和责任边界；只定义逻辑契约。
- **禁止项**：禁止 endpoint、HTTP/RPC 方法、请求响应类、Feign、认证头、重试库或序列化格式；禁止把外部系统可用性假定为本系统可控；不适用时明确写 `NONE` 行及依据。
- **正例**：发布完成后向企业消息平台提供公告标题、受众和生效时间；消息平台不可用时用户看到“发布已完成，通知待重试”。
- **反例**：使用 Feign 调用 `POST /messages`，超时 3 秒。错误原因：调用技术和超时实现属于 TDD。
- **机器判定**：`SRS-STRUCT-070` 检查外部交互表至少一行（允许受控 `NONE`）；`SRS-ID-070` 检查真实条目的 `IR-xxx` 唯一；`SRS-BOUNDARY-001` 检查技术协议。

## SRS-SEC-080 非功能需求

- **目的**：定义性能、容量、可用性、安全、可访问性、兼容性、审计和恢复等可验证质量目标。
- **正向要求**：非功能项使用 `NFR-xxx`；启用 BRD 时引用其约束，未启用时上游 ID 写 `NONE`；写适用场景、度量指标、目标值、测量条件、失败影响和验收方式；目标必须来自用户确认或现状基线，禁止 AI 编造。
- **禁止项**：禁止“性能良好、安全可靠、体验流畅”等不可测表述；禁止在本章指定缓存、线程池、数据库或框架方案；禁止无来源地编造目标值。
- **正例**：在约定业务高峰 200 名并发查看者下，公告工作区 95% 的可见结果在 2 秒内完成，测量不包含用户网络时延。
- **反例**：使用 Redis 保证高性能。错误原因：是实现选择且没有可验收指标。
- **机器判定**：`SRS-STRUCT-080` 检查 NFR 表、度量和目标值必填；`SRS-ID-080` 检查 `NFR-xxx` 唯一；边界检查技术方案词。

## SRS-SEC-090 系统验收标准

- **目的**：把业务验收转化为可执行的系统行为断言，覆盖成功、失败、禁止、边界和非功能结果。
- **正向要求**：系统验收使用 `SAC-xxx`；启用 BRD 时引用至少一个 `BAC`，未启用时业务验收 ID 写 `NONE` 并对应保障基线中的人工确认验收事实；始终引用一个本地 `FR/UC/PG/BT/DR/IR/NFR`；写前置状态、用户或外部动作、可观察结果、失败/边界结果和验收类型。
- **禁止项**：禁止以实现类、接口 200、数据库行数或测试命令作为期望结果；禁止只覆盖正常路径；禁止一个 SAC 覆盖多个独立业务结果。
- **正例**：`SAC-001`：公告信息完整时提交后显示待审核；信息缺失时不提交并在对应信息处显示业务原因。
- **反例**：调用接口返回 JSON 的 `code=0`。错误原因：是技术响应，不是用户可观察的系统行为。
- **机器判定**：`SRS-STRUCT-090` 检查验收表和必填值；`SRS-ID-090` 检查 `SAC-xxx` 唯一；来源必须同时含上游和本地 ID；边界检查技术验收表达。

## SRS-SEC-100 系统需求追踪矩阵

- **目的**：证明每个系统要求都有适用来源和系统验收；启用 BRD 时同时证明所有业务项被承接。
- **正向要求**：矩阵逐项登记上游 ID、系统需求 ID、SAC 和覆盖说明；启用 BRD 时覆盖所有上游 `BG/BS/BA/BO/BF/BR/BAC`，未启用时上游 ID 写 `NONE` 并在覆盖说明中关联保障基线事实；所有本地 `SC/SA/FR/UC/PG/BT/DR/IR/NFR/SAC` 必须出现。
- **禁止项**：禁止孤儿系统需求；禁止静默遗漏上游 ID；禁止引用不存在 ID；禁止用章节名称代替稳定 ID。
- **正例**：`BF-001 -> FR-001, UC-001, PG-001, BT-001 -> SAC-001`。
- **反例**：业务需求均已覆盖。错误原因：无可验证映射。
- **机器判定**：`SRS-TRACE-100` 检查本地 ID 全覆盖、引用存在和无孤儿；生命周期检查器读取 BRD 合同后检查上游 ID 全覆盖及无未知引用。

## SRS-SEC-110 阶段判定与审批

- **目的**：用外部校验和系统需求评审决定是否可进入技术设计。
- **正向要求**：登记 checker、适用的上游摘要校验、阻断数、例外和系统需求审批证据；只有内容校验、适用生命周期校验及人工评审通过时才允许 `NEXT`。`NEXT` 只表示 SRS 自身批准，不自动启用 TDD 或其它措施。
- **禁止项**：禁止 AI 自填 PASS 作为证据；禁止上游摘要不一致仍继续；禁止未关闭需求缺口进入 TDD；禁止无期限例外。
- **正例**：checker 与 handoff 均 PASS，系统分析负责人批准，编排器写入 `APPROVED/NEXT`。
- **反例**：页面原型已写完，因此可以开发。错误原因：没有覆盖、边界和审批证据。
- **机器判定**：`SRS-GATE-110` 检查门禁表和元数据一致；生命周期检查器验证上游摘要、审批和追踪覆盖。

## SRS-BOUNDARY-001 阶段边界

- **目的**：允许系统行为和 UI 需求，阻止进入技术设计或实施计划。
- **正向要求**：使用“系统应提供的可观察行为”表达；页面、字段、动作仅写业务语义、状态和反馈；外部交互仅写逻辑能力。
- **禁止项**：禁止 URL、路径参数、HTTP/RPC 方法、请求/响应类、OpenAPI 注解；禁止 api/core/starter/starter-remote 模块归属；禁止 Controller、Feign、Service、MangoCrudService、Mapper、Entity、DTO、VO、Command、Query、`R`、`Require`、`ErrorCode`；禁止表、列、类型、索引、SQL、migration；禁止路由、component key、组件库、测试命令和任务排期。
- **正例**：系统应允许审核员查看待处理公告并给出通过或拒绝结果。
- **反例**：`NoticeApi` 在 starter-remote 中定义 Feign，Controller 使用 `@PostMapping`。错误原因：属于技术设计和代码规范。
- **机器判定**：合同对结构化文本节点执行技术词、代码标识、路径模板和 SQL 片段检查并报告本 `ruleId`；需求语义是否完整由系统分析负责人审核。
