# 产品文档生命周期与移交规范

本文件是 BRD -> SRS -> TDD -> Plan 生命周期、风险等级和阶段移交的唯一规范源。四份文档的章节内容分别由同目录 `01` 至 `04` 规范约束；本文件不复制其正文。

## LIFE-RISK-001 L0-L3 风险分级

- **目的**：引用统一风险分级结果决定文档门禁强度，避免复杂任务跳阶段，也避免低风险任务制造空文档。
- **正向要求**：风险等级及判定口径以 `mango-pmo/rules/09-test-case-automation-flow.md` 为唯一源；四阶段元数据只记录 `riskLevel` 和 `riskAssessmentEvidence`。进入正式产品文档链路的 L2/L3 任务必须保留完整四阶段；L0/L1 使用其适用的轻量流程，不伪造四阶段文档。
- **禁止项**：禁止仅以代码行数或“看起来简单”降级；禁止 L2/L3 缺失 BRD、SRS、TDD 或 Plan；禁止 Agent 自行将 L2/L3 改成 L1；禁止用 L0/L1 回避业务目标和验收。
- **正例**：风险评估证据引用测试流程规则和任务事实，结论为 L2 后完整执行四阶段。
- **反例**：接口只改一个方法，因此判定 L1。错误原因：公开契约和消费者影响与代码量无关。
- **机器判定**：`LIFE-RISK-001` 检查四文档风险等级一致；L2/L3 必须传入完整四阶段文件；L0/L1 的轻量路径必须由其它入口明确声明，不能伪造四阶段 `NEXT`。

## LIFE-ORDER-010 固定阶段顺序

- **目的**：确保业务、系统、技术和实施决定逐层收敛，后续阶段不能代替或反向污染前置阶段。
- **正向要求**：正式能力按 BRD -> SRS -> TDD -> Plan 顺序；每个下游只引用紧邻上游的唯一 ID 和摘要；发现缺口回到拥有该决定的阶段修订，再重新执行后续门禁。
- **禁止项**：禁止跳过 SRS 直接由 BRD 生成 API；禁止在 Plan 新增设计；禁止下游文档反写上游事实而不重新审批；禁止同时把多个阶段内容塞入旧 PRD。
- **正例**：SRS 发现业务规则缺少拒绝边界时执行 ASK，修订并批准 BRD 后重新生成 SRS。
- **反例**：在 TDD 中补一个“默认业务规则”继续开发。错误原因：越权且上游无法追踪。
- **机器判定**：`LIFE-ORDER-010` 按 `documentType` 检查文件数量、顺序和相邻 `upstreamDocumentId`；L2/L3 缺任一阶段立即失败。

## LIFE-HASH-020 上游摘要与失效

- **目的**：用内容摘要证明下游基于哪个不可变上游版本，防止审批后静默修改。
- **正向要求**：下游元数据记录上游完整文件的 SHA-256；生命周期校验现场重新计算；上游任何变化都使下游 `STALE/BLOCKED`，必须重新审查受影响链路。
- **禁止项**：禁止使用文件名、分支名、“最新版”或人工版本描述代替摘要；禁止摘要不一致仍保留 NEXT；禁止只更新摘要而不评估内容变化。
- **正例**：BRD 修订后，旧 SRS 的摘要校验失败，编排器阻断 TDD 和 Plan。
- **反例**：只改了一个验收描述，不影响设计，所以继续。错误原因：影响判断尚未经过重新评审。
- **机器判定**：`LIFE-HASH-020` 计算原始 UTF-8 文件字节 SHA-256，与下游元数据严格比较；不一致报告上下游文档 ID。

## LIFE-TRACE-030 双向追踪

- **目的**：保证所有上游要求被下游承接，且所有下游要求、设计和任务都有合法来源。
- **正向要求**：合同声明每阶段本地定义 ID 和追踪章节；移交时检查上游所有可追踪 ID 至少被下游矩阵引用，并检查下游引用无未知上游 ID；例外必须有规则 ID、范围、审批和期限。
- **禁止项**：禁止静默遗漏、孤儿下游项、自然语言替代 ID；禁止一个总括项覆盖多个独立验收；禁止把空矩阵判定为通过。
- **正例**：`BAC-001 -> SAC-001 -> API-001/TC-001 -> TASK-001/VAL-001`。
- **反例**：需求均已覆盖。错误原因：无法证明覆盖关系。
- **机器判定**：`LIFE-TRACE-030` 从各阶段合同指定的定义表提取 ID，从下游追踪章节提取上游 ID，执行集合全覆盖和未知引用检查。

## LIFE-GATE-040 STOP、ASK、WRITE 与 NEXT

- **目的**：把 Agent 动作变成外部可验证状态，而非正文中的自我声明。
- **正向要求**：信息或上游缺失为 `STOP`；需要责任人决定为 `ASK`；可继续编写但未满足移交为 `WRITE`；只有文档 checker、截至当前阶段的连续 handoff、阻断关闭和指定人工审批全部通过时由编排器写入 `NEXT`。本地 `approvalEvidence` 必须引用文档工作区内真实、非空的普通文件；分阶段 handoff 使用 `--through brd|srs|tdd|plan`，只要求当前阶段及其上游；最终交付检查仍要求完整四阶段。
- **禁止项**：禁止 Agent 或作者仅修改正文为 PASS/NEXT；禁止 AI/Agent 充当审批人或伪造审批证据；禁止无审批证据、空文件、符号链接或路径穿越获得 NEXT；禁止为了移交到下一阶段而要求尚未创建的未来文档；禁止开放阻断或过期例外 NEXT；禁止 blank-context 下根据一句“直接开发”跳过 L2/L3 前置阶段。
- **正例**：SRS checker 通过但业务参与者映射待确认，状态保持 ASK；确认、重检、人工审批并通过 `--through srs` 后才变为 NEXT，不提前要求 TDD/Plan。
- **反例**：AI 自检无问题，最终动作 NEXT。错误原因：缺少外部门禁和责任审批。
- **机器判定**：`LIFE-GATE-040` 按 `--through` 重新运行截至当前阶段的校验，检查 `APPROVED/NEXT`、非 AI 审批人、本地审批证据存在且非空、无开放阻断和连续风险链路；URL 证据只做格式校验，真实性由受保护评审负责；最终模式检查完整四阶段；测试包含分阶段正例、缺失审批文件和 blank-context L2 缺阶段反例。
