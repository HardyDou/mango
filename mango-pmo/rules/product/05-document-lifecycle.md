# 产品文档生命周期与移交规范

本文件是 `FULL` 模式启用适用 BRD、SRS、TDD、Plan 后，文档审批、摘要、追踪和阶段移交的唯一规范源。`SIMPLE` 不进入本生命周期，`STANDARD` 使用一个标准交付记录；模式选择以交付模式规范为准，本文件不复制其正文。

## 文档创建版本兼容性

- **目的**：允许合同语义未变化时保留可追溯的历史文档版本，同时防止新文档借旧版本绕过当前合同。
- **正向要求**：新建或迁移后的生命周期文档必须使用其合同 `metadata.fixed.pmoVersion`。单文档 checker 始终按该当前版本检查。文档集合 checker 仅可接受合同 `metadata.historicalPmoVersions` 中明确列出的同 schema 历史版本，且业务文档根目录的 `.mango-pmo-legacy-documents.json` 必须逐文件锁定相对路径、SHA-256、`pmoVersion` 和迁移原因；结构按当前合同及其显式声明的精确历史章节变体检查，审批、上游 ID 和 SHA-256 摘要仍全部执行。
- **禁止项**：禁止把任意旧版本、未来版本或未在合同声明的版本视为历史兼容；禁止因为文档版本兼容而跳过生命周期阶段顺序、上游摘要或审批门禁；禁止为新建文档选择历史版本或手工伪造历史版本基线。
- **正例**：PMO `1.3.15` 的合同仍使用 schema revision `1`，显式声明 `1.3.6` 至 `1.3.14` 为历史版本；`mango pmo upgrade` 为升级前已有且内容未变的历史 BRD/SRS/TDD/Plan 写入哈希版本基线，集合检查按版本声明的精确历史章节变体通过，模板和单文档 checker 则继续创建和校验 `1.3.15` 文档。
- **反例**：把新 BRD 写成 `pmoVersion: 1.3.6` 却没有升级生成的基线，或把 `1.3.5` 当作历史兼容版本。错误原因：前者没有受控历史证据，后者未获得当前合同的兼容声明。
- **机器判定**：`pin-historical-pmo-version-documents.mjs` 在升级前内容上生成历史版本基线；`check-document-set.mjs` 只在路径、基线版本和 SHA-256 均匹配时开启合同声明的历史版本与精确章节变体，输出实际命中的历史版本文档；`check-*-requirements.mjs` 和模板继续要求当前合同版本。

## LIFE-RISK-001 L0-L3 风险分级

- **目的**：保留需求影响和解决方案风险事实，并据此确定默认交付模式和审查强度。
- **正向要求**：风险等级及判定口径以 `mango-pmo/rules/09-test-case-automation-flow.md` 为唯一源；`L0/L1` 使用 SIMPLE，`L2` 使用 STANDARD，`L3` 使用 FULL。FULL 产品变更进入适用文档链；治理、发布等非产品任务使用专用完整记录，不伪造产品文档。BRD 记录需求影响预评，SRS 记录系统影响预评，TDD 按 `max(requirementImpactLevel, solutionRiskLevel)` 记录最终风险，Plan 继承 TDD。
- **禁止项**：禁止仅以代码行数、文件数量、关键词或“看起来简单”降级；禁止只评需求不评解决方案；禁止 SIMPLE 生成阶段文档、STANDARD 拆成四文档、FULL 跳过适用完整流程；禁止为非产品任务伪造产品文档。
- **正例**：L3 仓库治理变更进入 FULL 治理流程并使用治理记录、计划、策略测试和复核；跨租户产品变更进入 FULL 产品文档链和真实入口验证。
- **反例**：TDD 因为最终只改一个方法，把 SRS 的 L2 降为 L1。错误原因：方案简单不能消除已经确认的影响和失败后果。
- **机器判定**：`--mode` 显式传入交付模式；CLI 未传时按风险得到最低模式。检查模式不得低于风险基线，SIMPLE/STANDARD 不得携带四阶段产品文档，FULL 产品流程默认检查截至当前移交点的全部阶段，并检查相邻阶段风险单调不降和 TDD/Plan 最终等级一致。

## LIFE-ORDER-010 固定阶段顺序

- **目的**：确保 FULL 产品文档按真实依赖逐层收敛，后续文档不能代替或反向污染已确认的上游决定。
- **正向要求**：FULL 产品流程按 BRD -> SRS -> TDD -> Plan 顺序；只对任务不适用的阶段使用受控 `NONE` 并引用模式基线中的事实来源。发现缺口回到拥有该决定的阶段修订，再执行受影响门禁。
- **禁止项**：禁止跳过 SRS 直接由 BRD 生成 API；禁止在 Plan 新增设计；禁止下游文档反写上游事实而不重新审批；禁止同时把多个阶段内容塞入旧 PRD。
- **正例**：SRS 发现业务规则缺少拒绝边界时执行 ASK，修订并批准 BRD 后重新生成 SRS。
- **反例**：在 TDD 中补一个“默认业务规则”继续开发。错误原因：越权且上游无法追踪。
- **机器判定**：`LIFE-ORDER-010` 按模式基线中的适用阶段检查 `documentType`、顺序和相邻 `upstreamDocumentId`；FULL 产品流程未显式缩小适用阶段时默认要求完整链，使用 `--required-stages` 缩小时必须通过 `--applicability-evidence` 提供存在且非符号链接的外部证据文件，不再把空集合、任意人工选择或正文自证视为通过条件。

## LIFE-HASH-020 上游摘要与失效

- **目的**：用内容摘要证明下游基于哪个不可变上游版本，防止审批后静默修改。
- **正向要求**：下游元数据记录上游完整文件的 SHA-256；生命周期校验现场重新计算；上游任何变化都使下游 `STALE/BLOCKED`，必须重新审查受影响链路。
- **禁止项**：禁止使用文件名、分支名、“最新版”或人工版本描述代替摘要；禁止摘要不一致仍保留 NEXT；禁止只更新摘要而不评估内容变化。
- **正例**：BRD 修订后，旧 SRS 的摘要校验失败，编排器阻断 TDD 和 Plan。
- **反例**：只改了一个验收描述，不影响设计，所以继续。错误原因：影响判断尚未经过重新评审。
- **机器判定**：`LIFE-HASH-020` 计算原始 UTF-8 文件字节 SHA-256，与下游元数据严格比较；不一致报告上下游文档 ID。

## LIFE-TRACE-030 双向追踪

- **目的**：保证所有上游要求被下游承接，且所有下游要求、设计和任务都有合法来源。
- **正向要求**：合同声明每阶段本地定义 ID 和追踪章节；移交时检查上游所有可追踪 ID 至少被下游矩阵引用，并检查下游引用无未知上游 ID；例外必须有规则 ID、范围、审批和期限。
- **禁止项**：禁止静默遗漏、孤儿下游项、自然语言替代 ID；禁止一个总括项覆盖多个独立验收；禁止把空矩阵判定为通过。
- **正例**：`BAC-001 -> SAC-001 -> API-001/TC-001 -> TASK-001/VAL-001`。
- **反例**：需求均已覆盖。错误原因：无法证明覆盖关系。
- **机器判定**：`LIFE-TRACE-030` 从各阶段合同指定的定义表提取 ID，从下游追踪章节提取上游 ID，执行集合全覆盖和未知引用检查。

## LIFE-GATE-040 STOP、ASK、WRITE 与 NEXT

- **目的**：把 Agent 动作变成外部可验证状态，而非正文中的自我声明。
- **正向要求**：模式或关键事实无法确定时为 `ASK`；FULL 要求的文档信息或适用上游缺失为 `STOP`；可继续编写但未满足移交为 `WRITE`；只有该文档 checker、适用 handoff、阻断关闭和指定人工审批全部通过时由编排器写入 `NEXT`。
- **禁止项**：禁止 Agent 或作者仅修改正文为 PASS/NEXT；禁止 AI/Agent 充当审批人或伪造审批证据；禁止无审批证据、空文件、符号链接或路径穿越获得 NEXT；禁止开放阻断或过期例外 NEXT；禁止 blank-context 下缺少风险事实仍猜测模式。
- **正例**：SRS checker 通过但业务参与者映射待确认，状态保持 ASK；确认、重检、人工审批并通过 `--through srs` 后才变为 NEXT，不提前要求 TDD/Plan。
- **反例**：AI 自检无问题，最终动作 NEXT。错误原因：缺少外部门禁和责任审批。
- **机器判定**：`LIFE-GATE-040` 对 FULL 要求的文档重新运行适用校验，检查 `APPROVED/NEXT`、非 AI 审批人、本地审批证据、开放阻断和风险关系；测试覆盖 FULL 治理不伪造产品文档、跨租户产品任务进入完整链、风险降级和缺失审批证据等反例。
