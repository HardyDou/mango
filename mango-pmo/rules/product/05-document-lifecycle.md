# 产品文档生命周期与移交规范

本文件是用户确认启用 BRD、SRS、TDD、Plan 后，文档审批、摘要、追踪和阶段移交的唯一规范源。四份文档的章节内容分别由同目录 `01` 至 `04` 规范约束；保障措施的事实触发条件和人工确认以交付保障措施目录为准，本文件不复制其正文。

## LIFE-RISK-001 L0-L3 风险分级

- **目的**：保留需求影响和解决方案风险事实，用于说明影响与审查强度；风险等级不选择文档或其它保障措施。
- **正向要求**：风险等级及判定口径以 `mango-pmo/rules/09-test-case-automation-flow.md` 为唯一源；元数据只记录 `riskLevel` 和 `riskAssessmentEvidence`。AI 根据固定保障措施目录中的事实触发条件提出建议，说明价值、成本和跳过影响，并通过 Ask User 由用户确认采用哪些措施。只有用户启用的文档进入本生命周期；BRD 记录需求影响预评，SRS 记录系统影响预评，TDD 按 `max(requirementImpactLevel, solutionRiskLevel)` 记录最终风险，用户同时启用 TDD 和 Plan 时 Plan 继承 TDD。
- **禁止项**：禁止仅以代码行数、文件数量、关键词或“看起来简单”降级；禁止只评需求不评解决方案；禁止用 L0-L3 自动增加或删除 BRD、SRS、TDD、Plan；禁止 AI 代替用户确认措施；禁止用低风险结论回避已经由事实触发并经用户启用的保障措施。
- **正例**：L3 仓库治理变更触发治理记录、策略测试、远端状态回读和人工验收，用户未启用产品文档，因此不生成 BRD/SRS/TDD/Plan；跨租户业务变更触发业务、系统、技术和真实入口验证等相关措施，AI 说明理由后等待用户逐项确认。
- **反例**：TDD 因为最终只改一个方法，把 SRS 的 L2 降为 L1。错误原因：方案简单不能消除已经确认的影响和失败后果。
- **机器判定**：`LIFE-RISK-001` 只对用户启用并传入的文档检查风险证据、相邻阶段风险单调不降和已选择 TDD/Plan 的最终等级一致；禁止根据 L0-L3 推导必选文档。

## LIFE-ORDER-010 固定阶段顺序

- **目的**：确保用户启用的产品文档按其真实依赖逐层收敛，后续文档不能代替或反向污染已确认的上游决定。
- **正向要求**：用户启用多个相邻产品文档时按 BRD -> SRS -> TDD -> Plan 顺序；下游引用已确认相邻上游的唯一 ID 和摘要。相邻上游未启用时，下游使用受控 `NONE` 并引用保障基线中的目标与事实来源；发现缺口回到拥有该决定的文档或确认基线修订，再重新执行受影响门禁。未启用的文档不得为补齐形式而生成。
- **禁止项**：禁止跳过 SRS 直接由 BRD 生成 API；禁止在 Plan 新增设计；禁止下游文档反写上游事实而不重新审批；禁止同时把多个阶段内容塞入旧 PRD。
- **正例**：SRS 发现业务规则缺少拒绝边界时执行 ASK，修订并批准 BRD 后重新生成 SRS。
- **反例**：在 TDD 中补一个“默认业务规则”继续开发。错误原因：越权且上游无法追踪。
- **机器判定**：`LIFE-ORDER-010` 按用户确认的文档集合检查 `documentType`、顺序和适用的相邻 `upstreamDocumentId`；未启用文档不因风险等级缺失而失败。

## LIFE-HASH-020 上游摘要与失效

- **目的**：用内容摘要证明下游基于哪个不可变上游版本，防止审批后静默修改。
- **正向要求**：下游元数据记录上游完整文件的 SHA-256；生命周期校验现场重新计算；上游任何变化都使下游 `STALE/BLOCKED`，必须重新审查受影响链路。
- **禁止项**：禁止使用文件名、分支名、“最新版”或人工版本描述代替摘要；禁止摘要不一致仍保留 NEXT；禁止只更新摘要而不评估内容变化。
- **正例**：BRD 修订后，旧 SRS 的摘要校验失败，编排器阻断 TDD 和 Plan。
- **反例**：只改了一个验收描述，不影响设计，所以继续。错误原因：影响判断尚未经过重新评审。
- **机器判定**：`LIFE-HASH-020` 计算原始 UTF-8 文件字节 SHA-256，与下游元数据严格比较；不一致报告上下游文档 ID。

## LIFE-TRACE-030 双向追踪

- **目的**：保证所有上游要求被下游承接，且所有下游要求、设计和任务都有合法来源。
- **正向要求**：合同声明每阶段本地定义 ID 和追踪章节；移交时检查上游所有可追踪 ID 至少被下游矩阵引用，并检查下游引用无未知上游 ID；例外必须有规则 ID、范围、审批和期限。
- **禁止项**：禁止静默遗漏、孤儿下游项、自然语言替代 ID；禁止一个总括项覆盖多个独立验收；禁止把空矩阵判定为通过。
- **正例**：`BAC-001 -> SAC-001 -> API-001/TC-001 -> TASK-001/VAL-001`。
- **反例**：需求均已覆盖。错误原因：无法证明覆盖关系。
- **机器判定**：`LIFE-TRACE-030` 从各阶段合同指定的定义表提取 ID，从下游追踪章节提取上游 ID，执行集合全覆盖和未知引用检查。

## LIFE-GATE-040 STOP、ASK、WRITE 与 NEXT

- **目的**：把 Agent 动作变成外部可验证状态，而非正文中的自我声明。
- **正向要求**：保障措施尚未由用户确认时为 `ASK`；用户启用的文档信息或适用上游缺失为 `STOP`；可继续编写但未满足移交为 `WRITE`；只有该文档 checker、适用 handoff、阻断关闭和指定人工审批全部通过时由编排器写入 `NEXT`。本地 `approvalEvidence` 必须引用文档工作区内真实、非空的普通文件；分阶段 handoff 只检查用户启用且截至当前阶段的文档。
- **禁止项**：禁止 Agent 或作者仅修改正文为 PASS/NEXT；禁止 AI/Agent 充当审批人或伪造审批证据；禁止无审批证据、空文件、符号链接或路径穿越获得 NEXT；禁止要求用户未启用的未来文档；禁止开放阻断或过期例外 NEXT；禁止 blank-context 下按风险等级自行选择流程或文档。
- **正例**：SRS checker 通过但业务参与者映射待确认，状态保持 ASK；确认、重检、人工审批并通过 `--through srs` 后才变为 NEXT，不提前要求 TDD/Plan。
- **反例**：AI 自检无问题，最终动作 NEXT。错误原因：缺少外部门禁和责任审批。
- **机器判定**：`LIFE-GATE-040` 对用户启用的文档重新运行适用校验，检查 `APPROVED/NEXT`、非 AI 审批人、本地审批证据存在且非空、无开放阻断和适用风险关系；URL 证据只做格式校验，真实性由受保护评审负责；测试覆盖 L3 治理不自动生成四文档、跨租户任务等待用户确认、风险降级和缺失审批证据等反例。
