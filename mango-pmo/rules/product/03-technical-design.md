# 技术设计文档规范

本文件是技术设计文档（TDD）的唯一文档规范源。可执行投影位于 `mango-pmo/contracts/technical-design.json`，其中只能引用本文件的 `ruleId`。正式文档使用 `mango-pmo/templates/technical-design.md`。

技术设计回答系统如何实现已确认目标。用户同时启用 SRS 时承接已批准 SRS；未启用 SRS 时以用户确认的保障基线、目标和可引用事实为设计来源，不为补齐链路生成 SRS。Java、API、模块、数据库、安全和测试的长期细则仍以对应 `mango-pmo/rules/backend/**`、`frontend/**` 和测试规则为唯一源；本文只要求设计逐项引用和落实，不复制这些规则正文。

## TDD-REF-005 参考资料与代码基线

- **目的**：追踪设计实际采用的代码模板、源码事实和规范来源，不把引用变成开工前全文阅读要求。
- **正向要求**：至少登记类型、路径或模板 ID、版本或提交、用途和实际采用范围；新增代码优先引用 `code-templates/index.json` 中的模板版本。
- **禁止项**：禁止只写“参考现有代码”；禁止把旧项目代码登记为结构和编码规范来源；禁止因为文档列出参考资料就要求 Agent 批量全文读取。
- **正例**：登记 `business-module@1` 用于新增模块骨架，当前目标模块源码仅用于确认接口和兼容事实，并写明实际采用到 API、core、starter 和前端包。
- **反例**：写“参考现有模块和全部规范”。错误原因：没有可验证的模板身份、版本、用途和采用范围，还会把旧代码误当成规范来源。
- **机器判定**：`TDD-REF-005` 检查参考资料表存在且至少一行；模板 ID 和版本由 code baseline checker 验证。

## TDD-SEC-001 文档控制与上游基线

- **目的**：固定设计身份、风险等级、适用来源摘要、设计责任和审批状态。
- **正向要求**：填写唯一 `documentId`、固定 `documentType: technical-design`、PMO/结构版本、`riskLevel` 及证据、状态动作、责任人与审批证据；`riskLevel` 必须等于需求影响和方案风险最大值。FULL 产品流程存在 SRS 时引用其 ID 和 SHA-256；不适用 SRS 时使用 `NONE` 并引用模式基线。
- **禁止项**：禁止基于“最新版需求”设计；禁止适用来源变化后沿用旧审批；禁止只按需求或代码量定级；禁止省略解决方案风险；禁止用户已启用 TDD 后绕过设计门禁；禁止为形成上游而擅自生成未启用 SRS。
- **正例**：`TDD-ANN-001` 记录系统影响 L1、共享数据迁移方案风险 L2，因此 `riskLevel: L2`，并引用 `SRS-ANN-001` 的完整摘要和评审证据。
- **反例**：需求已口头确认，直接按代码现状设计。错误原因：没有稳定上游和风险门禁。
- **机器判定**：`TDD-META-001` 检查元数据、风险枚举、上游 ID/摘要、状态动作和占位符；生命周期检查器在 SRS 已启用时验证摘要和阶段顺序，未启用时要求受控 `NONE`。

## TDD-SEC-010 设计输入、约束与决策

- **目的**：登记设计所依据的 SRS、当前代码事实、长期规范和用户确认，并记录关键决策及取舍。
- **正向要求**：决策使用 `DEC-xxx`；写问题、候选方案、选择、理由、来源 ID/路径、影响、风险和回退条件；来源可以是已启用 SRS、用户确认的保障基线、当前代码事实或长期规范；推断必须显式标记并说明证据。
- **禁止项**：禁止把假设写成事实；禁止没有候选方案和来源的“采用最佳实践”；禁止在设计中创造新业务目标；禁止以历史文档覆盖当前代码和规范。
- **正例**：`DEC-001` 比较复用既有审核能力与新增独立能力，选择复用并引用 `FR-003`、当前模块 README 和模块规则。
- **反例**：按经验使用微服务更先进。错误原因：没有需求来源、事实和影响分析。
- **机器判定**：`TDD-STRUCT-010` 检查决策表、至少一行和必填值；`TDD-ID-010` 检查 `DEC-xxx` 唯一；来源引用必填。

## TDD-SEC-020 模块与依赖边界

- **目的**：把系统要求分配到明确模块和职责层，证明依赖方向符合 Mango 模块规范。
- **正向要求**：模块设计项使用 `MOD-xxx`；登记模块/包、职责、改动类型、依赖方向、公开能力、对应 SRS ID、适用规范 ruleId 和验证方式；涉及 api/core/starter/starter-remote 时必须逐层说明责任。
- **禁止项**：禁止只有文件清单没有职责；禁止反向依赖、跨域耦合或把业务实现放入 API 契约层；禁止在本文重写模块长期规则。
- **正例**：`MOD-001` 明确 API 层仅承载公开契约，core 承载领域实现，并引用模块规范的实际 ruleId 和验证入口。
- **反例**：所有代码放入 starter，方便依赖。错误原因：未分析职责和依赖边界。
- **机器判定**：`TDD-STRUCT-020` 检查模块表、`MOD-xxx` 唯一、SRS 来源和规范 ruleId 必填；真实依赖合规由代码侧架构检查器验证。

## TDD-SEC-030 技术对象与状态模型

- **目的**：把逻辑数据、业务对象和状态需求映射为技术模型、关系、状态编码及一致性边界。
- **正向要求**：模型设计项使用 `DM-xxx`；写对应 `BO/DR/FR`、模型职责、标识、关系、状态编码、审计/历史、归属/租户和一致性约束；状态流转写当前状态、触发、目标状态、前置条件、副作用和失败处理。
- **禁止项**：禁止只列 Entity 字段；禁止引入 SRS 不存在的状态和业务规则；禁止只有状态枚举没有流转；禁止忽略历史、审计或归属。
- **正例**：`DM-001` 将公告与审核决定分为主对象和不可变历史记录，逐项映射 `DR-001/DR-002`。
- **反例**：建一个大表保存所有信息。错误原因：没有关系、生命周期和一致性分析。
- **机器判定**：`TDD-STRUCT-030` 检查模型表与状态流转表、`DM-xxx` 唯一、来源引用和必填值；未知 SRS 引用由生命周期检查器报告。

## TDD-SEC-040 系统流程、事务与一致性

- **目的**：将 UC/FR/BR 展开为组件协作、事务边界、幂等、并发和失败补偿设计。
- **正向要求**：流程设计使用 `FLOW-xxx`；写调用入口、参与模块、处理顺序、事务起止、状态变化、幂等键、并发策略、外部失败、补偿和用户可见结果；引用对应 SRS ID。
- **禁止项**：禁止只有成功时序；禁止跨远程调用持有本地事务而不说明风险；禁止吞异常或固定成功；禁止把未确认业务规则嵌入流程。
- **正例**：`FLOW-001` 说明提交与状态更新在同一事务，外部通知异步执行，失败不回滚业务决定但形成可重试记录和用户反馈。
- **反例**：调用各服务，异常时重试。错误原因：事务、幂等、次数、结果和补偿均不明确。
- **机器判定**：`TDD-STRUCT-040` 检查流程表、`FLOW-xxx` 唯一及事务/失败字段；语义正确性由 Tech Lead 评审和实现测试验证。

## TDD-SEC-050 API 与远程契约设计

- **目的**：把系统行为映射为公开 API、Controller 入口和远程调用契约，并明确参数、响应、校验、错误和兼容性。
- **正向要求**：接口使用 `API-xxx`；逐项写对应 SRS ID、调用方、所属模块、入口类型、方法与路径、Command/Query/VO、返回契约、校验、权限/租户、幂等/分页、错误码、兼容策略、适用 API 规范 ruleId 和验证方式。
- **禁止项**：禁止无来源接口；禁止用 Entity 作为公开契约；禁止只给路径不写边界；禁止在本文另立 Controller、Feign、`R`、`Require` 或路径参数规则，必须引用后端 API 唯一规范并交由专用检查器判定。
- **正例**：`API-001` 映射 `FR-001/SAC-001`，完整登记契约结构、校验、错误和 `backend/03-api.md` 的适用 ruleId。
- **反例**：提供一个通用 CRUD 接口即可。错误原因：无法追溯功能行为，也没有契约和异常边界。
- **机器判定**：`TDD-STRUCT-050` 检查 API 表、`API-xxx` 唯一、来源/规范/验证字段；API 细则由后端 API 文档检查和代码静态门禁执行，本文不复制其模式。

## TDD-SEC-060 持久化与数据迁移设计

- **目的**：定义表、字段、约束、索引、Entity/Mapper 映射、租户审计、初始化、迁移、回填和回滚。
- **正向要求**：持久化项使用 `DB-xxx`；引用 `DM/DR/FR`，写表/实体、字段变化、约束、索引、租户审计、Mapper 边界、数据来源、migration、回填、回滚/补偿和适用数据库/持久化 ruleId。
- **禁止项**：禁止无逻辑需求来源建表；禁止只给 DDL 不说明对象和迁移；禁止绕过租户、审计或 MangoCrudService 基线而无批准例外；禁止复制数据库长期规则。
- **正例**：`DB-001` 说明新增审核历史表的来源、唯一约束、租户字段、回填不适用依据、migration 和回滚验证。
- **反例**：新增表，字段见 SQL。错误原因：缺少追踪、约束、迁移和边界设计。
- **机器判定**：`TDD-STRUCT-060` 检查数据表、`DB-xxx` 唯一、来源、迁移/回滚和规范引用；具体 DDL/Mapper/Entity 合规由数据库和持久化检查器验证。

## TDD-SEC-070 安全、权限、租户与数据边界

- **目的**：把 SA/FR/DR 的行为边界落为认证、权限资源、默认授权、租户隔离、数据权限和后端强制校验。
- **正向要求**：安全项使用 `SEC-xxx`；写来源、能力、权限资源、默认授权、后端校验入口、租户边界、数据归属断言、前端反馈、审计和验证方式；引用安全规范 ruleId。
- **禁止项**：禁止只隐藏按钮不做后端校验；禁止信任前端传入租户或归属；禁止用超级管理员绕过验收；禁止复制长期安全规则。
- **正例**：`SEC-001` 明确审核操作的前后端边界、租户归属断言、无权限反馈和跨租户反例验证。
- **反例**：前端无按钮即可保证安全。错误原因：没有服务端强制边界。
- **机器判定**：`TDD-STRUCT-070` 检查安全表、`SEC-xxx` 唯一和必填验证；真实安全行为由代码和测试门禁验证。

## TDD-SEC-080 错误码、异常与可观测性

- **目的**：将失败/禁止/边界结果映射为稳定错误语义、日志、指标、审计和用户反馈。
- **正向要求**：错误项使用 `ERR-xxx`；引用 `SAC/FR/BR`，写失败场景、触发、错误码、异常类型、用户反馈、日志上下文、指标/告警、重试/补偿和敏感信息处理；引用错误处理规范来源。
- **禁止项**：禁止 catch 后吞异常、返回固定成功或只写“系统异常”；禁止日志包含密码/token/敏感正文；禁止错误码无业务语义或无来源。
- **正例**：`ERR-001` 将状态冲突映射为稳定业务错误、明确用户动作建议，并记录对象 ID、原状态和请求追踪标识。
- **反例**：捕获 Exception 后返回 `R.success()`。错误原因：掩盖失败并违反交付红线。
- **机器判定**：`TDD-STRUCT-080` 检查错误表、`ERR-xxx` 唯一、来源、反馈与可观测字段；实现合规由 Java 静态和测试门禁验证。

## TDD-SEC-090 前端结构与交互实现映射

- **目的**：把 PG/BT/字段/状态要求映射为页面 key、路由、组件责任、状态管理、API 依赖和语义测试锚点。
- **正向要求**：前端设计项使用 `UI-xxx`；写 SRS 来源、页面/动作、页面 key/路由、区域与组件、状态来源、API、权限/不可操作、空/加载/失败态、语义锚点、复用判断和前端规范 ruleId。
- **禁止项**：禁止遗漏 SRS 页面状态；禁止为单页普通控件强造公共组件；禁止只有视觉稿没有数据和错误状态；禁止复制前端长期规则。
- **正例**：`UI-001` 映射 `PG-001/BT-001`，说明页面状态、API 依赖、不可操作原因和 `data-action` 语义锚点。
- **反例**：做一个好看的标准列表页。错误原因：无来源、无行为和状态设计。
- **机器判定**：`TDD-STRUCT-090` 检查前端映射表、`UI-xxx` 唯一和必填值；真实 UI 合规由前端检查与视觉验收验证。

## TDD-SEC-100 测试设计与验收映射

- **目的**：为每个 SAC 选择合适测试层级、数据、稳定契约、执行入口和证据，不在本文复制测试规则。
- **正向要求**：测试用例使用 `TC-xxx`；引用 SAC 和设计项，写场景、优先级、层级、自动化判断、测试数据、权限/租户边界、稳定契约、执行入口、证据和失败处理；引用测试流程 ruleId/路径。
- **禁止项**：禁止所有场景默认 E2E；禁止接口 200、页面打开或截图有画面作为完整断言；禁止没有隔离数据和证据；禁止复制测试规则正文。
- **正例**：`TC-001` 用 API 测试状态冲突，用 E2E 验证审核员可见结果，并分别登记数据和证据。
- **反例**：写几个单测覆盖即可。错误原因：没有 SAC 映射、层级选择和业务断言。
- **机器判定**：`TDD-STRUCT-100` 检查测试表、`TC-xxx` 唯一、SAC/设计项引用和必填值；测试规则细节由对应测试门禁执行。

## TDD-SEC-110 兼容与已启用能力说明影响

- **目的**：识别兼容、升级和用户已启用 M08 时的能力说明影响；发布、版本、制品和发布恢复保持独立。
- **正向要求**：存在适用影响时使用 `IMP-xxx`；写影响对象、当前行为、目标行为、兼容策略、升级/补偿、已启用能力说明、验证和责任人。
- **禁止项**：禁止由 M05 自动启用 M08；禁止把发布批次或发布恢复写进 TDD；禁止把实现计划写进本章；禁止重复能力文档规则。
- **正例**：`IMP-001` 明确 API 契约兼容、业务项目升级步骤、README 和版本化验证责任。
- **反例**：仅内部调整，无需说明。错误原因：没有证据判断是否真的不影响消费者。
- **机器判定**：`TDD-STRUCT-110` 只检查实际存在的兼容/能力说明影响；M08=`ENABLE` 时才执行能力文档专项 checker，发布走独立流程。

## TDD-SEC-120 技术追踪矩阵

- **目的**：证明所有适用来源要求有设计和测试承接，所有设计项都有合法来源。
- **正向要求**：逐项登记来源 ID/路径、设计项 ID、测试用例 ID 和覆盖说明；存在 SRS 时覆盖其全部可追踪项，不适用时覆盖模式基线目标和事实；始终覆盖所有本地设计项。
- **禁止项**：禁止孤儿设计；禁止用一个主流程覆盖多个 SAC；禁止引用不存在 ID；禁止将未设计项默认为不适用。
- **正例**：`FR-001, PG-001, SAC-001 -> API-001, DB-001, UI-001 -> TC-001`。
- **反例**：需求均已设计，测试后补。错误原因：无法开发和验收闭环。
- **机器判定**：`TDD-TRACE-120` 检查本地 ID 全覆盖、引用存在和无孤儿；存在 SRS 时检查上游全覆盖，不适用时不得伪造 SRS 引用。

## TDD-SEC-130 阶段判定与审批

- **目的**：结合风险等级、设计校验、规范专项检查和 Tech Lead 审批决定 TDD 自身是否批准；是否启用实施计划由 M06 单独建议并由用户确认。
- **正向要求**：FULL 要求独立 TDD 或用户显式升档后，登记 checker、handoff、专项检查、阻断/例外、风险和审批证据；全部通过才允许 `NEXT`。
- **禁止项**：禁止 AI 自报 PASS；禁止以“可编码”替代设计完整性；禁止 AI 因 L2/L3 自动生成 TDD 或补齐产品文档；禁止用户已启用 TDD 后跳过适用上游、设计审批或未经授权的永久例外。
- **正例**：TDD 与生命周期检查通过，适用 API/模块/数据库规则均有验证计划，Tech Lead 批准后由编排器更新状态。
- **反例**：代码结构很简单，直接开发。错误原因：复杂度和风险未经门禁判定。
- **机器判定**：`TDD-GATE-130` 检查门禁表、风险和元数据一致；生命周期检查器验证 FULL 要求的 TDD 及适用上游、摘要、追踪和审批。

## TDD-BOUNDARY-001 阶段边界

- **目的**：允许完整技术设计，同时阻止重新定义业务需求或提前伪造实施结果。
- **正向要求**：每个技术结论必须引用适用 SRS、模式基线、当前事实、人工决定或长期规范；任务拆解在 FULL 进入 Plan，STANDARD 写入单文件，测试结果进入验证证据。
- **禁止项**：禁止新增无来源业务目标、参与者、业务规则或系统功能；禁止宣称未执行的代码、测试、发布已完成；禁止在 TDD 复制后端、前端和测试长期规则正文。
- **正例**：设计新增 API 是为了落实 `FR-001/SAC-001`，并引用后端 API 规则和后续验证入口。
- **反例**：设计时顺便增加批量发布功能。错误原因：新增了 SRS 未批准范围。
- **机器判定**：合同检查上游引用、必填来源和禁止完成态措辞；业务范围语义与技术正确性由系统分析负责人和 Tech Lead 联合评审。
