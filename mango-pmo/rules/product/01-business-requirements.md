# 业务需求说明书规范

本文件是业务需求说明书（BRD）的唯一规范源。适用于 Mango 主仓能力和基于 Mango 的业务项目。可执行投影位于 `mango-pmo/contracts/business-requirements.json`，其中只能引用本文件的 `ruleId`，不得新增规则。正式文档使用 `mango-pmo/templates/business-requirements.md`。

业务需求说明书只回答为什么做、为谁做、业务上做什么以及怎样判断业务结果成立。菜单、页面、字段、按钮、接口、数据库、模块和实现方案属于后续阶段。

## BRD-SEC-001 文档控制

- **目的**：固定文档身份、所用 PMO 版本、结构修订、责任人与阶段状态，使文档可追溯且可判定是否允许移交。
- **正向要求**：填写唯一 `documentId`、固定 `documentType: business-requirements`、`pmoVersion`、`schemaRevision`、`riskLevel`、`riskAssessmentEvidence`、`status`、`action`、负责人、审批人和审批证据；BRD 的 `riskLevel` 只表示需求影响预评，证据只使用业务影响和失败后果，不假定实现方案；风险口径引用统一测试流程规则；BRD 没有上游文档，两个上游字段填写 `NONE`。
- **禁止项**：禁止缺失元数据；禁止把 `NEXT` 当作作者声明；禁止在没有审批证据时标记 `APPROVED`；禁止填写模板占位符后提交。
- **正例**：`documentId: BRD-ANN-001`，`status: APPROVED`，`action: NEXT`，审批证据指向已确认的评审记录。
- **反例**：只在正文写“需求已确认，可以开发”。错误原因：没有稳定文档身份、结构版本和可校验审批证据。
- **机器判定**：`BRD-META-001` 检查元数据键、固定值、ID/版本格式、状态动作组合、`NONE` 上游和占位符；`NEXT` 仅在 `APPROVED` 且审批信息完整时允许。

## BRD-SEC-010 业务背景与问题

- **目的**：说明当前业务现状、待解决问题、受影响对象和问题证据，不提前给出系统方案。
- **正向要求**：每个问题使用 `BP-xxx`；写清现状、问题、影响对象、影响程度和事实来源；事实与判断分开表达。
- **禁止项**：禁止写页面改版、接口新增、数据库调整或技术组件；禁止只写“体验不好”“效率低”等无证据结论；禁止把解决方案伪装成问题。
- **正例**：`BP-001`：公告审核依赖线下消息确认，运营人员无法判断当前责任人，近三个月有 18 次超过约定时限。
- **反例**：`BP-001`：缺少公告审核接口，需要增加 Controller。错误原因：描述的是技术方案，不是业务问题。
- **机器判定**：`BRD-STRUCT-010` 检查章节唯一且问题表表头完整、至少一行、必填单元格非空；`BRD-ID-010` 检查 `BP-xxx` 唯一；边界词由 `BRD-BOUNDARY-001` 检查。

## BRD-SEC-020 业务目标与成功口径

- **目的**：把业务问题转化为可衡量目标，明确基线、目标值、统计周期和数据口径。
- **正向要求**：每个目标使用 `BG-xxx`，关联至少一个 `BP-xxx`；写明目标对象、当前基线、目标值、统计周期和统计口径；无法量化时必须给出可观察的完成条件。
- **禁止项**：禁止使用“优化、完善、提升体验、支持能力”作为完整目标；禁止把上线接口、建表或完成编码当作业务成功；禁止没有基线或口径的百分比目标。
- **正例**：`BG-001`：公告审核平均业务处理时长由 2 个工作日降至 4 小时，以提交至最终业务决定的时间差按月统计。
- **反例**：`BG-001`：完成公告模块开发并优化性能。错误原因：是交付动作和技术表述，不能验证业务价值。
- **机器判定**：`BRD-STRUCT-020` 检查目标表结构、至少一行和必填值；`BRD-ID-020` 检查 `BG-xxx` 唯一；`BRD-TRACE-020` 检查来源 `BP-xxx` 格式及引用存在。

## BRD-SEC-030 范围与不处理范围

- **目的**：确定本次业务边界，防止遗漏、隐式扩展和用“后续处理”回避范围确认。
- **正向要求**：范围项使用 `BS-xxx`；分别登记纳入范围与不处理范围，写清业务能力、适用对象、业务场景和边界原因；不处理范围必须说明对本次目标是否有影响。
- **禁止项**：禁止出现菜单、页面、按钮、API、表、类或模块路径；禁止只写“其它不变”；禁止用“后续优化”代替明确边界。
- **正例**：`BS-001`：纳入运营人员提交公告、审核员作出审核决定以及发布后的撤回；不包含跨企业公告共享。
- **反例**：`BS-001`：新增公告列表页、编辑页和 `/api/announcements`。错误原因：越过业务边界进入系统和技术设计。
- **机器判定**：`BRD-STRUCT-030` 检查范围表、范围类型枚举和必填值；`BRD-ID-030` 检查 `BS-xxx` 唯一；`BRD-BOUNDARY-001` 检查技术内容。

## BRD-SEC-040 业务参与者与术语

- **目的**：统一业务语言，明确参与者承担的业务责任和不能执行的业务动作。
- **正向要求**：参与者使用 `BA-xxx`；写清业务身份、职责、参与场景、允许动作、禁止动作及业务原因；术语只解释业务含义、唯一主名称和必要别名。
- **禁止项**：禁止用系统角色码、权限码、账号类型或数据库字段定义参与者；禁止用 Controller、DTO、Entity 等技术词充当业务术语；禁止只列角色名不写职责边界。
- **正例**：`BA-001 运营人员`负责拟定并提交公告，不能作出最终审核决定，因为提交人与决定人需业务分离。
- **反例**：`ROLE_NOTICE_ADMIN` 拥有 `notice:publish` 权限。错误原因：这是授权实现，不是业务参与者职责。
- **机器判定**：`BRD-STRUCT-040` 检查参与者表和术语表均存在且有数据；`BRD-ID-040` 检查 `BA-xxx` 唯一；`BRD-BOUNDARY-001` 检查技术标识。

## BRD-SEC-050 关键业务对象与生命周期

- **目的**：定义业务关注的核心对象、识别口径、归属、数量/有效期边界和用户可理解的生命周期。
- **正向要求**：对象使用 `BO-xxx`；对象表写业务含义、唯一识别口径、归属和关键业务边界；状态表写状态含义、进入/退出条件、允许/禁止业务动作、是否可逆和是否终态。
- **禁止项**：禁止出现表名、字段名、数据类型、技术枚举或持久化策略；禁止只有状态名称没有进入/退出条件；禁止把页面字段清单当作业务对象。
- **正例**：`BO-001 公告`以所属企业、业务标题和创建时间共同识别；“已撤回”为不可逆终态，不能再次发布。
- **反例**：`notice_info.status` 使用 `VARCHAR(20)` 保存 `WITHDRAWN`。错误原因：属于数据和编码设计。
- **机器判定**：`BRD-STRUCT-050` 检查对象表与生命周期表、必填列及至少一行；`BRD-ID-050` 检查 `BO-xxx` 唯一；生命周期中的对象引用必须已定义。

## BRD-SEC-060 业务场景与流程

- **目的**：从参与者视角描述达成业务目标的主流程、替代流程、异常流程和终止条件。
- **正向要求**：流程使用 `BF-xxx`；写明父流程、目标、参与者、前置条件、用户业务动作、可观察业务结果、异常/终止分支和涉及规则；主流程父 ID 为 `NONE`，子流程引用已定义父流程。
- **禁止项**：禁止写服务调用、接口请求、消息队列、事务或算法步骤；禁止把系统内部处理写进用户动作；禁止只有成功主链路而没有失败、禁止和终止结果。
- **正例**：运营人员提交公告后，审核员作出通过或拒绝决定；超出处理时限进入升级处理分支，提交人可看到当前业务状态。
- **反例**：Controller 调用 Service 保存 Entity 后发送 MQ。错误原因：这是实现流程。
- **机器判定**：`BRD-STRUCT-060` 检查流程表结构和必填值；`BRD-ID-060` 检查 `BF-xxx` 唯一；`BRD-PARENT-060` 检查父流程存在、禁止自引用并检测循环；参与者、对象、规则引用必须格式正确。

## BRD-SEC-070 业务规则

- **目的**：定义允许、禁止、计算、状态变化、冲突优先级和例外的业务判断口径。
- **正向要求**：规则使用 `BR-xxx`；每条规则写适用参与者、触发条件、判断口径、允许结果、禁止/失败结果、业务反馈、状态影响、优先级和例外；规则必须被流程或验收项使用。
- **禁止项**：禁止只写规则名称；禁止用代码表达式、异常类、错误码或 SQL 代替业务判断；禁止由 AI 发明未确认阈值、状态和例外。
- **正例**：`BR-001`：公告只有在审核通过且仍处于有效期内时可发布；不满足时保持原状态并告知对应业务原因。
- **反例**：`Require.isTrue(status == 2, ErrorCode.NOTICE_001)`。错误原因：是代码和错误码实现，且没有业务口径。
- **机器判定**：`BRD-STRUCT-070` 检查规则表字段及必填值；`BRD-ID-070` 检查 `BR-xxx` 唯一；参与者、流程、对象引用必须存在；`BRD-BOUNDARY-001` 检查技术表达。

## BRD-SEC-080 业务约束、风险与待确认问题

- **目的**：显式记录法规、组织、时间、资源等业务约束，区分风险、假设和未确认问题。
- **正向要求**：条目使用 `BI-xxx`；标明类型、来源、影响范围、处理方式、责任人、截止时间和是否阻断；未确认内容只能留在本章，不能写成正式业务结论。
- **禁止项**：禁止用风险章节隐藏当前范围内必须完成的内容；禁止没有来源的假设；禁止阻断项未关闭仍进入下一阶段。
- **正例**：`BI-001`：法务尚未确认公告最长保留期，影响 `BR-003`，标记为阻断并指定确认人和日期。
- **反例**：接口性能以后再优化，不影响本次。错误原因：技术事项越界，且“以后”没有责任和期限。
- **机器判定**：`BRD-STRUCT-080` 检查风险表、类型/是否阻断枚举和必填值；`BRD-ID-080` 检查 `BI-xxx` 唯一；当存在未关闭阻断项时 `action` 不得为 `NEXT`。

## BRD-SEC-090 业务验收标准

- **目的**：用业务动作、前置业务条件和可观察业务结果判断需求是否达成。
- **正向要求**：验收项使用 `BAC-xxx`；每项引用 `BG/BO/BF/BR` 中至少一个来源，写业务场景、前置条件、业务动作、期望业务结果和失败/边界结果；一个独立业务结果一条验收项。
- **禁止项**：禁止以接口 200、页面打开、数据库有记录、测试通过或代码完成作为业务验收；禁止一个“主流程通过”覆盖多项独立结果；禁止只有成功结果。
- **正例**：`BAC-001`：合格公告经审核员通过后进入可发布状态；不合格公告保持未发布并记录拒绝原因。
- **反例**：`POST /api/notices` 返回 `R.success`。错误原因：验证的是技术响应，不是业务结果。
- **机器判定**：`BRD-STRUCT-090` 检查验收表和必填值；`BRD-ID-090` 检查 `BAC-xxx` 唯一；来源引用必须存在且至少一个；`BRD-BOUNDARY-001` 检查技术验收词。

## BRD-SEC-100 业务追踪矩阵

- **目的**：证明问题、目标、对象、流程、规则和业务验收之间双向可追溯，防止遗漏和孤儿要求。
- **正向要求**：每个已定义 `BP/BG/BS/BA/BO/BF/BR/BAC` 至少出现一次；写清来源 ID、关联 ID、业务验收 ID和覆盖说明；不适用必须给出已确认原因。
- **禁止项**：禁止只复制 ID 清单；禁止引用不存在的 ID；禁止有未覆盖业务项仍标记 READY；禁止用自然语言替代稳定 ID。
- **正例**：`BG-001 -> BF-001, BR-001 -> BAC-001`，覆盖说明指出如何验证处理时长目标。
- **反例**：目标均已覆盖，详见正文。错误原因：无法机器校验，也无法定位遗漏。
- **机器判定**：`BRD-TRACE-100` 检查矩阵表、所有本地 ID 全覆盖、引用存在、无重复定义和无孤儿验收项。

## BRD-SEC-110 阶段判定与审批

- **目的**：记录 checker 证据、未关闭阻断数和人工业务审批，决定是否可进入系统需求阶段。
- **正向要求**：填写 checker 命令与结果、阻断数、例外清单、审批结论和证据；只有 checker 通过、阻断为 0、业务负责人批准且文档未变化时才允许 `NEXT`。
- **禁止项**：禁止 AI 自评代替 checker；禁止用正文中的 PASS 绕过外部门禁；禁止无审批证据进入系统需求；禁止把 `EXCEPTION` 当作默认通过。
- **正例**：记录检查命令、0 个阻断、业务负责人审批记录，元数据由编排器更新为 `APPROVED/NEXT`。
- **反例**：AI 自检全部 PASS，最终动作 NEXT。错误原因：自报结果没有外部证据和责任人审批。
- **机器判定**：`BRD-GATE-110` 检查门禁表必填值与元数据一致；外部生命周期检查器重新执行文档校验并验证审批和摘要。

## BRD-BOUNDARY-001 阶段边界

- **目的**：阻止业务需求说明书跨越到系统需求、技术设计或实施计划。
- **正向要求**：只使用业务语言描述目标、对象、流程、规则和业务结果；系统呈现需求移交 SRS，技术实现移交 TDD，任务安排移交实施计划。
- **禁止项**：禁止菜单、页面、字段、按钮和布局；禁止 URL、HTTP 方法、请求/响应结构、API 注解；禁止 Controller、Feign、Service、Mapper、Entity、DTO、VO、Command、Query、`R`、`Require`、`ErrorCode`；禁止表、列、索引、SQL、migration、模块路径、路由、component key、权限码、测试命令和开发任务。
- **正例**：审核员可以作出通过或拒绝的业务决定，并向提交人说明原因。
- **反例**：新增 `NoticeController` 的 `POST /notices/{id}/approve`，返回 `R<NoticeVO>`。错误原因：同时越过系统需求和技术设计边界。
- **机器判定**：合同按结构化文本节点执行禁止词、代码标识、路径模板和 SQL 片段检查；命中时报告本 `ruleId` 和所在章节。语义遗漏仍需业务负责人审核。
