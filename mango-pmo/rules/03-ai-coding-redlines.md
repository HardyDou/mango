# AI 编码红线

## 1. 适用范围

- 适用于 Mango 框架开发者。
- 适用于基于 Mango 的业务项目开发者。
- 适用于 Agent、人工开发者和人机协同开发。
- 适用于后端、前端、数据库、测试、配置、脚本和文档交付。

## 2. 禁止事项

- 禁止写伪代码。
- 禁止写 TODO、FIXME、未来再优化、临时方案。
- 禁止在业务实现、接口返回、页面交互、持久化数据或交付数据中写 mock、fake、dummy、hardcode 内容作为最终交付。
- 测试中的 mock、stub、fake、spy 必须遵循对应测试规范，禁止替代被测目标或冒充真实链路验收。
- 禁止写空实现。
- 禁止用 `UnsupportedOperationException`、空方法、固定返回值或接口壳子冒充已实现。
- 禁止 catch 后吞异常。
- 禁止返回固定成功。
- 禁止绕过权限、租户、数据权限。
- 禁止未接数据库却伪装完成。
- 禁止未接真实接口却伪装完成。
- 禁止把应由数据库、配置、字典、枚举中心或真实接口提供的数据写死在 Controller、Service、前端页面或测试替身中。
- 禁止在明确要求“重写”或“替换”时保留旧实现作为默认 fallback，或通过 feature detection、异常捕获、空值判断、开关和调用失败重新进入旧路径。
- 禁止以“能编译、能启动、能打开页面”替代真实业务链路、真实数据、真实权限和真实交互验收。
- 禁止交付明显低质量页面，包括布局混乱、字段无业务分组、联动字段分散、按钮区域不统一、状态表达不清、加载/空/错误态缺失。

## 2.1 默认变更行为

以下内容是 Agent 的默认判断方式，不是每个任务都要填写的检查表。每条规则分配条款 ID，供 Agent、Skill 和评测引用；Skill 只引用 ID，不复制本节正文。

### REDLINE-REUSE-010 复用优先顺序

先判断需求是否真的需要新增实现，再按以下顺序选择实现：

1. Mango 已有能力
2. 当前模块已有实现
3. 标准库（JDK、Spring、Vue、Element Plus）
4. 已安装依赖
5. 新增抽象、配置、接口、模块或依赖

只有第 1 至 4 项都不能满足需求时，才选择第 5 项。新增第 5 项时必须同时给出被放弃的复用对象和放弃原因。

### REDLINE-MINIMAL-020 最小充分实现

每个新增抽象、配置、接口、模块或依赖必须同时具备：

- 当前消费者：本次需求中真实调用它的人或代码，不接受“未来可能需要”。
- 责任边界：适用场景和不适用场景。
- 验证入口：能证明它工作的检查、测试或观察点。

“最小充分实现”只表示满足目标所需的最小完整方案，不表示通过减少代码删除安全、权限、租户、数据一致性、错误处理、可访问性或验证边界。

### REDLINE-TERMS-030 稳定术语

先复用已有主术语。新增公共类型、API、配置、权限码、事件、页面 key、Resource 类型或抽象概念时：

- 术语冲突或主名称不确定时必须 `ASK`。
- 禁止为已有概念创造同义词。
- 禁止直接重命名公共标识；重命名属于兼容性变更，必须走对应阶段判断。

### REDLINE-HIST-040 历史代码只是事实证据

历史代码、旧设计、旧提交和存量测试只能作为事实证据；与当前规则冲突时不得复制其写法。

### REDLINE-QUEST-050 简单任务不生成问卷

简单任务不生成固定问卷、无消费者文档或无观察目标的测试。只有出现新增公共概念或认知风险时，才按需记录术语决定。

### REDLINE-OVERDESIGN-060 过度设计判定

以下事实构成过度设计；Agent 在设计和编码时不得引入，Review 必须识别并给出文件与行号证据：

- 新增抽象，但本 PR 中没有消费者代码。
- 新增配置项，但没有读取该配置的逻辑。
- 新增接口或扩展点，但只有一个实现，且扩展需求未出现在已批准需求中。
- 新增依赖，但目标能力用标准库或已安装依赖即可实现。
- 新增公共类型，但只在单一模块内部使用。
- 同一概念在同一交付范围内出现多个名称，且没有迁移或兼容理由。
- 以“代码更整洁”为唯一理由新增抽象层，且没有架构规则或模块边界要求。

## 3. 必须满足

- 代码必须可编译。
- 单测必须可运行。
- 配置必须可启动。
- 接口必须有真实实现。
- 异常必须有明确处理。
- 日志必须有上下文。
- 数据必须来自数据库、配置或真实接口。
- 页面必须完成真实交互、真实数据回显和 UI 布局走查。
- 字典、菜单、权限、租户默认数据、状态映射、业务配置等持久化或可运营数据必须有明确数据来源和初始化方式。
- 不确定时必须先列出阻塞点。

## 3.1 重写与兼容边界

- “重写”或“替换”表示新实现成为交付范围内唯一执行路径；必须删除旧实现、旧调用、旧配置以及只服务旧路径的测试和兜底分支。
- 交付前必须搜索旧入口、旧标识、旧配置和 fallback 条件，证明运行时不能重新进入旧实现；只证明新路径存在不等于完成重写。
- 业务确需兼容迁移时，必须把兼容对象、适用期限、退出条件和验证入口定义为独立迁移需求；不得以“稳妥”为由把未定义期限的旧路径留在重写任务中。

## 4. 交付要求

- 交付报告必须说明实际验证命令和结果。
- 重写或替换任务必须说明旧实现、旧调用、旧配置和 fallback 的清理结果；存在获批兼容迁移时必须说明其退出条件和独立验证证据。
- 未连接真实数据库、真实接口或真实权限链路时，必须标记为阻塞或例外，禁止声明完成。
- 未完成真实 UI 走查、真实接口联调或真实数据来源确认时，必须标记为未验证，禁止声明页面或接口可用。
- 发现红线冲突时，必须先修复冲突；无法修复时，必须在交付台账中标记 `EXCEPTION` 并写明用户确认依据。
