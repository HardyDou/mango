# Agent 文本输出规范

## 1. 适用范围

- 适用于 Agent 发出的所有文本，以及 Agent 写入仓库的文档、PRD、SRS、技术设计、测试文档、实施计划、Issue、PR、沟通记录、交付记录和代码注释。
- 适用于中文、英文、表格、代码块、图示说明和生成的 HTML/视频文字稿。
- 本规则只约束表达质量，不减少文档合同要求，不改变事实、审批、测试或发布门禁。

## 2. 核心要求

每次输出前先明确：读者是谁、读者要做什么、什么结论最重要。然后按以下顺序表达：

1. 先写结论、影响或下一步。
2. 再写事实、依据和必要背景。
3. 最后写限制、失败边界、待确认事项和详细参考。

文本必须：

- 一句话表达一个主要意思；
- 优先使用主动语态和具体主语；
- 使用一个稳定术语，不为同一对象随意换名；
- 首次出现的术语先给直白含义，再给代码名或英文名；
- 区分 `事实`、`推断`、`决定`、`待确认`；
- 用路径、ID、错误码、角色、租户和状态等具体名词替代“相关逻辑”“适当处理”“后续优化”；
- 把重要的成功条件、失败条件、权限、租户、数据和风险写在正文，不藏在附注中；
- 使用短段落、标题、列表或表格帮助扫描，但不为形式增加重复内容。

## 3. 不同文本的最小结构

| 文本 | 先写什么 | 至少说明什么 |
|---|---|---|
| 沟通回复 | 结论或需要对方做的事 | 依据、影响、负责人、下一步 |
| PRD/需求文档 | 目标和真实场景 | 范围、成功/失败边界、验收标准、不做什么 |
| 技术文档 | 方案结论和适用边界 | 输入、责任、状态变化、接口、失败处理、验证入口 |
| 测试文档/结果 | 测了什么和结果 | 环境、数据、权限/租户、命令、证据、未测/阻塞项 |
| 实施计划 | 顺序、责任和交付物 | 依赖、完成标准、验证、阻塞和回退 |
| Issue | 影响和问题摘要 | 版本、复现、实际/期望、影响、证据 |
| 代码注释 | 为什么这样做 | 约束、风险或不能改成什么；不要复述代码本身 |

文档仍必须遵守对应模板、追踪、审批和证据要求；“简单明了”不是删除必填信息，也不是把多个独立决定压缩成一句空话。

## 4. 受控语言与输出媒介

- 用户要求“简单、重点、看懂”时，使用受控语言：短句、明确主语、一个动作一个句子、少用抽象名词和模糊指代。
- 可以使用图、HTML 或视频降低理解成本，但必须保留可复制的文字结论、失败边界和当前源码/文档引用。
- 图、HTML、视频是解释视图，不是规范源、验收证据或事实的替代品。
- 不声称文本符合 ASD-STE100 认证；需要时只能说明采用“受控语言”写法。
- 不同时生成多种媒介；只选择能降低当前读者理解成本的最小形式。

## 5. 禁止事项

- 禁止用长篇背景掩盖结论、风险或待办。
- 禁止用“简单”“高效”“无影响”“已完成”“通过”等结论替代证据。
- 禁止把“等等”“相关”“适当”“后续优化”当作范围、责任或失败处理。
- 禁止为了显得专业堆叠术语、缩写、英文或架构图。
- 禁止代码注释描述读者可以直接从代码读出的语句。
- 禁止用图、动画、HTML 或视频隐藏权限、租户、数据和错误边界。

## 6. 输出前检查

在发送或写入前，Agent 必须检查：

- 读者能否在开头找到结论或下一步；
- 每个关键结论是否有当前依据；
- 是否明确成功、失败、责任和未完成项；
- 是否存在未解释术语、同义词漂移或空泛表达；
- 是否删掉了不影响决定的背景和重复内容。

如果文本用于正式需求、设计、测试、计划、Issue、PR 或交付记录，还必须运行该资产对应的 checker；文本清晰不能替代机器门禁和人工审批。
